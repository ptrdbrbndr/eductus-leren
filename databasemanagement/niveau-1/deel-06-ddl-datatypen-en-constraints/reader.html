1. Leerdoelen

Na dit deel kun je:

  • tabellen aanmaken met passende datatypen en een onderbouwde keuze per kolom;
  • uitleggen waarom numeric voor geld en text voor tekst de standaardkeuzes zijn in PostgreSQL;
  • alle constrainttypen toepassen, inclusief EXCLUDE voor overlappende perioden;
  • identiteitskolommen aanmaken en het verschil met serial uitleggen;
  • DEFAULT, gegenereerde kolommen, domeinen en enums inzetten en hun nadelen benoemen;
  • een bestaande tabel wijzigen en de risico’s van die wijziging in productie inschatten;
  • het verschil tussen DELETE, TRUNCATE en DROP toepassen;
  • gebruikmaken van het feit dat DDL in PostgreSQL transactioneel is;
  • het model uit deel 5 omzetten in werkende DDL.

De kernboodschap van dit deel: elke regel die je niet in de database vastlegt, moet iemand anders onthouden. Constraints zijn geen luxe maar de plek waar het model uit deel 5 werkelijkheid wordt.

2. DDL, DML, DCL, TCL

SQL wordt traditioneel in vier groepen verdeeld:

Groep Wat Commando’s
DDL — Data Definition Structuur CREATE, ALTER, DROP, TRUNCATE
DML — Data Manipulation Gegevens INSERT, UPDATE, DELETE, SELECT
DCL — Data Control Rechten GRANT, REVOKE (deel 9)
TCL — Transaction Control Transacties BEGIN, COMMIT, ROLLBACK (deel 7)

Dit deel gaat over DDL. Nuttig om te weten voor het examen en voor het gesprek met collega’s; de indeling zelf is verder van beperkt praktisch belang.

3. CREATE TABLE

CREATE TABLE plaats (
    plaats_id  integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    naam       text NOT NULL,
    provincie  text,
    CONSTRAINT plaats_naam_uniek UNIQUE (naam)
);

Constraints kun je op kolomniveau schrijven (achter de kolom) of op tabelniveau (als aparte regel). Functioneel gelijk, met één verschil: een constraint over meerdere kolommen kan alleen op tabelniveau.

Geef constraints altijd een naam. Zonder naam verzint PostgreSQL er een (plaats_naam_key), en die verschijnt in foutmeldingen die je gebruikers te zien krijgen. Een zelfgekozen naam is bovendien nodig om de constraint later gericht te kunnen verwijderen.

Handige varianten:

CREATE TABLE IF NOT EXISTS …          -- geen fout als hij al bestaat
CREATE TEMP TABLE …                   -- verdwijnt aan het eind van de sessie
CREATE TABLE nieuw (LIKE bestaand INCLUDING ALL);   -- zelfde structuur
CREATE TABLE kopie AS SELECT …;       -- structuur én gegevens, maar ZONDER constraints

Die laatste is een bekende valkuil: CREATE TABLE AS SELECT neemt geen sleutels, constraints of indexen over. Je krijgt een tabel die eruitziet als het origineel en niets bewaakt.

4. Datatypen: numeriek

Type Bereik / precisie Gebruik
smallint ±32.767 Kleine tellers, jaartallen
integer ±2,1 miljard De standaardkeuze voor gehele getallen
bigint ±9,2 triljoen Identiteitskolommen van grote tabellen
numeric(p,s) Exact, willekeurige precisie Geld, alles waar exactheid telt
real / double precision Binaire benadering Wetenschappelijke metingen

De regel die je nooit vergeet: geld is numeric. Uit deel 3:

SELECT 0.1::float + 0.2::float = 0.3::float;        -- false
SELECT 0.1::numeric + 0.2::numeric = 0.3::numeric;  -- true

Bij een pensioenuitvoerder is een afrondingsverschil van een cent op honderdduizenden aanspraken geen academisch punt.

numeric(10,2) betekent: maximaal 10 cijfers in totaal, waarvan 2 achter de komma. Kies p ruim genoeg — het aanpassen van de precisie op een grote tabel is een operatie met downtime.

Over integer versus bigint voor sleutels: integer gaat tot 2,1 miljard. Dat lijkt genoeg tot je bedenkt dat een sequentie ook doorloopt bij mislukte transacties en verwijderde rijen. Voor tabellen die snel groeien (logregels, gebeurtenissen, mutaties) is bigint de veilige keuze; de extra vier bytes zijn zelden het probleem. Voor werkgever met 250 rijen is integer ruim voldoende.

5. Datatypen: tekst

Type Betekenis
text Onbegrensde tekst
varchar(n) Tekst met maximumlengte
varchar Gelijk aan text
char(n) Vaste lengte, aangevuld met spaties

In PostgreSQL is text de standaardkeuze. Anders dan in sommige andere DBMS’en levert een lengtelimiet hier geen prestatiewinst op; alle drie de typen worden intern hetzelfde opgeslagen.

Wanneer dan wél varchar(n)? Alleen als de lengte een echte bedrijfsregel is: een KvK-nummer is acht tekens, een ISO-landcode twee. Dan is de limiet documentatie én bewaking. Gebruik hem niet als vage schatting (“naam is vast niet langer dan 100”), want de eerste keer dat iemand een langere naam heeft, krijg je een productiefout op een regel die niemand ooit heeft bedacht.

char(n) moet je vermijden. De opvulling met spaties leidt tot verrassingen bij vergelijken en samenvoegen. In de casusdatabase is bsn char(9) gebruikt — verdedigbaar omdat een BSN altijd negen cijfers heeft, maar text met een CHECK op het formaat was beter geweest, omdat dat óók afdwingt dat het cijfers zijn.

6. Datatypen: datum en tijd

Type Legt vast
date Kalenderdatum
time Tijd zonder datum (zelden nuttig)
timestamp Datum en tijd zonder tijdzone
timestamptz Datum en tijd met tijdzonebesef
interval Tijdsduur
daterange, tstzrange Een periode als één waarde

Gebruik timestamptz, niet timestamp. timestamptz slaat een absoluut moment op en toont het in de tijdzone van de sessie. timestamp is een wandkloktijd zonder context: op de nacht van de zomertijdovergang is 2026-10-25 02:30 in Nederland dubbelzinnig, en de database kan je niet helpen.

De rangetypen verdienen aandacht, want ze lossen het historieprobleem uit deel 5 elegant op:

SELECT daterange(DATE '2024-01-01', DATE '2024-07-01', '[)') @> DATE '2024-03-15';
-- true

De notatie '[)' betekent: ondergrens inclusief, bovengrens exclusief — hetzelfde veilige patroon als bij datumfilters in deel 3. Een daterange maakt “geldig van/tot” één waarde in plaats van twee kolommen, en maakt de exclusion constraint uit paragraaf 16 mogelijk.

7. Datatypen: overige

Type Gebruik
boolean true / false / NULL
uuid Universeel unieke identificatie
bytea Binaire gegevens
inet, cidr, macaddr Netwerkadressen
jsonb Geïndexeerd, doorzoekbaar JSON
array Meerdere waarden van hetzelfde type
enum Vaste lijst van waarden

Over boolean en NULL: een boolean-kolom die NULL mag zijn, heeft drie toestanden. Bedoel je dat? Meestal niet — dan hoort er NOT NULL DEFAULT false bij. Bedoel je het wel (“we weten nog niet of deze deelnemer akkoord is”), leg het dan vast in de kolomnaam of het commentaar.

Over uuid als sleutel: aantrekkelijk bij gedistribueerde systemen, omdat elke bron zelf sleutels kan maken zonder centrale coördinatie. Nadelen: 16 bytes in plaats van 4 of 8, willekeurige volgorde (slechter voor indexlokaliteit), en onleesbaar in foutmeldingen en gesprekken. Voor Meridiaan is een identiteitskolom de betere keuze; in niveau 3 komt de gedistribueerde situatie terug waar dat kantelt.

8. jsonb en arrays: wanneer wel

Uit deel 5: jsonb voor wat je bewaart, kolommen voor wat je gebruikt.

Legitiem gebruik bij Meridiaan:

  • het ruwe bericht dat via een koppelvlak binnenkwam, bewaard voor onderzoek en aantoonbaarheid;
  • een configuratieblok dat als geheel wordt gelezen en geschreven;
  • schemaloze uitbreidingen die per soort verschillen en waarop je niet bewaakt.

Niet-legitiem: het adres in jsonb zetten “omdat het flexibeler is”. Op een adres wil je filteren, bewaken en historie voeren — dat zijn precies de dingen die jsonb je niet geeft.

CREATE TABLE koppelvlakbericht (
    bericht_id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    ontvangen_op timestamptz NOT NULL DEFAULT now(),
    bron        text NOT NULL,
    inhoud      jsonb NOT NULL
);

SELECT inhoud ->> 'bsn' FROM koppelvlakbericht;      -- als tekst
SELECT inhoud -> 'adres' ->> 'plaats' FROM koppelvlakbericht;

Arrays zijn een schending van 1NF en meestal een teken dat je een tabel mist. Uitzondering: een korte, vaste lijst waar je nooit los op filtert of naar verwijst — bijvoorbeeld een reeks tags. Zodra je een array wilt joinen, had het een tabel moeten zijn.

9. Sleutelwaarden genereren

-- Aanbevolen (standaard-SQL, sinds PostgreSQL 10)
deelnemer_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY

-- Ouder, PostgreSQL-eigen
deelnemer_id serial PRIMARY KEY

Beide gebruiken onderliggend een sequentie. Verschillen:

  • GENERATED ALWAYS verbiedt dat je zelf een waarde meegeeft (tenzij je OVERRIDING SYSTEM VALUE schrijft). Dat voorkomt de klassieke fout waarbij iemand handmatig een id invoegt en de sequentie daarna botsingen geeft.
  • GENERATED BY DEFAULT staat een eigen waarde wél toe — nuttig bij het migreren van bestaande gegevens.
  • serial is geen echt type maar een afkorting; het gedraagt zich als GENERATED BY DEFAULT en de sequentie is losser gekoppeld aan de kolom.

Advies: gebruik GENERATED ALWAYS AS IDENTITY voor nieuwe tabellen. Kom je serial tegen, dan hoef je het niet te vervangen, maar weet dat het legacy is.

Sequenties zijn niet gatenloos. Een teruggedraaide transactie geeft de gebruikte waarde niet terug. Wie een gatenloze nummering nodig heeft — factuurnummers bij de Belastingdienst, bijvoorbeeld — moet dat anders oplossen, met alle gevolgen voor gelijktijdigheid. Verwacht deze vraag van de business en beloof niets voordat je de gevolgen hebt uitgelegd.

10. Constraints: het contract met de werkelijkheid

Nu de kern van dit deel.

Een constraint is een regel die de database zelf afdwingt. Het alternatief is de regel in applicatiecode zetten — en dat gaat mis, om drie redenen:

  1. Er is bijna nooit één applicatie. Er is de applicatie, plus een importscript, plus een correctie die iemand met psql uitvoert, plus straks een tweede systeem.
  2. Applicatiecode wordt vervangen; gegevens blijven. De database van Meridiaan gaat twintig jaar mee; de applicatie erboven waarschijnlijk vijf.
  3. De database bewaakt bij gelijktijdigheid. Applicatiecode die “eerst kijken of het bestaat, dan invoegen” doet, faalt onder gelijktijdige belasting. Een UNIQUE-constraint niet.

Vuistregel: elke regel die je niet in de database vastlegt, moet iemand anders onthouden.

Dat betekent niet dat álles een constraint moet zijn. Regels die vaak wijzigen, die van externe gegevens afhangen of die per situatie verschillen, horen in de applicatie of in een referentietabel. Maar de standaardhouding is: leg het vast, tenzij.

11. NOT NULL

achternaam text NOT NULL

De eenvoudigste en meest verwaarloosde constraint. Uit deel 5: de optionaliteit die je in het model tekende, wordt hier NOT NULL of niet.

Wees streng. Een kolom die nullable is zonder reden, dwingt elke query die hem gebruikt om NULL te behandelen (deel 3), en elke ontwikkelaar om zich af te vragen wat NULL hier betekent. Kun je niet uitleggen wat NULL in deze kolom betekent, dan hoort er NOT NULL.

12. UNIQUE

kvk_nummer text NOT NULL UNIQUE
CONSTRAINT premienota_uniek_per_periode UNIQUE (werkgever_id, periode_jaar, periode_maand)

PostgreSQL maakt automatisch een index aan om een UNIQUE-constraint af te dwingen. Dat is een gratis bijeffect dat je in deel 8 leert waarderen.

Twee dingen om te weten:

  1. UNIQUE staat meerdere NULL’s toe (deel 2). Twee rijen met NULL in dezelfde unieke kolom zijn toegestaan, want ze zijn niet aantoonbaar gelijk. In de casus is dat precies wat we willen bij bsn.
  2. Gedeeltelijke uniciteit vereist een unieke index in plaats van een constraint:
CREATE UNIQUE INDEX deelnemer_actief_bsn_uniek
    ON deelnemer (bsn) WHERE einddatum_deelname IS NULL;

Hiermee zeg je: onder actieve deelnemers is het BSN uniek, maar historische rijen mogen het herhalen. Dat soort regel is met een gewone constraint niet uit te drukken.

13. PRIMARY KEY

deelnemer_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY

Een primaire sleutel is UNIQUE plus NOT NULL, en er is er maximaal één per tabel. Dat is de entiteitsintegriteitsregel uit deel 2, hier geïmplementeerd.

Uit deel 2, als cursusregel: surrogaatsleutel als primaire sleutel, natuurlijke sleutel als UNIQUE. In de casus is dat deelnemer_id als sleutel en bsn UNIQUE.

Elke tabel hoort een primaire sleutel te hebben. PostgreSQL staat een tabel zonder toe, maar dan kun je een individuele rij niet aanspreken — geen gerichte UPDATE, geen verwijzing, en logische replicatie (niveau 2) werkt niet. De enige verdedigbare uitzondering is een pure logtabel waarvan de rijen nooit individueel worden benaderd, en zelfs daar is een identiteitskolom goedkoop.

14. FOREIGN KEY

CONSTRAINT dienstverband_deelnemer_fk
    FOREIGN KEY (deelnemer_id) REFERENCES deelnemer (deelnemer_id)
    ON DELETE RESTRICT
    ON UPDATE CASCADE

De referentiële integriteit uit deel 2. Het gedrag bij verwijderen is daar behandeld; hier de praktische aanvullingen.

ON UPDATE CASCADE is bij surrogaatsleutels zelden nodig — die wijzigen immers nooit. Bij natuurlijke sleutels is het onmisbaar, wat op zichzelf een extra argument voor surrogaten is.

PostgreSQL maakt géén index aan op de foreign key-kolom. Dit is een van de bekendste valkuilen. De sleutel zelf (aan de ouderkant) is geïndexeerd; de verwijzende kolom niet. Gevolgen: joins zijn traag, en — belangrijker — elke DELETE op de oudertabel moet de hele kindtabel scannen om te controleren of er nog verwijzingen zijn.

In het casusscript staan die indexen daarom expliciet:

CREATE INDEX dienstverband_deelnemer_idx ON dienstverband (deelnemer_id);

Uitgestelde constraints. Soms moet je tijdelijk een inconsistente toestand toestaan binnen een transactie (bijvoorbeeld bij circulaire verwijzingen):

CONSTRAINT … FOREIGN KEY … DEFERRABLE INITIALLY DEFERRED

De controle vindt dan pas bij COMMIT plaats. Gebruik dit spaarzaam en bewust.

15. CHECK

CONSTRAINT deelnemer_deelname_logisch
    CHECK (einddatum_deelname IS NULL OR einddatum_deelname >= startdatum_deelname)

CONSTRAINT dienstverband_deeltijdfactor_bereik
    CHECK (deeltijdfactor > 0 AND deeltijdfactor <= 1)

CONSTRAINT aanspraak_soort_toegestaan
    CHECK (soort IN ('ouderdom','partner','wezen','arbeidsongeschiktheid'))

De domeinintegriteit uit deel 2. Drie aandachtspunten:

1. NULL en CHECK. Een CHECK die unknown oplevert, wordt toegestaan. CHECK (bedrag > 0) laat een NULL-bedrag dus door. Wil je dat niet, voeg dan NOT NULL toe — de CHECK doet dat niet voor je.

2. Een CHECK mag alleen naar de eigen rij kijken. Geen subquery’s, geen verwijzingen naar andere tabellen. Wie “het bedrag moet lager zijn dan het jaartotaal van deze werkgever” wil afdwingen, heeft een trigger nodig (niveau 2) of moet het in de applicatie doen.

3. Een lijst toegestane waarden in een CHECK is een ontwerpkeuze met kosten. Een nieuwe waarde toevoegen vereist ALTER TABLE, en dat lockt de tabel (paragraaf 19). Voor een stabiele lijst (de vier aanspraaksoorten) prima; voor een lijst die groeit is een referentietabel met een foreign key beter. Dit is precies zwakte 18.4 uit deel 5.

16. EXCLUDE: de constraint die je in deel 5 miste

In opdracht 5.6c wilde je voorkomen dat twee adresperioden van dezelfde deelnemer elkaar overlappen. Met UNIQUE lukt dat niet: de perioden zijn niet gelijk, ze overlappen alleen.

PostgreSQL heeft daar de exclusion constraint voor:

CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE adres (
    adres_id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    deelnemer_id integer NOT NULL REFERENCES deelnemer,
    straat       text NOT NULL,
    huisnummer   text NOT NULL,
    postcode     text NOT NULL,
    plaats_id    integer NOT NULL REFERENCES plaats,
    geldigheid   daterange NOT NULL,
    CONSTRAINT adres_geen_overlap
        EXCLUDE USING gist (deelnemer_id WITH =, geldigheid WITH &&)
);

Lees de constraint als: er mogen geen twee rijen bestaan waarvoor deelnemer_id gelijk is (=) én de geldigheidsperioden overlappen (&&).

De extensie btree_gist is nodig omdat je een gewoon type (integer) combineert met een rangetype in dezelfde index.

Waarom dit ertoe doet: zonder deze constraint moet de applicatie overlap bewaken, en dat faalt zodra twee mutaties gelijktijdig binnenkomen — precies het gelijktijdigheidsargument uit paragraaf 10. Met de constraint is het onmogelijk, ongeacht wie het probeert.

Dit is een van de dingen die PostgreSQL kan en de meeste andere DBMS’en niet. Het is het waard om te kennen.

17. DEFAULT en gegenereerde kolommen

aangemaakt_op timestamptz NOT NULL DEFAULT now(),
land          text        NOT NULL DEFAULT 'NL',
actief        boolean     NOT NULL DEFAULT true

Een DEFAULT geldt alleen als de kolom bij INSERT niet wordt genoemd. Geef je expliciet NULL mee, dan krijg je NULL (of een foutmelding bij NOT NULL) — niet de standaardwaarde.

Gegenereerde kolommen worden door de database zelf berekend en bijgehouden:

volledige_naam text GENERATED ALWAYS AS (
    concat_ws(' ', voorletters, tussenvoegsel, achternaam)
) STORED

Dit is de veilige vorm van de “denormalisatie” uit opdracht 5.5d: de waarde staat opgeslagen, maar niemand kan hem inconsistent maken, want alleen de database schrijft hem. De uitdrukking moet wel immutable zijn — je kunt er geen now() of een subquery in gebruiken.

18. DOMAIN en ENUM

Een domein is een hergebruikbaar type met constraints — precies het begrip “domein” uit deel 2, nu als taalconstructie:

CREATE DOMAIN bsn AS text
    CHECK (VALUE ~ '^[0-9]{9}$');

CREATE DOMAIN positief_bedrag AS numeric(12,2)
    CHECK (VALUE >= 0);

CREATE TABLE deelnemer (
    …
    bsn bsn UNIQUE,
    …
);

Voordeel: de regel staat op één plek en geldt overal waar het domein gebruikt wordt. Nadeel: het wijzigen van een domein dat in veel tabellen wordt gebruikt, raakt al die tabellen tegelijk.

Een enum is een type met een vaste waardenlijst:

CREATE TYPE aanspraaksoort AS ENUM ('ouderdom','partner','wezen','arbeidsongeschiktheid');

Aantrekkelijk, maar met echte nadelen: een waarde toevoegen kan (ALTER TYPE … ADD VALUE), een waarde verwijderen of hernoemen praktisch niet, en de sorteervolgorde is de definitievolgorde — wat verrast.

Advies voor deze cursus: voor een korte, stabiele lijst is een CHECK het eenvoudigst. Voor een lijst die groeit of waar je extra gegevens bij wilt (een omschrijving, een volgorde, een einddatum) is een referentietabel met een foreign key de beste keuze. Enums zijn zelden de moeite waard.

19. ALTER TABLE — en waarom het gevaarlijk is

ALTER TABLE deelnemer ADD COLUMN e_mailadres text;
ALTER TABLE deelnemer ALTER COLUMN woonplaats DROP NOT NULL;
ALTER TABLE deelnemer ADD CONSTRAINT deelnemer_land_geldig CHECK (land ~ '^[A-Z]{2}$');
ALTER TABLE deelnemer RENAME COLUMN woonplaats TO plaatsnaam;
ALTER TABLE deelnemer DROP COLUMN plaatsnaam;

Op een lege ontwikkelmachine is dit onschuldig. Op een productietabel met miljoenen rijen niet, en dit is de belangrijkste waarschuwing van dit deel.

Elke ALTER TABLE neemt een lock. Hoe zwaar, verschilt sterk:

Bewerking Kosten
Kolom toevoegen zonder default Vrijwel gratis (alleen metadata)
Kolom toevoegen met een constante default Vrijwel gratis in moderne versies
Kolom toevoegen met een volatiele default Herschrijft de hele tabel
Type wijzigen Herschrijft de hele tabel
NOT NULL toevoegen Scant de hele tabel
CHECK toevoegen Scant de hele tabel
Kolom verwijderen Vrijwel gratis (ruimte komt later vrij)

Een tabelherschrijving houdt gedurende de hele operatie een exclusieve lock vast: alle lezers en schrijvers wachten. Op een tabel van tien miljoen rijen kan dat minuten duren, en in die minuten staat de applicatie stil.

Het patroon om dat te vermijden — een constraint eerst NOT VALID toevoegen en daarna in een tweede stap valideren — hoort bij zero-downtime migraties en komt in niveau 2 (deel 22) en niveau 3 (deel 27) uitgebreid aan bod. Onthoud voor nu vooral: test elke ALTER TABLE op een kopie met productievolume voordat je hem uitvoert, en kijk hoe lang hij duurt.

20. DROP, DELETE en TRUNCATE

Commando Doet Terugdraaibaar in transactie
DELETE FROM t WHERE … Verwijdert rijen, rij voor rij Ja
TRUNCATE t Leegt de tabel in één keer Ja (in PostgreSQL)
DROP TABLE t Verwijdert de tabel zelf Ja (in PostgreSQL)

TRUNCATE is veel sneller dan DELETE omdat het geen rijen individueel verwerkt en geen dode rijversies achterlaat (MVCC, deel 2). Maar: het neemt een exclusieve lock, het activeert geen row-triggers, en het respecteert foreign keys alleen met CASCADE — wat betekent dat TRUNCATE … CASCADE ook de verwijzende tabellen leegt. Dat laatste is een van de effectiefste manieren om per ongeluk een database te wissen.

DROP TABLE … CASCADE verwijdert ook alle objecten die ervan afhangen: views, foreign keys, en meer. Gebruik het nooit in productie zonder eerst zonder CASCADE te proberen — de foutmelding vertelt je precies wat er afhangt, en dat is informatie die je wilt zien vóórdat je het weggooit.

21. DDL is transactioneel

Dit is een van de sterkste eigenschappen van PostgreSQL en het is een van de weinige plekken waar het duidelijk beter is dan de concurrentie.

BEGIN;

CREATE TABLE plaats (…);
INSERT INTO plaats (naam) SELECT DISTINCT initcap(trim(woonplaats)) FROM deelnemer WHERE woonplaats IS NOT NULL;
ALTER TABLE deelnemer ADD COLUMN plaats_id integer REFERENCES plaats;
UPDATE deelnemer SET plaats_id = p.plaats_id FROM plaats p WHERE p.naam = initcap(trim(deelnemer.woonplaats));
ALTER TABLE deelnemer DROP COLUMN woonplaats;

-- Controleren voordat je vastlegt:
SELECT count(*) FROM deelnemer WHERE plaats_id IS NULL AND woonplaats IS NOT NULL;

COMMIT;   -- of ROLLBACK als het niet klopt

In Oracle en MySQL wordt een DDL-opdracht automatisch vastgelegd; een half mislukte migratie laat je daar achter met een tabel die half is omgebouwd. In PostgreSQL draai je de hele migratie terug met één ROLLBACK.

Maak hier gebruik van. Zet elke migratie tussen BEGIN en COMMIT, voer controlequery’s uit vóór de COMMIT, en draai terug als er iets niet klopt. Dit is de belangrijkste praktische gewoonte uit dit deel.

(Uitzonderingen bestaan: CREATE INDEX CONCURRENTLY en VACUUM kunnen niet in een transactie. Die kom je in niveau 2 tegen.)

22. Naamgevingsconventies

Er is geen officiële standaard. Er is wel een verkeerde keuze: geen conventie hebben.

De conventie die deze cursus aanhoudt:

  • Kleine letters met liggende streepjes: deelnemer_id, geldig_van. Zo ontloop je het probleem met dubbele aanhalingstekens uit deel 3.
  • Tabelnamen enkelvoud: deelnemer, niet deelnemers. Een rij is één deelnemer. (Hierover bestaat oprechte onenigheid in het vak; kies één kant en wees consequent.)
  • Sleutelkolom <entiteit>_id.
  • Foreign key heet net als de kolom waarnaar hij verwijst.
  • Constraints: <tabel>_<kolom>_<soort>, bijvoorbeeld deelnemer_bsn_uniek, dienstverband_deelnemer_fk.
  • Geen afkortingen die niet in de organisatie gangbaar zijn. dv_dt_st bespaart tekens en kost begrip.
  • Geen gereserveerde woorden als naam: user, order, group, table. Ze werken alleen met dubbele aanhalingstekens en zijn daarna een blijvende ergernis.

23. Commentaar in de database

COMMENT ON TABLE deelnemer IS
    'Personen met pensioenaanspraken bij Meridiaan, inclusief slapers en gepensioneerden.';
COMMENT ON COLUMN deelnemer.einddatum_deelname IS
    'NULL betekent: deelname loopt nog. Zie beleidsregel PB-2024-03.';

Commentaar staat in de catalogus (deel 2) en is zichtbaar met \d+ in psql. Het reist mee met de database, ook als het projectdocument verdwijnt — en dat is precies wat er over twintig jaar gebeurd zal zijn.

Documenteer vooral de niet-vanzelfsprekende dingen: wat NULL betekent in een kolom, waarom een denormalisatie er staat, welke bedrijfsregel achter een CHECK zit. De kolomnaam achternaam heeft geen toelichting nodig.

24. Aansluiting op de certificering

Voor de Associate-certificering paraat:

  • de datatypen en hun toepassingsgebied, met nadruk op numeric versus float en text versus varchar;
  • alle constrainttypen en hun gedrag bij NULL;
  • GENERATED AS IDENTITY versus serial;
  • het gedrag van DELETE, TRUNCATE en DROP, inclusief CASCADE;
  • dat DDL in PostgreSQL transactioneel is;
  • dat een foreign key geen index aanmaakt op de verwijzende kolom.

Raadpleeg de actuele EDB-blauwdruk; deze cursus is voorbereiding, geen vervanging van het officiële examenmateriaal.

25. Kernbegrippen

DDL — de commando’s die structuur definiëren. Constraint — regel die de database zelf afdwingt. Identiteitskolom — automatisch gegenereerde sleutelwaarde. Exclusion constraint — verbiedt combinaties van rijen, bijvoorbeeld overlappende perioden. Gegenereerde kolom — kolom die de database zelf berekent en bijhoudt. Domein — hergebruikbaar type met constraints. Rangetype — een periode of bereik als één waarde. Tabelherschrijving — ALTER TABLE-bewerking die de hele tabel opnieuw schrijft, met exclusieve lock. Transactionele DDL — structuurwijzigingen die terugdraaibaar zijn.

Volgende deel: transacties, ACID en MVCC. Je hebt nu een database die regels afdwingt. Volgende keer kijken we wat er gebeurt als twee mensen tegelijk iets willen wijzigen — het probleem uit deel 1 dat we nog niet hebben opgelost.
