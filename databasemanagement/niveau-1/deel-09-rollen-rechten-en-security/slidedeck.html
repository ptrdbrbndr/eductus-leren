Slide 9 — Rollen

Geen aparte gebruikers en groepen. Alleen rollen — het verschil is LOGIN.

CREATE ROLE analist NOLOGIN;              -- groep
CREATE ROLE anouk LOGIN PASSWORD '…';     -- gebruiker
GRANT analist TO anouk;                   -- lidmaatschap

Slide 10 — Rechten aan groepen, niet aan personen

Anouk gaat weg.

Hoeveel handelingen zijn er nodig?

Groepsrol: één. Direct toegekend: uitzoekwerk dat zelden volledig lukt.

Slide 11 — VALID UNTIL

CREATE ROLE stagiair LOGIN PASSWORD '…'
    VALID UNTIL '2026-09-01';

Tijdelijke toegang met een einddatum.

Dan hoeft niemand eraan te denken.

Slide 12 — Rechten zijn hiërarchisch

GRANT CONNECT ON DATABASE meridiaan TO analist;
GRANT USAGE  ON SCHEMA meridiaan     TO analist;
GRANT SELECT ON ALL TABLES IN SCHEMA meridiaan TO analist;

Alle drie zijn nodig.

Vergeet je USAGE, dan krijgt de gebruiker een foutmelding die niets zegt over de oorzaak.

Slide 13 — En vergeet de sequenties niet

GRANT USAGE ON ALL SEQUENCES IN SCHEMA meridiaan TO schrijver;

Zonder dit faalt elke INSERT in een tabel met een identiteitskolom — met een fout over een object dat je nooit hebt aangemaakt.

Slide 15 — Voorspel

CREATE ROLE buitenstaander LOGIN PASSWORD 'test';

Kan deze rol nu iets?

Notities: vrijwel iedereen zegt nee. Verbind dan als buitenstaander.

Slide 16 — Het lukt

Niemand heeft deze rol

ook maar één recht gegeven.

PUBLIC heeft standaard CONNECT op elke nieuwe database. Iedereen is automatisch lid van PUBLIC.

Slide 17 — En verder?

SELECT * FROM pg_roles;

Werkt ook. De rol kent nu alle accounts op het cluster, inclusief wie superuser is.

Slide 18 — Dat is de stagiair

Account voor de werkgeversanalyse → via PUBLIC toegang tot elke database op het cluster

Niemand had hem dat gegeven.

Het stond aan.

Slide 19 — Dichtzetten

REVOKE CONNECT ON DATABASE meridiaan FROM PUBLIC;
REVOKE ALL ON SCHEMA public FROM PUBLIC;

⚠ Kan bestaande applicaties breken die er stilzwijgend op leunden. Test op acceptatie. Niet op vrijdagmiddag.

Slide 25 — Het BSN afschermen

Kolomrechten:

GRANT SELECT (deelnemer_id, achternaam, woonplaats)
    ON deelnemer TO analist;

Werkt — maar elke nieuwe kolom vereist onderhoud.

Slide 26 — Of: een view

CREATE VIEW deelnemer_beperkt AS SELECT … FROM deelnemer;
REVOKE ALL ON deelnemer FROM analist;
GRANT SELECT ON deelnemer_beperkt TO analist;

De view draait met de rechten van zijn eigenaar. Nul rechten op de tabel, en toch leesbaar.

Slide 30 — De belangrijkste regel

De applicatie is geen superuser.

Een superuser omzeilt élke rechtencontrole, élke row level security, élke auditmaatregel.

Bij een SQL-injectie ligt het hele cluster open.

Het rollenmodel bouwen

Slide 32 — Row level security

Kolomrechten beperken welke kolommen. RLS beperkt welke rijen.

CREATE POLICY deelnemer_eigen ON deelnemer
    FOR SELECT TO portaal_app
    USING (deelnemer_id = current_setting('app.deelnemer_id')::integer);

Slide 33 — Drie dingen over RLS

  1. De tabeleigenaar omzeilt RLS standaard → FORCE ROW LEVEL SECURITY
  2. Superusers omzeilen hem altijd → zie slide 30
  3. Het kost prestaties — indexeer de kolom in de policy

Slide 34 — De testfout

Je test als eigenaar. Je ziet alles. Je concludeert dat de policy niet werkt.

En dan ga je hem “repareren”

terwijl hij goed was.

Slide 36 — SECURITY DEFINER

CREATE FUNCTION mutatie_afronden(integer) …
SECURITY DEFINER
SET search_path = meridiaan, pg_temp

Eén afgebakende handeling, zonder rechten op de tabel.

SET search_path is niet optioneel.

Zonder is het rechtenescalatie.

Slide 37 — Encryptie

Onderweg — TLS. Altijd doen. In rust — schijfversleuteling. Kolom — pgcrypto; niet doorzoekbaar, niet indexeerbaar.

Encryptie in rust beschermt tegen

een gestolen schijf — niet tegen

iemand met een geldige verbinding.

Slide 38 — Auditing en AVG

log_statement = 'all' zet ook gegevens in de log.

Je logbestand wordt een tweede kopie

van je persoonsgegevens — met andere

toegangsregels.

De meest verwaarloosde maatregel: de ongeanonimiseerde productiekopie op acceptatie.
