Slide 1 — Titel

Indexen en views

Niveau 1 — Deel 8

Jullie database is correct. Nu maken we hem snel.

Slide 2 — “De database is traag”

Dat kan betekenen:

  • één query is traag
  • alles is traag
  • het is traag sinds vanochtend
  • het is traag sinds de laatste release
  • het is traag voor één gebruiker

Vijf verschillende problemen.

Slide 3 — De vier oorzaken

  1. Een ontbrekende index
  2. Verouderde statistieken → verkeerd plan
  3. Een query die te veel opvraagt
  4. Vergrendeling — hij rekent niet, hij wacht

Notities: op het bord, laat staan tot opdracht 8.7.

Slide 4 — Alleen bij nummer 1

helpt een index.

Bij nummer 4 helpt hij niets — en dat is precies waar mensen er het vaakst een toevoegen.

Slide 5 — B-tree

Gesorteerd, gebalanceerd. Zoeken als in een telefoonboek.

8 miljoen rijen → ongeveer 23 stappen

De index kent de waarde plus een verwijzing naar de rij.

Slide 6 — Waar een B-tree goed in is
= < > BETWEEN IN Ja
ORDER BY op dezelfde kolommen Ja — al gesorteerd
LIKE 'abc%' Ja
LIKE '%abc' Nee

Slide 7 — EXPLAIN

Seq Scan on deelnemer  (cost=0.00..205.00 rows=320 width=97)
  Filter: (achternaam = 'Jansen'::text)

cost = geschat, niet in seconden rows = geschat aantal width = bytes per rij

EXPLAIN voert de query niet uit.

Slide 8 — EXPLAIN ANALYZE

Seq Scan on deelnemer  (cost=0.00..205.00 rows=320 width=97)
                       (actual time=0.021..1.842 rows=298 loops=1)
  Rows Removed by Filter: 7702
  Buffers: shared hit=105
Execution Time: 1.903 ms

Slide 9 — Wat je zoekt in een plan

1. Rows Removed by Filter — hoog? → index ontbreekt

2. rows= tegenover actual rows=

Factor 10 verschil?

De statistieken kloppen niet.

Slide 10 — Waarschuwing

EXPLAIN ANALYZE voert de query uit.

Op een UPDATE betekent dat: de wijziging vindt plaats.

BEGIN;
EXPLAIN ANALYZE UPDATE …;
ROLLBACK;

Slide 14 — Pauze

Slide 15 — Seq Scan is geen fout

Sequentieel is de beste keuze wanneer:

  • de tabel klein is
  • je meer dan ~5-10% van de rijen nodig hebt
  • je toch alles nodig hebt

Slide 16 — De juiste vraag

Zie je een Seq Scan waar je een index verwachtte:

Niet: “hoe dwing ik een index af?”

Wel: "waarom denkt de planner dat dit

goedkoper is — en heeft hij gelijk?"

Meestal heeft hij gelijk.

Slide 17 — Joinalgoritmen

Nested Loop — per rij links zoeken rechts Hash Join — hashtabel van de kleinste kant Merge Join — beide gesorteerd doorlopen

Je kiest ze niet. Je leest ze.

Let op Nested Loop met een hoge loops.

Slide 18 — De klassieke fout

-- index op geboortedatum wordt NIET gebruikt
WHERE extract(year FROM geboortedatum) = 1960

-- wél
WHERE geboortedatum >= DATE '1960-01-01'
  AND geboortedatum <  DATE '1961-01-01'

Een functie om de kolom

maakt de index onbruikbaar.

Slide 19 — Of: expressie-index

CREATE INDEX ON deelnemer (lower(achternaam));

Maar: herschrijven verslaat een expressie-index.

De herschrijving is gratis. De index kost onderhoud.

Slide 21 — Samengestelde index

CREATE INDEX ON premienota (werkgever_id, periode_jaar, periode_maand);
Filter op Bruikbaar?
werkgever_id Ja
werkgever_id + periode_jaar Ja
alleen periode_jaar Nee

Slide 22 — Twee regels

1. Bruikbaar voor een voorvoegsel

van de kolommen.

2. Gelijkheid vóór bereik.

WHERE werkgever_id = 42 AND jaar >= 2024 → index op (werkgever_id, jaar)

Slide 23 — Opdracht 8.4

Kolomvolgorde

Vier query’s, één index. Welke werken?

20 min, tweetallen

Slide 24 — Pauze

Slide 25 — Partiële index

CREATE INDEX mutatie_open_idx
    ON mutatie (aangemeld_op)
    WHERE verwerkt_op IS NULL;

12% van de rijen → ongeveer ⅛ van de omvang

En: verwerkte rijen verdwijnen eruit. De index groeit niet mee met de historie.

Slide 26 — Covering index

CREATE INDEX ON dienstverband (deelnemer_id) INCLUDE (jaarsalaris);

Alle gevraagde kolommen in de index → Index Only Scan, de tabel blijft ongemoeid.

Kosten: grotere index.

Slide 28 — Wat een index kost

  1. Schijfruimte
  2. Schrijfsnelheid — elke INSERT/UPDATE/DELETE werkt élke index bij

Slide 29 — De afweging

Een index die één rapport per dag versnelt

en duizend schrijfbewerkingen per uur vertraagt,

is een verlies.

Meet beide kanten.

Slide 30 — Opdracht 8.6

De kosten van indexen

Slide 31 — Prestatiefolklore

Allemaal onjuist of achterhaald:

  • count(1) is sneller dan count(*)
  • IN is trager dan OR
  • meer indexen is beter
  • CTE’s zijn altijd traag (niet meer sinds v12)
  • SELECT * maakt niets uit

Niet zelf gemeten = gerucht.

Slide 33 — De conclusie van 8.7

Slide 34 — Views

CREATE VIEW actieve_deelnemer AS
SELECT … FROM deelnemer WHERE einddatum_deelname IS NULL;

Slaat geen gegevens op — de query draait elke keer.

Slide 35 — Waarom een view ertoe doet

Deel 1: drie afdelingen, drie deelnemersaantallen.

Een view legt vast wat

“actieve deelnemer” betekent.

Eén plek. Zichtbaar. Wijziging werkt overal door.

Slide 36 — Materialized view

Slaat het resultaat wel op.

REFRESH MATERIALIZED VIEW CONCURRENTLY …;   -- vereist unieke index

De nette vorm van denormalisatie uit deel 5.

Slide 37 — Het risico

Een materialized view die stilletjes

stopt met verversen, ziet er precies

hetzelfde uit als een actuele.

Regel: bewaak de verversing, en zet het verversmoment in de gegevens.
