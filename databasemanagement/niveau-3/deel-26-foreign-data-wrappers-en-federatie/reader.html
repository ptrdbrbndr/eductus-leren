1. Leerdoelen

Na dit deel kun je:

  • uitleggen welk architectuurprobleem foreign data wrappers oplossen, in samenhang met deel 23;
  • postgres_fdw opzetten tussen twee zelfstandige databases;
  • foreign tables aanmaken en bevragen, en het verschil met een lokale tabel benoemen;
  • via EXPLAIN zien welk deel van een query wordt doorgeschoven naar de externe server en welk deel lokaal gebeurt;
  • een federatieve rapportagelaag ontwerpen voor de Pensioenfederatie;
  • FDW, logische replicatie en Citus tegen elkaar afwegen als drie manieren om meerdere databases te verbinden;
  • beoordelen of schrijven via een foreign table verstandig is;
  • de keuze voor FDW beargumenteren of afraden voor een gegeven scenario.

2. Het gat dat deel 23 openliet

In deel 23 werd de architectuurkeuze gemaakt: Meridiaan en Kompas op patroon 2 (schema per fonds), Baken op patroon 3 (eigen database). In deel 24 en 25 loste sharding een ander probleem op: horizontale capaciteit voor de kerngegevens van één, groot geheel.

Geen van beide loste de vraag op die in deel 23, paragraaf 10, expliciet openbleef: hoe bouwt de federatie een gezamenlijke rapportage als de gegevens over gescheiden databases (of zelfs servers) verspreid staan?

Logische replicatie (deel 18, 22) is één antwoord: kopieer de relevante gegevens naar een aparte rapportagedatabase. Dat werkt, maar introduceert vertraging (de kopie loopt per definitie achter) en een tweede plek waar dezelfde gegevens staan, met de bijbehorende beheerlast.

Dit deel behandelt het andere antwoord: query’s die rechtstreeks, live, over de grenzen van afzonderlijke databases heen gaan — zonder de data te dupliceren. Dat heet federatie, en het gereedschap ervoor in PostgreSQL is de foreign data wrapper.

3. Wat een foreign data wrapper is

Een foreign data wrapper (FDW) is een PostgreSQL-extensie die een externe gegevensbron laat verschijnen als een gewone tabel binnen een lokale database, zonder de gegevens fysiek te kopiëren.

Coördinerende database (federatie-rapportage)
        │
        │  ziet "foreign tables" die eruitzien als gewone tabellen
        ▼
   postgres_fdw
        │
   ┌────┼────┬────────┐
   ▼    ▼    ▼         
Meridiaan  Kompas  Baken
(elk een eigen, zelfstandige database)

postgres_fdw is de wrapper die specifiek een andere PostgreSQL-database als bron gebruikt — het meest voorkomende geval bij een architectuur die zelf al volledig uit PostgreSQL bestaat, zoals de Pensioenfederatie. Andere wrappers bestaan voor niet-PostgreSQL-bronnen (bijvoorbeeld file_fdw voor platte bestanden, of wrappers voor andere databasesystemen), maar die vallen buiten dit deel.

Het cruciale verschil met alles wat eerder in deze cursus over meerdere servers ging (replicatie in deel 18, sharding in deel 24-25): een foreign table bevraagt de externe server op het moment van de query, live. Er is geen kopie, geen vertraging door replicatie-lag (deel 18, paragraaf 6) — maar wel de kosten van een netwerkverbinding bij elke bevraging.

4. postgres_fdw opzetten

-- Op de federatieve rapportagedatabase
CREATE EXTENSION postgres_fdw;

-- Een server-definitie per bron
CREATE SERVER meridiaan_server
    FOREIGN DATA WRAPPER postgres_fdw
    OPTIONS (host 'meridiaan-db-host', port '5432', dbname 'meridiaan');

CREATE SERVER kompas_server
    FOREIGN DATA WRAPPER postgres_fdw
    OPTIONS (host 'kompas-db-host', port '5432', dbname 'kompas');

CREATE SERVER baken_server
    FOREIGN DATA WRAPPER postgres_fdw
    OPTIONS (host 'baken-db-host', port '5432', dbname 'baken');

-- Een user mapping: met welke identiteit wordt op de bron ingelogd
CREATE USER MAPPING FOR federatie_rapportage
    SERVER meridiaan_server
    OPTIONS (user 'fdw_leesrol', password 'wachtwoord');

De rol fdw_leesrol op elke bron-database verdient dezelfde aandacht als elke andere rol in deze cursus (deel 9, 21): minimale rechten, alleen leestoegang tot precies de tabellen die de federatie nodig heeft — niet een brede beheerdersrol “voor het gemak”.

5. Foreign tables gebruiken

-- Handmatig, tabel voor tabel
CREATE FOREIGN TABLE meridiaan_deelnemer (
    deelnemer_id integer,
    achternaam   text,
    fonds_id     integer
) SERVER meridiaan_server
  OPTIONS (schema_name 'meridiaan_prod', table_name 'deelnemer');

-- Of, sneller: importeer een heel schema in één keer
IMPORT FOREIGN SCHEMA meridiaan_prod
    LIMIT TO (deelnemer, dienstverband, premienota)
    FROM SERVER meridiaan_server
    INTO federatie_meridiaan;

IMPORT FOREIGN SCHEMA is in de praktijk vrijwel altijd te verkiezen boven handmatig elke tabel opnieuw te definiëren — het leest de structuur rechtstreeks van de bron en voorkomt dat een handmatige definitie uit de pas loopt met een structuurwijziging op de bron (een vorm van drift die lijkt op het schema-drift-risico uit deel 23).

Eenmaal aangemaakt, gedraagt een foreign table zich grotendeels als een gewone tabel:

SELECT * FROM federatie_meridiaan.deelnemer WHERE deelnemer_id = 42;

Deze query lijkt lokaal, maar PostgreSQL stuurt hem (of een deel ervan) naar de Meridiaan-server, ontvangt het resultaat, en presenteert het alsof het lokaal was opgehaald.

6. Wat wordt doorgeschoven: predicate en join pushdown

De reden dat FDW bruikbaar is en niet gewoon “alles ophalen en lokaal filteren”: PostgreSQL is slim genoeg om een deel van het werk naar de bron te verplaatsen.

SELECT * FROM federatie_meridiaan.deelnemer WHERE deelnemer_id = 42;

Predicate pushdown: de WHERE-voorwaarde wordt meegestuurd naar Meridiaans server, die zelf filtert en alleen de relevante rij(en) teruggeeft — niet de hele tabel. Dit is vergelijkbaar met hoe een index in deel 8 werkt, maar dan over een netwerkverbinding.

SELECT d.achternaam, dv.werkgever_id
FROM federatie_meridiaan.deelnemer d
JOIN federatie_meridiaan.dienstverband dv USING (deelnemer_id)
WHERE d.deelnemer_id = 42;

Join pushdown: als beide tabellen van dezelfde foreign server komen, kan PostgreSQL soms de hele join naar die server verplaatsen — de bron voert de join zelf uit en stuurt alleen het eindresultaat terug, in plaats van twee aparte resultaten die lokaal moeten worden samengevoegd.

Aggregate pushdown (sinds recentere PostgreSQL-versies) laat zelfs een count() of sum() op de bron zelf uitvoeren, in plaats van alle rijen op te halen en lokaal te tellen.

7. Wat niet wordt doorgeschoven: de grenzen van pushdown

-- Een join tussen TWEE VERSCHILLENDE foreign servers: geen pushdown mogelijk
SELECT m.achternaam, k.achternaam
FROM federatie_meridiaan.deelnemer m, federatie_kompas.deelnemer k
WHERE m.achternaam = k.achternaam;

Dit is het federatieve equivalent van een cross-shard-join uit deel 24-25. Meridiaan en Kompas zijn twee volledig gescheiden servers; geen van beide kan de join van de ander uitvoeren. PostgreSQL moet alle relevante rijen van beide bronnen ophalen en de join lokaal, op de coördinerende database, uitvoeren — met alle netwerk- en geheugenkosten die daarbij horen.

Andere grenzen:

  • Lokale functies en complexe expressies in de WHERE-clausule worden vaak niet doorgeschoven, met hetzelfde soort gevolg als de functie-op-kolom-valkuil uit deel 8, 13 en 16 — de bron kan de voorwaarde niet zelf toepassen, dus haalt meer op dan nodig en filtert lokaal.
  • Sorteren en limiteren over meerdere bronnen (ORDER BY ... LIMIT 10 over een federatieve UNION van Meridiaan, Kompas en Baken) kan niet worden doorgeschoven als geheel — elke bron moet zijn eigen top-N teruggeven, en de coördinator sorteert en beperkt daarna opnieuw.
  • Statistieken over de foreign table zijn beperkter dan bij een lokale tabel (deel 8, 13) — de planner kent de werkelijke verdeling van de bron minder goed, tenzij je ANALYZE expliciet op de foreign table uitvoert om een schatting te verzamelen.

8. EXPLAIN op een foreign table

EXPLAIN SELECT * FROM federatie_meridiaan.deelnemer WHERE deelnemer_id = 42;

Foreign Scan on deelnemer
  Remote SQL: SELECT deelnemer_id, achternaam, fonds_id
              FROM meridiaan_prod.deelnemer WHERE (deelnemer_id = 42)

Remote SQL toont precies wat naar de bron wordt gestuurd — dit is het equivalent van Task Count in Citus (deel 25) en pruning in deel 16: een expliciet, controleerbaar signaal of je query het gunstige pad neemt.

EXPLAIN SELECT m.achternaam, k.achternaam
FROM federatie_meridiaan.deelnemer m, federatie_kompas.deelnemer k
WHERE m.achternaam = k.achternaam;

Nested Loop
  ->  Foreign Scan on deelnemer m   -- haalt Meridiaans hele tabel op
  ->  Foreign Scan on deelnemer k   -- haalt Kompas' hele tabel op
      (join gebeurt lokaal, na het ophalen)

De discipline blijft ongewijzigd sinds deel 8: controleer met EXPLAIN of je aanname over wat er gebeurt, klopt — vertrouw niet op hoe een query eruitziet.

9. De federatieve rapportagelaag voor de Pensioenfederatie

Het concrete antwoord op de vraag die in deel 23 openbleef:

CREATE VIEW federatie_rapportage.deelnemers_per_fonds AS
SELECT 'Meridiaan' AS fonds, count(*) FROM federatie_meridiaan.deelnemer
UNION ALL
SELECT 'Kompas', count(*) FROM federatie_kompas.deelnemer
UNION ALL
SELECT 'Baken', count(*) FROM federatie_baken.deelnemer;

Elke deelquery in deze UNION ALL wordt naar de betreffende bron doorgeschoven (predicate/aggregate pushdown, paragraaf 6) — de coördinerende database voert alleen de laatste stap uit: de drie deelresultaten samenvoegen.

Governance blijft, zoals in deel 23, expliciet nodig: welke kolommen worden via de foreign tables ontsloten (geen BSN in de gezamenlijke rapportagelaag, dataminimalisatie uit deel 9/21), en wie mag de federatieve rapportagedatabase bevragen.

10. Materialized views bovenop foreign tables

Het probleem met live federatie: elke keer dat iemand het dashboard opent, worden alle drie de bronnen live bevraagd — bij een zware aggregatie (Karins kwartaaloverzicht) kan dat traag zijn en onnodige belasting op de bronservers leggen, precies op het moment dat veel mensen tegelijk het dashboard willen zien.

CREATE MATERIALIZED VIEW federatie_rapportage.kwartaaloverzicht AS
SELECT fonds, sector, sum(bedrag) AS totaal
FROM (... federatieve query over alle drie de bronnen ...) x
GROUP BY fonds, sector;

REFRESH MATERIALIZED VIEW federatie_rapportage.kwartaaloverzicht;

Dit is exact het patroon uit deel 8, nu toegepast op federatieve in plaats van lokale gegevens: de dure, cross-server-aggregatie gebeurt eenmalig (bijvoorbeeld 's nachts), en interactieve raadplegingen lezen de al-berekende materialized view — snel, maar per definitie een moment achter de werkelijkheid, net als elke materialized view.

De afweging is dezelfde als in deel 8: hoe actueel moet het dashboard zijn? Voor een kwartaaloverzicht is een nachtelijke verversing ruim voldoende; voor een operationeel dashboard zou dat te traag kunnen zijn, wat dan weer richting logische replicatie (deel 18, met zijn eigen, kleinere vertraging) wijst.

11. FDW versus logische replicatie versus Citus

Drie manieren om meerdere databases met elkaar te laten samenwerken, elk met een ander profiel:

FDW Logische replicatie Citus
Data gedupliceerd? Nee Ja Ja (over shards)
Actualiteit Live (elke query) Vertraging (lag) Live (binnen het cluster)
Geschikt voor Ad-hoc, incidentele cross-database-query’s Een continu bijgewerkte kopie voor rapportage Eén logisch, horizontaal geschaald geheel
Schrijven mogelijk? Beperkt (paragraaf 13) Ja, op de bron; het doel is meestal read-only Ja, overal, met Citus’ coördinatie
Beheerlast Laag (geen extra opslag) Middel (een tweede kopie onderhouden) Hoog (een volledig gedistribueerd systeem)

Voor de Pensioenfederatie: FDW past bij incidentele, ad-hoc federatieve vragen (“hoeveel deelnemers hebben Meridiaan en Kompas samen”) en bij de rapportagelaag uit paragraaf 9-10. Logische replicatie (zoals voorgesteld in deel 23, opdracht 23.7) past beter bij een continu, snel bijgewerkt dashboard. Citus (deel 24-25) lost een ander probleem op — horizontale capaciteit binnen één logisch geheel — en is voor de federatie als los-gekoppelde verzameling zelfstandige fondsen niet het juiste gereedschap; het past beter binnen één fonds als dat fonds zelf op een gegeven moment moet shardten.

12. Rechten en credentials over een FDW-verbinding

De user mapping bevat een wachtwoord dat, net als elk ander wachtwoord in deze cursus (deel 9, 21), niet losjes behandeld mag worden.

-- Rechten op de user mapping zelf
REVOKE ALL ON FOREIGN SERVER meridiaan_server FROM PUBLIC;
GRANT USAGE ON FOREIGN SERVER meridiaan_server TO federatie_rapportage;

Op de bron-database (Meridiaan, Kompas, Baken) hoort de fdw_leesrol een minimaal recht te krijgen — alleen SELECT op precies de kolommen die de federatieve rapportage nodig heeft, met dezelfde dataminimalisatie-discipline als bij elke andere rol (deel 9, 21). Een BSN-kolom hoort niet in de geïmporteerde foreign tables als de rapportagelaag die nooit nodig heeft.

SSL blijft van toepassing (deel 21): de verbinding tussen de coördinerende database en elke bron moet net zo goed versleuteld zijn als elke andere verbinding met persoonsgegevens.

CREATE SERVER meridiaan_server
    FOREIGN DATA WRAPPER postgres_fdw
    OPTIONS (host 'meridiaan-db-host', port '5432', dbname 'meridiaan', sslmode 'verify-full');

13. Schrijven via een foreign table

INSERT INTO federatie_meridiaan.deelnemer (achternaam, fonds_id) VALUES ('Jansen', 1);

Technisch mogelijk, maar met belangrijke beperkingen die het risicovol maken voor kritieke schrijfoperaties:

  • Geen transactionele garantie over meerdere foreign servers heen — een INSERT op Meridiaan en een op Kompas binnen dezelfde lokale transactie zijn niet atomair gekoppeld, hetzelfde probleem als cross-shard-transacties (deel 24, paragraaf 7), nu tussen volledig onafhankelijke databases.
  • Constraints en triggers op de bron gelden nog steeds, maar fouten daar zijn voor de schrijvende sessie soms lastiger te doorgronden dan bij een lokale schrijfactie.
  • Prestatie: elke schrijfactie via FDW kost een volledige netwerk-rondgang, trager dan een lokale INSERT.

De aanbeveling: gebruik FDW primair voor lezen. Voor schrijfoperaties die de grens van een database moeten oversteken, is een expliciet ontworpen patroon (een applicatie die zelf naar de juiste bron schrijft, of een berichtenwachtrij) meestal beter te doorgronden en te beheersen dan schrijven via een foreign table.

14. Wanneer FDW de juiste keuze is, wanneer niet

FDW past goed bij: ad-hoc, incidentele cross-database-rapportage; een federatieve laag bovenop een architectuur die al uit patroon 2/3-gescheiden databases bestaat (deel 23); situaties waar duplicatie van gegevens (zoals bij logische replicatie) onwenselijk is, bijvoorbeeld om opslagkosten of AVG-redenen (minder plekken waar dezelfde persoonsgegevens staan, deel 9).

FDW past minder goed bij: frequente, prestatiekritieke query’s die continu dezelfde federatieve join uitvoeren (elke keer een nieuwe netwerk-rondgang is duur, in tegenstelling tot een lokale, gerepliceerde kopie); schrijfoperaties die transactionele garanties over de grenzen van databases heen vereisen; en query’s met veel cross-server-joins tussen verschillende bronnen (paragraaf 7 — geen pushdown, alles lokaal samenvoegen).

De vraag die je stelt vóór je FDW gebruikt: is dit een incidentele, leesgerichte behoefte die duplicatie niet rechtvaardigt? Zo ja, FDW. Is het een continue, snelle behoefte? Overweeg logische replicatie. Is het onderdeel van één logisch, horizontaal geschaald geheel? Dat is Citus, niet FDW.

15. Veelgemaakte fouten

Fout Gevolg Beter
Foreign tables handmatig definiëren in plaats van IMPORT FOREIGN SCHEMA Drift tussen bron en foreign table-definitie IMPORT FOREIGN SCHEMA, opnieuw uitvoeren na brondwijzigingen
Aannemen dat elke join wordt doorgeschoven Trage query’s zonder duidelijke oorzaak EXPLAIN, Remote SQL controleren
Cross-server-joins tussen verschillende bronnen verwachten als lokaal Onderschatte kosten, alle data lokaal samengevoegd Beperken tot wat elke bron zelf kan filteren
Een brede beheerdersrol gebruiken voor de user mapping Onnodig risico bij een gecompromitteerde federatieve laag Minimale, specifieke leesrol per bron
Kritieke schrijfoperaties via foreign tables laten lopen Geen transactionele garantie over servers heen FDW primair voor lezen; schrijven expliciet ontwerpen
FDW gebruiken voor een continu, snel dashboard Onnodige belasting op bronservers bij elke raadpleging Materialized view, of logische replicatie
Geen SSL op de FDW-verbinding Onversleuteld verkeer met persoonsgegevens tussen databases sslmode expliciet instellen, net als bij elke andere verbinding

16. Kernbegrippen

Foreign data wrapper (FDW) — mechanisme dat een externe bron laat verschijnen als een lokale tabel. postgres_fdw — de wrapper specifiek voor een andere PostgreSQL-database als bron. Foreign server — de verbindingsdefinitie naar een externe bron. User mapping — de identiteit waarmee wordt ingelogd op de externe bron. Foreign table — de lokale representatie van een externe tabel. IMPORT FOREIGN SCHEMA — bulk-import van foreign table-definities vanaf de bron. Predicate/join/aggregate pushdown — het verplaatsen van filter-, join- of aggregatiewerk naar de bron. Federatie — het samenbrengen van gegevens uit meerdere, zelfstandige bronnen zonder duplicatie. Remote SQL — het deel van een EXPLAIN-plan dat toont wat naar de bron wordt gestuurd.
