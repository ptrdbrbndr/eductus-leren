1. Leerdoelen

Na dit deel kun je:

  • de architectuur van een Citus-cluster (coördinator, workers) beschrijven;
  • een distributed table en een reference table aanmaken en hun onderlinge samenhang uitleggen;
  • co-locatie expliciet configureren met colocate_with;
  • een EXPLAIN-plan op een distributed query lezen en onderscheid maken tussen lokale en cross-shard-uitvoering;
  • rebalancing met Citus’ ingebouwde gereedschap uitvoeren en de risico’s herkennen die ondanks automatisering blijven bestaan;
  • een bestaande, gepartitioneerde PostgreSQL-tabel migreren naar een Citus distributed table;
  • beoordelen of Citus voor een gegeven situatie het juiste gereedschap is.

2. Wat Citus is en wat het niet is

Citus is een PostgreSQL-extensie — geen apart databasesysteem, geen fork. Je installeert hem op een gewone PostgreSQL-installatie (dezelfde manier waarop je pg_trgm of pgcrypto installeerde in deel 14 en 21), en hij voegt sharding-functionaliteit toe aan wat verder gewoon PostgreSQL is.

Wat dat concreet betekent:

  • Alle SQL die je in niveau 1 en 2 leerde, blijft geldig.
  • Alle systeemweergaven uit deel 20 blijven bestaan, met Citus-specifieke aanvullingen.
  • Elke node in een Citus-cluster is een volwaardige PostgreSQL-server, met alles wat daarbij hoort: WAL, vacuum, indexen, replicatie (deel 18), zelfs Patroni voor HA per node (deel 19) indien gewenst.

Wat Citus toevoegt: een laag die weet hoe een logische tabel over meerdere fysieke servers wordt verdeeld, en die query’s herschrijft zodat ze — voor de gebruiker onzichtbaar — over de juiste shards worden uitgevoerd en de resultaten worden samengevoegd.

Dit deel implementeert letterlijk de concepten uit deel 24. Elke term uit dat deel (shardsleutel, co-locatie, referentietabel, rebalancing) krijgt hier een concrete CREATE-opdracht.

3. De architectuur: coördinator en workers

                  ┌──────────────┐
   Applicatie ──→ │ Coördinator  │
                  │ (weet WAT    │
                  │  waar staat) │
                  └──────┬───────┘
           ┌─────────────┼─────────────┐
           ▼             ▼             ▼
     ┌──────────┐  ┌──────────┐  ┌──────────┐
     │ Worker 1 │  │ Worker 2 │  │ Worker 3 │
     │ (shards) │  │ (shards) │  │ (shards) │
     └──────────┘  └──────────┘  └──────────┘

De coördinator is het aanspreekpunt voor de applicatie. Hij bevat geen shard-data zelf (in de gangbare opzet), maar wel de metadata: welke tabel is gesherd, op welke sleutel, en welke shard op welke worker staat. Elke query komt bij de coördinator binnen, die hem herschrijft naar een of meerdere queries op de betrokken workers en de resultaten samenvoegt.

De workers zijn gewone PostgreSQL-servers die de daadwerkelijke shards bevatten — elk een fysieke tabel die een deel van de logische, gesharde tabel vertegenwoordigt.

Belangrijke nuance: de coördinator kan een single point of failure zijn tenzij hij zelf ook met Patroni (deel 19) hoogbeschikbaar wordt gemaakt. Recente Citus-versies ondersteunen ook een opzet zonder aparte coördinator-node (elke node kan coördinator én worker zijn), maar het klassieke model met een aparte coördinator blijft het meest voorkomend en het duidelijkst om te leren.

4. Een cluster opzetten

Conceptueel, per node:

-- Op elke node (coördinator én workers)
CREATE EXTENSION citus;

-- Alleen op de coördinator: workers registreren
SELECT citus_add_node('worker1-host', 5432);
SELECT citus_add_node('worker2-host', 5432);
SELECT citus_add_node('worker3-host', 5432);

-- Controleren
SELECT * FROM citus_get_active_worker_nodes();

Vanaf dit punt gedraagt de coördinator zich naar de applicatie toe als één gewone PostgreSQL-database — het enige verschil is dat sommige tabellen (die je hierna expliciet distribueert) hun data over de workers hebben verspreid.

5. Distributed tables aanmaken

-- Eerst een gewone tabel, zoals altijd
CREATE TABLE deelnemer (
    deelnemer_id integer GENERATED ALWAYS AS IDENTITY,
    fonds_id     integer NOT NULL,
    achternaam   text NOT NULL,
    bsn_hash     text NOT NULL,
    PRIMARY KEY (deelnemer_id)
);

-- Dan: distribueren op de shardsleutel uit deel 24
SELECT create_distributed_table('deelnemer', 'deelnemer_id');

Vanaf create_distributed_table bestaat deelnemer niet meer als één fysieke tabel — Citus heeft hem opgesplitst in een (standaard: 32) shards, verdeeld over de geregistreerde workers, met hash-gebaseerde verdeling op deelnemer_id (deel 24, paragraaf 11).

-- Zichtbaar maken hoe de verdeling eruitziet
SELECT * FROM citus_shards WHERE table_name = 'deelnemer'::regclass;

Het aantal shards (citus.shard_count, standaard 32) is vooraf in te stellen en bepaalt de fijnmazigheid van toekomstige rebalancing — meer shards dan workers is gebruikelijk, zodat een worker meerdere shards draagt en toekomstige rebalancing kleinere eenheden kan verplaatsen.

6. Reference tables in de praktijk

Het concept uit deel 24, paragraaf 9, wordt hier één functieaanroep:

CREATE TABLE fonds (
    fonds_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    naam     text NOT NULL,
    sector   text NOT NULL
);

SELECT create_reference_table('fonds');

Wat er nu is: een volledige kopie van fonds op elke worker. Een join tegen fonds vanuit een gesharde tabel op elke worker blijft lokaal aan die worker — geen cross-shard-verkeer nodig, precies de belofte uit deel 24.

-- Deze join blijft lokaal aan elke worker, ongeacht welke shard van deelnemer wordt geraakt
SELECT d.achternaam, f.naam
FROM deelnemer d JOIN fonds f USING (fonds_id)
WHERE d.deelnemer_id = 42;

Wijzigingen op een reference table (een nieuw fonds toevoegen) worden door Citus automatisch naar elke worker gerepliceerd — de applicatiecode ziet één simpele INSERT, Citus regelt de vermenigvuldiging naar alle kopieën.

7. Co-locatie expliciet maken

Standaard krijgt elke distributed table zijn eigen, onafhankelijke sharding-schema. Voor co-locatie (deel 24, paragraaf 6) moet je expliciet aangeven dat twee tabellen dezelfde verdeling moeten delen:

CREATE TABLE dienstverband (
    dienstverband_id bigint GENERATED ALWAYS AS IDENTITY,
    deelnemer_id      integer NOT NULL,
    werkgever_id      integer NOT NULL,
    PRIMARY KEY (dienstverband_id, deelnemer_id)
);

SELECT create_distributed_table('dienstverband', 'deelnemer_id',
    colocate_with => 'deelnemer');

Wat colocate_with garandeert: rijen in dienstverband met dezelfde deelnemer_id als een rij in deelnemer belanden gegarandeerd op dezelfde worker. Een join tussen de twee op deelnemer_id is daardoor altijd lokaal, ongeacht welke specifieke deelnemer het betreft.

-- Lokaal aan één worker, dankzij colocate_with
SELECT d.achternaam, dv.werkgever_id
FROM deelnemer d JOIN dienstverband dv USING (deelnemer_id)
WHERE d.deelnemer_id = 42;

Controleren of twee tabellen co-located zijn:

SELECT logicalrelid, colocationid FROM pg_dist_partition
WHERE logicalrelid IN ('deelnemer'::regclass, 'dienstverband'::regclass);
-- gelijke colocationid = co-located

Dit is de implementatie van de analyse die je in deel 24, opdracht 24.3, op papier deed — nu met een concrete parameter die het afdwingt.

8. Query’s op een distributed table: wat blijft hetzelfde

Bijna alles. Dit is het punt dat Citus zo aantrekkelijk maakt ten opzichte van applicatieniveau-sharding: de applicatie schrijft gewone SQL, zonder te weten dat de data over meerdere servers verspreid is.

-- Ziet er precies zo uit als in niveau 1/2
SELECT * FROM deelnemer WHERE deelnemer_id = 42;
INSERT INTO mutatie (deelnemer_id, soort, ...) VALUES (42, 'adreswijziging', ...);
UPDATE deelnemer SET achternaam = 'Jansen' WHERE deelnemer_id = 42;

Voor elk van deze query’s herkent Citus, op basis van de WHERE-voorwaarde op de shardsleutel, direct welke ene shard (en dus welke ene worker) de query moet raken. De coördinator stuurt de query door naar die ene worker en geeft het resultaat terug — vergelijkbaar met, maar over servergrenzen heen, partition pruning uit deel 16.

De voorwaarde: de shardsleutel moet in de WHERE-clausule staan, op dezelfde manier als een partitiesleutel moet voorkomen voor pruning (deel 16, paragraaf 8) — een functie om de shardsleutel, of het ontbreken van de voorwaarde, dwingt Citus om alle workers te bevragen.

9. Query’s die de coördinator moet samenvoegen

-- Geen enkele voorwaarde op de shardsleutel: alle workers moeten mee
SELECT count(*) FROM deelnemer WHERE fonds_id = 2;

Deze query kan niet naar één worker worden gestuurd — fonds_id is niet de shardsleutel (deelnemer_id is dat), dus Citus weet niet vooraf welke shard de relevante rijen bevat. De coördinator stuurt de query naar alle workers, elk telt zijn eigen deel, en de coördinator sommeert de deelresultaten.

-- Een aggregatie over de hele dataset: hetzelfde patroon, complexer samenvoegen
SELECT soort, count(*) FROM mutatie GROUP BY soort;

Voor een GROUP BY stuurt Citus de aggregatie naar elke worker (die zijn eigen gedeeltelijke GROUP BY soort, count(*) uitvoert), en voegt de coördinator de deelresultaten samen tot het eindtotaal — een tweetraps-aggregatie die griffig is voor count/sum, en complexer (soms onmogelijk in één stap) voor bijvoorbeeld een exacte median of count(DISTINCT ...) over de hele dataset.

Dit is exact de “distributed query” uit deel 24, paragraaf 6, nu zichtbaar in de praktijk. Karins kwartaalrapportage, die nu over alle fondsen gaat in plaats van één, is precies dit soort query — werkend, maar duurder dan een lokale.

10. EXPLAIN op een distributed query

EXPLAIN SELECT * FROM deelnemer WHERE deelnemer_id = 42;

Custom Scan (Citus Adaptive)
  Task Count: 1
  Tasks Shown: All
  ->  Task
        Node: host=worker2 port=5432
        ->  Index Scan using deelnemer_pkey on deelnemer_102008
              Index Cond: (deelnemer_id = 42)

Task Count: 1 bevestigt wat paragraaf 8 beloofde: deze query raakt precies één shard, op precies één worker. Dit is het distributed-equivalent van “één partitie in het plan” uit deel 16.

EXPLAIN SELECT count(*) FROM deelnemer WHERE fonds_id = 2;

Aggregate
  ->  Custom Scan (Citus Adaptive)
        Task Count: 32
        ->  Task
              Node: host=worker1 port=5432
              ->  Seq Scan on deelnemer_102001
                    Filter: (fonds_id = 2)
        (... 31 more tasks ...)

Task Count: 32 — alle shards moeten worden doorzocht, en de coördinator telt de resultaten bij elkaar op. Precies de “geen pruning”-situatie uit deel 16, nu met de aanvullende kostenpost van netwerkverkeer tussen coördinator en elke worker.

De discipline blijft dezelfde als in deel 8, 13, 16: controleer met EXPLAIN of je query het gunstige (Task Count: 1) of het dure (Task Count: <shard_count>) pad neemt, vóórdat je aanneemt dat een query snel is.

11. Rebalancing met Citus

-- Een nieuwe worker toevoegen
SELECT citus_add_node('worker4-host', 5432);

-- Shards herverdelen zodat de nieuwe worker ook data draagt
SELECT rebalance_table_shards('deelnemer');

rebalance_table_shards implementeert het expand-migrate-contract-patroon uit deel 24, paragraaf 10, grotendeels automatisch: shards worden gekopieerd naar de nieuwe worker, verkeer wordt omgeleid, en de oude locatie wordt opgeschoond — met minimale onderbreking van lopend verkeer.

Wat automatisering wél en niet wegneemt:

  • Wel: het handmatige kopieerwerk, de coördinatie tussen expand/migrate/contract, en een groot deel van het risico op menselijke fouten tijdens de uitvoering.
  • Niet: de noodzaak om te verifiëren dat de rebalancing correct is afgerond (dezelfde discipline als deel 6, 16, 22 — automatisering vermindert het risico, het elimineert het niet). En niet de planning: wanneer je rebalancet (buiten de piek, deel 15’s lessen over timing), en of de resulterende verdeling daadwerkelijk gelijkmatiger is.
-- Verifiëren na afloop
SELECT * FROM citus_shards WHERE table_name = 'deelnemer'::regclass;
-- controleer de verdeling van shards over workers

12. Wat Citus niet automatisch oplost

Cross-shard-transacties (deel 24, paragraaf 7) vereisen nog steeds bewust ontwerp. Citus ondersteunt 2PC voor transacties die meerdere shards raken, maar de prestatiekosten en het ontwerpadvies (co-locatie eerst) blijven onveranderd geldig — Citus maakt 2PC mogelijk, niet gratis.

Globale uniciteit (deel 24, paragraaf 8) buiten de shardsleutel blijft een aandachtspunt: een UNIQUE-constraint op een kolom die niet de shardsleutel is (of er onderdeel van is), kan Citus niet over shards heen afdwingen — vergelijkbaar met de partitiesleutel-eis uit deel 16.

HA per node (deel 19) is niet automatisch — elke worker (en de coördinator) is een gewone PostgreSQL-server die zijn eigen replicatie- en failover-opzet nodig heeft als hoge beschikbaarheid gewenst is. Citus lost horizontale capaciteit op, niet beschikbaarheid; die twee zijn orthogonale eisen.

Back-up (deel 17) moet per node worden ingericht, en een consistente back-up van het hele cluster (coördinator plus alle workers, op hetzelfde moment) is complexer dan een back-up van één server — Citus biedt hier gereedschap voor coördinatie, maar het blijft een zorgvuldiger operatie dan in niveau 2.

13. Citus en de niveau-2-technieken

Partitionering (deel 16) binnen een shard: een shard is een gewone PostgreSQL-tabel (fysiek); niets weerhoudt je ervan die zelf te partitioneren als hij groot genoeg wordt. Citus en partitionering zijn stapelbaar.

Indexen (deel 14): gewoon aan te maken op de gedistribueerde tabel; Citus zorgt dat de index op elke shard wordt aangemaakt — hetzelfde patroon als een index op een gepartitioneerde tabel in deel 16, nu over workers verspreid.

CREATE INDEX ON deelnemer (achternaam);
-- wordt op elke shard van deelnemer aangemaakt, op elke worker

Concurrency (deel 15): locking gedraagt zich normaal binnen een shard/worker; over workers heen bestaat geen gedeelde lockwachtrij — een lock op worker 1 heeft geen effect op worker 2. Dat is deels bevrijdend (minder kans op een lockwachtrij die het hele systeem raakt) en deels een nieuwe complexiteit (cross-shard-consistentie is niet met locks te garanderen, vandaar 2PC).

Monitoring (deel 20): pg_stat_statements en de andere weergaven bestaan per node — de coördinator heeft een eigen overzicht, elke worker zijn eigen. Citus voegt eigen weergaven toe (citus_stat_statements, citus_shards) die het geheel samenbrengen.

14. Migreren van een gepartitioneerde tabel naar Citus

De volledige toepassing van het architectuur-migratiepad uit deel 23 en het sharding-migratiepad uit deel 24, nu met Citus als concreet gereedschap.

-- Stap 1: Citus beschikbaar maken (expand, op infrastructuurniveau)
CREATE EXTENSION citus;
SELECT citus_add_node(...);

-- Stap 2: de bestaande, gepartitioneerde mutatie-tabel (deel 16)
-- kan niet direct gedistribueerd worden terwijl hij gepartitioneerd is
-- op een andere sleutel dan de shardsleutel — hier moet een keuze:

-- Optie A: de bestaande partitiesleutel (aangemeld_op) hergebruiken
--          als shardsleutel is meestal ongewenst (deel 24: hotspot-risico)
-- Optie B: een nieuwe tabel opzetten met de juiste shardsleutel
--          (deelnemer_id) en migreren zoals in deel 22

CREATE TABLE mutatie_nieuw (LIKE mutatie INCLUDING ALL);
SELECT create_distributed_table('mutatie_nieuw', 'deelnemer_id',
    colocate_with => 'deelnemer');

-- Stap 3: data overzetten — logische replicatie (deel 18) of een
-- backfill-patroon (deel 22, paragraaf 9), afhankelijk van de omvang

-- Stap 4: omschakelmoment, verificatie, en pas dan de oude tabel opruimen

De les die hier samenkomt: dit is geen nieuwe migratietechniek. Het is expand-contract (deel 22) plus de shardsleutel-analyse (deel 24) plus de Citus-syntax (vandaag) — drie eerder geleerde stukken kennis, samengevoegd tot één concrete operatie.

15. Wanneer Citus, wanneer niet

Dezelfde toetsvraag als deel 24, paragraaf 13, nu toegepast op de keuze van gereedschap.

Citus past goed bij: een datamodel dat natuurlijk co-located kan worden rond één dominante sleutel (zoals deelnemer_id bij de Pensioenfederatie), een aangetoonde capaciteitsgrens die verticaal schalen niet meer oplost, en een team dat de operationele last van meerdere PostgreSQL-nodes aankan (deel 17-20, vermenigvuldigd).

Citus past minder goed bij: een datamodel met veel sterk verweven relaties zonder een natuurlijke co-locatie-sleutel, een werklast die overwegend uit cross-shard-aggregaties bestaat (waar de winst van sharding grotendeels wordt opgegeten door coördinatiekosten), of een organisatie die nog niet buiten de mogelijkheden van verticaal schalen en niveau-2-technieken is gegroeid.

Voor de Pensioenfederatie, concreet vandaag: met drie fondsen en een volume ruim onder de aangenomen capaciteitsgrens (deel 24, opdracht 24.1) is Citus nu niet nodig — het architectuuradvies uit deel 23 (patroon 2, met patroon 3 voor Baken) volstaat. Wat vandaag is opgebouwd, is de kennis en de concrete implementatiekennis om wanneer het wel nodig wordt, niet vanaf nul te hoeven beginnen.

16. Veelgemaakte fouten

Fout Gevolg Beter
Een tabel distribueren zonder eerst de shardsleutel-analyse van deel 24 Slechte verdeling, veel cross-shard-verkeer Eerst de analyse, dan pas create_distributed_table
colocate_with vergeten bij gerelateerde tabellen Onnodige cross-shard-joins Expliciet co-locaten waar het toegangspatroon dat vraagt

Query’s schrijven zonder de shardsleutel in de WHERE-clausule, en verbaasd zijn over trage prestaties Elke query raakt alle shards (Task Count: <shard_count>) EXPLAIN controleren, shardsleutel expliciet meegeven
Rebalancing draaien zonder verificatie achteraf Onopgemerkte inconsistentie Dezelfde verificatiediscipline als elke migratie
Citus invoeren zonder de HA- en back-upgevolgen per node te doordenken Complexiteit vermenigvuldigd met het aantal nodes, zonder dat back-up/HA is meegegroeid Elk niveau-2-onderwerp opnieuw doorlopen, nu per node

17. Kernbegrippen

Coördinator — de Citus-node die metadata bewaart en query’s routeert. Worker — een Citus-node die daadwerkelijke shard-data bevat. create_distributed_table — de opdracht die een gewone tabel omzet naar een gesharde tabel. create_reference_table — de opdracht die een tabel op elke worker volledig repliceert. colocate_with — de parameter die co-locatie tussen tabellen afdwingt. Task Count — in een EXPLAIN-plan: het aantal shards dat een query moet raken. rebalance_table_shards — Citus’ geautomatiseerde rebalancing-gereedschap. citus_shards — systeemweergave die toont welke shard op welke worker staat.
