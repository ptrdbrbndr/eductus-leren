1. Leerdoelen

Na dit deel kun je:

  • een command handler bouwen die business regels toepast vóórdat een event wordt vastgelegd;
  • optimistische concurrency correct afhandelen bij een conflicterend volgnummer;
  • snapshotting toepassen om lange streams beheersbaar te houden;
  • projecties automatisch laten bijwerken, inclusief de afweging tussen polling en LISTEN/NOTIFY;
  • een oplossing ontwerpen voor het recht op vergetelheid binnen een onveranderlijke event store;
  • event-schema-evolutie beheren zonder de geschiedenis te breken;
  • een event-sourced systeem testen en monitoren;
  • de volledige mutatieverwerking van Meridiaan als event-sourced systeem beschrijven.

2. Van concept naar productie

Deel 27 gaf je de concepten en de geruststelling dat je de bouwstenen al kende. Dit deel voegt precies de stukken toe die nodig zijn om van een demonstratie naar een werkend systeem te gaan:

  • Business logica die bepaalt of een event überhaupt geldig is (paragraaf 3-4).
  • Snapshotting, zodat een stream van tienduizenden events niet bij elke berekening helemaal opnieuw hoeft te worden doorlopen (paragraaf 5-6).
  • Geautomatiseerde projectie-updates, in plaats van een handmatige REFRESH (paragraaf 7-8).
  • Een antwoord op het recht op vergetelheid — het AVG-vraagstuk dat in deel 27 als openstaand probleem werd achtergelaten (paragraaf 9-10).
  • Schema-evolutie, testen en monitoring — de operationele volwassenheid die elk patroon in deze cursus uiteindelijk nodig heeft.

3. Command handlers: business logica toepassen op een stream

Een event mag niet zomaar worden toegevoegd — er moet eerst gecontroleerd worden of het geldig is, gegeven de huidige stand van het aggregaat. Dat is de taak van een command handler.

CREATE OR REPLACE FUNCTION verwerk_salariswijziging(
    p_aggregate_id uuid, p_nieuw_salaris numeric, p_verwacht_volgnummer integer
) RETURNS void AS $$
DECLARE
    v_huidig_salaris numeric;
BEGIN
    -- 1. Bereken de huidige stand (of lees uit een snapshot, deel 5-6)
    SELECT (payload->>'nieuw_salaris')::numeric INTO v_huidig_salaris
    FROM events WHERE aggregate_id = p_aggregate_id AND event_type = 'SalarisGewijzigd'
    ORDER BY volgnummer DESC LIMIT 1;

    -- 2. Bedrijfsregel: een salariswijziging van meer dan 50% vereist goedkeuring
    IF v_huidig_salaris IS NOT NULL
       AND abs(p_nieuw_salaris - v_huidig_salaris) / v_huidig_salaris > 0.5 THEN
        RAISE EXCEPTION 'Salariswijziging van meer dan 50%% vereist goedkeuring';
    END IF;

    -- 3. Vastleggen, met het verwachte volgnummer (optimistic concurrency, §4)
    INSERT INTO events (aggregate_id, event_type, payload, volgnummer)
    VALUES (p_aggregate_id, 'SalarisGewijzigd',
            jsonb_build_object('nieuw_salaris', p_nieuw_salaris),
            p_verwacht_volgnummer);
END;
$$ LANGUAGE plpgsql;

Dit is het punt waar het onderscheid tussen “commando” en “event” (deel 27, paragraaf 4) operationeel wordt. verwerk_salariswijziging is het commando — een verzoek dat kan falen. Het SalarisGewijzigd-event dat er (mogelijk) uit voortkomt, is een feit dat, eenmaal vastgelegd, niet meer ter discussie staat.

Waar plaats je de business logica — hier, in de database, of in de applicatielaag? Beide zijn gangbaar. In de database (zoals hierboven) profiteer je van transactionele garanties zonder een extra rondgang; in de applicatielaag heb je meer flexibiliteit in taal en testbaarheid. Dit is dezelfde afweging als bij SECURITY DEFINER-functies (deel 21): logica dicht bij de data geeft garanties, logica in de applicatie geeft flexibiliteit.

4. Optimistic concurrency in de praktijk

Uit deel 27: de UNIQUE (aggregate_id, volgnummer)-constraint voorkomt dubbele volgnummers. In de praktijk moet de aanroepende code dat conflict afhandelen.

-- Als twee sessies tegelijk hetzelfde aggregaat wijzigen:
-- Sessie A leest volgnummer 4, probeert 5 te schrijven — lukt.
-- Sessie B leest ook volgnummer 4 (vóór A's schrijfactie), probeert ook 5 — faalt.

Het patroon dat hierbij hoort, is bijna identiek aan de retry-logica uit deel 15, paragraaf 16 (serialisatiefouten bij SERIALIZABLE):

poging = 0
zolang poging < 5:
    volgnummer = lees_huidig_volgnummer(aggregate_id)
    probeer:
        voer command handler uit met verwacht_volgnummer = volgnummer + 1
        klaar
    bij unique_violation (SQLSTATE 23505):
        poging = poging + 1
        wacht kort (met spreiding, zoals deel 15)
geef op met een duidelijke melding

Waarom dit geen nieuw probleem is: het is exact hetzelfde patroon als bij een serialisatiefout — een botsing die correct wordt afgevangen in plaats van stilzwijgend fout te gaan, met retry als de aangewezen afhandeling. De cursus heeft je dit patroon al één keer grondig geleerd; vandaag pas je het toe op een nieuwe context.

5. Snapshotting: waarom lange streams een probleem worden

Een dienstverband van dertig jaar, met honderden salariswijzigingen, promoties en aanpassingen, genereert een stream met honderden events. Elke keer de huidige stand berekenen door alle events opnieuw af te spelen, wordt op een gegeven moment traag — een herkenbaar probleem: het is de “meet op schaal, niet op een speelgoedvoorbeeld”-les uit deel 12, nu toegepast op streams.

Snapshotting: periodiek de berekende stand zelf opslaan, zodat je bij de volgende berekening niet bij event 1 hoeft te beginnen, maar bij de laatste snapshot plus de events die daarna zijn toegevoegd.

CREATE TABLE snapshots (
    aggregate_id uuid NOT NULL,
    volgnummer   integer NOT NULL,
    state        jsonb NOT NULL,
    created_at   timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (aggregate_id, volgnummer)
);

Dit is hetzelfde idee als een materialized view (deel 8) of een BRIN-index (deel 14): een vooraf berekend, goedkoper te raadplegen tussenresultaat, met de bekende afruil tussen actualiteit en snelheid.

6. Een snapshot bouwen en gebruiken

-- Een snapshot maken op het huidige volgnummer
INSERT INTO snapshots (aggregate_id, volgnummer, state)
SELECT aggregate_id, max(volgnummer),
       jsonb_build_object(
           'huidig_salaris', (
               SELECT payload->>'nieuw_salaris' FROM events e2
               WHERE e2.aggregate_id = e.aggregate_id AND event_type = 'SalarisGewijzigd'
               ORDER BY volgnummer DESC LIMIT 1)
       )
FROM events e WHERE aggregate_id = '...'
GROUP BY aggregate_id;

-- De stand berekenen: snapshot plus de events erna
SELECT s.state, array_agg(e.payload ORDER BY e.volgnummer) AS events_erna
FROM snapshots s
LEFT JOIN events e ON e.aggregate_id = s.aggregate_id AND e.volgnummer > s.volgnummer
WHERE s.aggregate_id = '...'
GROUP BY s.state
ORDER BY s.volgnummer DESC LIMIT 1;

Wanneer een snapshot maken? Een gangbare vuistregel: elke N events (bijvoorbeeld elke 100), of periodiek (bijvoorbeeld nachtelijk voor actieve aggregaten) — vergelijkbaar met de checkpoint-cyclus uit deel 11: te vaak is overhead, te zelden betekent lange hersteltijden (hier: lange herberekeningstijden).

Snapshots zijn, net als projecties, volledig herbouwbaar — verlies of corrumpeer een snapshot, en je kunt hem opnieuw berekenen uit de events. De events blijven de enige, onvervangbare bron van waarheid; alles daarna afgeleid (projecties, snapshots) is comfort, geen noodzaak.

7. Projecties automatisch bijwerken

In deel 27 werkte je een materialized view handmatig bij met REFRESH. In productie wil je dat automatiseren.

Optie 1 — periodiek, met een geplande taak:

-- Via pg_cron (deel 16, paragraaf 15) of een externe scheduler
SELECT cron.schedule('ververs-projecties', '*/5 * * * *',
    $$REFRESH MATERIALIZED VIEW CONCURRENTLY dienstverband_huidige_stand$$);

CONCURRENTLY (deel 8, deel 14) voorkomt dat de materialized view tijdens de verversing ontoegankelijk is voor lezers — dezelfde reden dat je CREATE INDEX CONCURRENTLY verkiest boven de gewone variant.

Optie 2 — trigger-gebaseerd, direct na elk event:

CREATE OR REPLACE FUNCTION update_projectie_na_event() RETURNS trigger AS $$
BEGIN
    -- Werk de projectie voor dit ene aggregaat bij (geen volledige REFRESH)
    -- ... UPSERT-logica op een gewone (niet-materialized) projectietabel ...
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_update_projectie
    AFTER INSERT ON events
    FOR EACH ROW EXECUTE FUNCTION update_projectie_na_event();

De afweging tussen de twee is opnieuw de klok-versus-actualiteit-afweging uit deel 8 en 18: periodiek is eenvoudiger en lichter, maar met een vertragingsvenster; trigger-gebaseerd is (bijna) synchroon, maar voegt overhead toe aan elke schrijfactie op de event store — vergelijkbaar met hoe een index (deel 14) elke INSERT iets duurder maakt in ruil voor snellere leesacties.

8. LISTEN/NOTIFY als lichte trigger voor projecties

Een tussenweg tussen “periodiek” en “synchroon binnen dezelfde transactie”: PostgreSQL’s ingebouwde publish-subscribe-mechanisme.

-- Bij het vastleggen van een event, ook een notificatie versturen
CREATE OR REPLACE FUNCTION notify_nieuw_event() RETURNS trigger AS $$
BEGIN
    PERFORM pg_notify('nieuw_event', NEW.aggregate_id::text);
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_notify_event AFTER INSERT ON events
    FOR EACH ROW EXECUTE FUNCTION notify_nieuw_event();

Een aparte projectie-bijwerkende dienst luistert (LISTEN nieuw_event;) en werkt, zodra een notificatie binnenkomt, buiten de oorspronkelijke transactie de relevante projectie bij — asynchroon, maar met minder vertraging dan een periodieke taak.

Herinner je deel 15 en 19: LISTEN/NOTIFY werkt niet betrouwbaar in transaction-pooling-modus (PgBouncer). Een dienst die op notificaties luistert, heeft een permanente, niet-gepoolde verbinding nodig — een detail dat gemakkelijk over het hoofd wordt gezien als je gewend bent dat alles door een pooler loopt (deel 19). Dit is precies het soort valkuil die je in deel 19 al leerde herkennen, nu in een nieuwe context.

9. Het vraagstuk: recht op vergetelheid in een onveranderlijke geschiedenis

Terug naar Sanne, en naar de belofte aan het eind van deel 27. Een deelnemer oefent zijn recht op vergetelheid uit (AVG) en wil dat zijn persoonsgegevens worden verwijderd. Bij een event store is dat principieel lastiger dan bij een gewone tabel.

-- Bij een gewone tabel: triviaal
DELETE FROM deelnemer WHERE deelnemer_id = 42;

-- Bij een event store: de events bevatten het BSN, de naam, het adres —
-- verspreid over tientallen events in de stream. Verwijderen zou de
-- onveranderlijkheid schenden die het hele patroon draagt.

Het spanningsveld, precies benoemd: event sourcing belooft een volledige, onveranderlijke geschiedenis — dat is de kern van zijn waarde (deel 27, paragraaf 8). De AVG vereist dat persoonsgegevens op verzoek daadwerkelijk verwijderd kunnen worden. Deze twee eisen lijken elkaar tegen te spreken.

10. Crypto-shredding als oplossing

De gangbare oplossing verzoent beide eisen door de vraag te herformuleren: je hoeft het event zelf niet te verwijderen — je moet het onleesbaar maken.

-- Persoonsgegevens in de payload worden versleuteld met een sleutel
-- die UNIEK is per deelnemer (niet per event, niet clusterbreed)
CREATE TABLE deelnemer_sleutels (
    deelnemer_id integer PRIMARY KEY,
    sleutel      bytea NOT NULL   -- of een verwijzing naar extern sleutelbeheer, deel 21
);

-- Bij het vastleggen van een event: persoonsgegevens versleuteld opslaan
INSERT INTO events (aggregate_id, event_type, payload, volgnummer)
VALUES (42, 'AdresGewijzigd',
        jsonb_build_object(
            'straat_enc', pgp_sym_encrypt('Kerkstraat 12', (SELECT sleutel::text FROM deelnemer_sleutels WHERE deelnemer_id = 42))
        ), 5);

Het recht op vergetelheid wordt dan:

-- Niet: events verwijderen (schendt onveranderlijkheid)
-- Wel: de sleutel vernietigen
DELETE FROM deelnemer_sleutels WHERE deelnemer_id = 42;

Na het vernietigen van de sleutel zijn de versleutelde velden in alle historische events onherstelbaar onleesbaar — de gebeurtenis “er vond een adreswijziging plaats op deze datum” blijft bestaan (de structuur van de geschiedenis, nodig voor audit en analyse), maar de persoonsgegevens zelf (welk adres) zijn voorgoed ontoegankelijk. Dit heet crypto-shredding, en het is precies de toepassing van pgcrypto uit deel 21 op het specifieke probleem van dit deel.

Wat dit wel en niet oplost:

Crypto-shredding
Persoonsgegevens onleesbaar maken Ja, effectief onomkeerbaar
De structuur van de geschiedenis (dat er een wijziging was) bewaren Ja
Volledig fysiek verwijderen van elk spoor Nee — de versleutelde bytes blijven fysiek aanwezig
Werkt met back-ups (deel 17) Ja, mits de sleutel niet ook in de back-up van de sleuteltabel overleeft

De laatste rij is een reëel aandachtspunt: als deelnemer_sleutels zelf in oudere back-ups staat, overleeft de sleutel daar mogelijk nog. Het bewaarbeleid voor back-ups (deel 17, paragraaf 15) moet daarom consistent zijn met deze aanpak — een back-up van de sleuteltabel die langer bewaard blijft dan de intentie van het verwijderingsverzoek, ondermijnt crypto-shredding net zoals een te lange back-upbewaartermijn in deel 17 al een spanningsveld opleverde met gewone verwijderingsverzoeken.

Ontwerpimplicatie: bepaal vooraf welke velden in een event-payload persoonsgegevens bevatten, en versleutel die specifiek — niet de hele payload (dat zou ook niet-persoonlijke, voor analyse waardevolle gegevens onnodig onleesbaar maken) en niet slechts een deel als het niet dekkend is (dan blijft er een lek).

11. Event-schema-evolutie: wanneer een event-type moet veranderen

Een SalarisGewijzigd-event kreeg ooit alleen nieuw_salaris. Een jaar later wil je ook reden vastleggen. De oude events in de store hebben dat veld niet en kunnen niet met terugwerkende kracht worden aangepast (onveranderlijkheid, deel 27).

Oplossing: expliciete versionering.

-- Nieuwe events krijgen een versie-aanduiding
{"_version": 2, "nieuw_salaris": 45000, "reden": "jaarlijkse verhoging"}

-- Oude events blijven zoals ze waren
{"_version": 1, "nieuw_salaris": 42000}

Projecties en command handlers moeten met beide versies kunnen omgaan — een upcasting-functie die een oud-formaat-event vertaalt naar het nieuwe formaat vóórdat de projectielogica erop wordt losgelaten:

CREATE FUNCTION upcast_salariswijziging(payload jsonb) RETURNS jsonb AS $$
    SELECT CASE WHEN payload ? '_version' AND (payload->>'_version')::int >= 2
           THEN payload
           ELSE payload || jsonb_build_object('_version', 2, 'reden', 'onbekend (historisch)')
           END;
$$ LANGUAGE sql IMMUTABLE;

Dit is vergelijkbaar met de kolomtype-migratie uit deel 22, maar dan voor de betekenis van een event in plaats van een kolom — en met een belangrijk verschil: bij een kolomtype-migratie kun je uiteindelijk de oude kolom verwijderen (contract); bij event-schema-evolutie blijven oude events voor altijd in hun oorspronkelijke vorm bestaan, en moet de toepassingslogica daarmee blijven leven, in principe voor de levensduur van het systeem.

12. Testen van een event-sourced systeem

Het goede nieuws: event-sourced systemen zijn vaak makkelijker te testen dan state-based systemen, omdat elke test simpelweg is: gegeven deze reeks events, en dit commando, verwacht ik dit nieuwe event (of deze foutmelding).

Test: "Een salariswijziging van meer dan 50% zonder goedkeuring wordt geweigerd"
Gegeven: stream met [DienstverbandGestart, SalarisGewijzigd(40000)]
Wanneer: verwerk_salariswijziging(nieuw_salaris=70000)
Dan: verwacht een foutmelding, geen nieuw event

Dit is geen databasetest in de traditionele zin — het is een test van de command handler-logica, en omdat de events onveranderlijk en expliciet zijn, is de testopzet (gegeven-wanneer-dan) natuurlijk en herleidbaar.

13. Monitoring: wat je nu extra in de gaten houdt

Bovenop alles uit deel 20, komen er specifieke signalen bij:

Signaal Waarom het ertoe doet
Groei van de event store Analoog aan elke tabelgroei (deel 12), maar hier is DELETE principieel geen optie — alleen partitioneren en archiveren (deel 16)
Projectie-lag (tijd sinds laatste REFRESH/update) Het eventual-consistency-venster uit deel 27, nu een meetbaar getal
Aantal unique_violation-conflicten per aggregaat Hoog aantal duidt op een hotspot-aggregaat (deel 15) dat vaak gelijktijdig wordt gewijzigd
Snapshot-leeftijd versus streamlengte Te oude snapshots betekenen trage herberekeningen
LISTEN/NOTIFY-achterstand (indien gebruikt) Een luisterende dienst die zelf traag is, wordt een verborgen bottleneck

14. Meridiaans mutatieverwerking, end-to-end

Een samenvattend beeld van hoe deel 27 en 28 samen op de bestaande casus worden toegepast:

  1. Commando: het portaal (of de klantenservice) dient een mutatieverzoek in.
  2. Command handler: controleert bedrijfsregels (bijvoorbeeld: is de deelnemer nog actief), en legt bij succes een MutatieIngediend-event vast, met optimistische concurrency op het dienstverband-aggregaat.
  3. Verwerking: een achtergrondproces (vergelijkbaar met de SKIP LOCKED-wachtrij uit deel 15, nu toegepast op events in plaats van rijen) verwerkt het event en legt een MutatieVerwerkt-event vast.
  4. Projectie: de “huidige stand van de deelnemer”-projectie wordt bijgewerkt, via LISTEN/NOTIFY (paragraaf 8) of een periodieke taak.
  5. Persoonsgegevens: relevante velden in de payload zijn versleuteld per deelnemer (paragraaf 10), zodat een toekomstig verwijderingsverzoek mogelijk blijft.
  6. Partitionering: de event store zelf is, net als mutatie in deel 16, gepartitioneerd op tijd — oude, buiten de bewaartermijn vallende partities kunnen verdwijnen zodra de bijbehorende sleutels (indien van toepassing) al zijn vernietigd.

Dit is geen ander systeem dan wat je in niveau 2 bouwde — het is dezelfde mutatie-verwerking, met de events als expliciet, eersteklas concept in plaats van een impliciete bijeffect van hoe de tabel toevallig was ingericht.

15. Veelgemaakte fouten

Fout Gevolg Beter
Business logica pas ná het vastleggen van een event controleren Ongeldige feiten in de geschiedenis Command handler valideert vóór het event bestaat
Geen snapshotting bij lange streams Trage, groeiende herberekeningstijden Periodieke snapshots, herbouwbaar
LISTEN/NOTIFY via een gepoolde verbinding Werkt onbetrouwbaar of helemaal niet Permanente, niet-gepoolde verbinding voor de luisteraar
Events verwijderen bij een verwijderingsverzoek Schendt onveranderlijkheid, breekt projecties die op volledigheid rekenen Crypto-shredding
De hele payload versleutelen, ook niet-persoonlijke velden Onnodig verlies van voor analyse waardevolle, niet-gevoelige gegevens Selectief versleutelen, per veld
Sleutels voor crypto-shredding zelf te lang bewaren in back-ups Het verwijderingsverzoek wordt via een oude back-up ondermijnd Sleutelbewaarbeleid consistent met deel 17
Event-schema’s wijzigen zonder versionering Oude events kunnen niet meer correct worden geïnterpreteerd Expliciete _version, upcasting-functies
Testen alsof het een gewone CRUD-applicatie is Mist de kracht van gegeven-wanneer-dan-tests op commando’s Testen op het niveau van commando’s en verwachte events

16. Kernbegrippen

Command handler — logica die een commando valideert en, bij succes, een event vastlegt. Optimistic concurrency (in event sourcing) — het volgnummer-conflictmechanisme uit deel 27, hier met de bijbehorende retry-logica. Snapshot — een periodiek opgeslagen, herbouwbare tussenstand van een aggregaat. LISTEN/NOTIFY — PostgreSQL’s ingebouwde publish-subscribe-mechanisme, hier gebruikt om projecties bijna-synchroon bij te werken. Recht op vergetelheid — de AVG-eis dat persoonsgegevens op verzoek verwijderbaar moeten zijn. Crypto-shredding — persoonsgegevens onleesbaar maken door de bijbehorende versleutelingssleutel te vernietigen, in plaats van de gegevens zelf te verwijderen. Event-schema-evolutie — het beheren van veranderingen in het formaat van een event-type over tijd. Upcasting — het vertalen van een ouder event-formaat naar het nieuwste formaat vóór verwerking.

Volgende deel: geo-distributie. Vandaag ging het over wát je vastlegt. Volgende keer keert de vraag terug naar waar — maar nu op de schaal van meerdere regio’s en landsgrenzen, met alles wat dat aan latency, dataresidentie en AVG-complicaties met zich meebrengt.
