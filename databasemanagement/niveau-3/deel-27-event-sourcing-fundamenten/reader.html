1. Leerdoelen

Na dit deel kun je:

  • het onderscheid tussen state-based en event-based opslag uitleggen;
  • de kernbegrippen event, event store, aggregate, stream en projectie definiëren en op elkaar betrekken;
  • benoemen wat event sourcing “gratis” oplevert ten opzichte van traditionele opslag, en wat het kost;
  • CQRS als companion-patroon plaatsen naast event sourcing;
  • terugvinden waar deze cursus, zonder het te benoemen, al naar event-sourcing-achtige patronen wees;
  • beoordelen of event sourcing voor een gegeven domein de juiste keuze is.

2. Een aanname die nooit hardop werd gezegd

Zesentwintig delen lang, van deel 1 tot deel 26, is er één aanname geweest die nooit is uitgesproken omdat hij zo vanzelfsprekend leek: een database bewaart de huidige stand van zaken.

UPDATE deelnemer SET achternaam = 'Jansen-Vermeer' WHERE deelnemer_id = 42;

Na deze opdracht is de oude achternaam weg. Niet meteen fysiek (deel 7, 12: MVCC bewaart de oude rijversie totdat vacuum hem opruimt), maar logisch: er is geen manier meer om via een gewone SELECT te achterhalen wat de achternaam vóór deze wijziging was, tenzij je expliciet een aparte historietabel had bijgehouden.

Dit deel stelt die aanname zelf ter discussie. Niet omdat hij fout is — voor het overgrote deel van wat je in deze cursus hebt gebouwd, is “de huidige stand bewaren en de rest overschrijven” precies de juiste keuze. Maar er is een alternatief, en voor bepaalde domeinen — waaronder delen van een pensioenadministratie — is dat alternatief soms de sterkere keuze.

3. State-based versus event-based

State-based (wat je tot nu toe deed): de database bewaart de huidige toestand. Een wijziging overschrijft de vorige waarde.

-- state-based: de rij IS de waarheid, op dit moment
UPDATE aanspraak SET opgebouwd_bedrag = 45000 WHERE aanspraak_id = 7;

Event-based (event sourcing): de database bewaart elke gebeurtenis die ooit heeft plaatsgevonden, in volgorde, onveranderlijk. De huidige toestand is niet iets dat wordt bewaard — het is iets dat wordt berekend door alle events voor een gegeven aggregaat op volgorde toe te passen.

-- event-based: de gebeurtenissen zijn de waarheid; het bedrag is een afgeleide
INSERT INTO events (aggregate_id, event_type, payload, occurred_at) VALUES
    (7, 'AanspraakOpgebouwd', '{"bedrag": 40000}', '2024-01-15'),
    (7, 'AanspraakOpgebouwd', '{"bedrag": 5000}',  '2024-06-01');
-- de huidige stand (45000) volgt uit het optellen van beide events

Het fundamentele verschil, in één zin: state-based bewaart wat waar is; event-based bewaart wat er is gebeurd, en leidt daaruit af wat waar is.

4. Wat een event is

Een event is een onveranderlijk feit over iets dat is gebeurd — geschreven in de verleden tijd, nooit in de tegenwoordige of gebiedende wijs.

Geen event (een commando/wens) Wel een event (een feit)
“Wijzig het adres” AdresGewijzigd
“Verwerk deze mutatie” MutatieVerwerkt
“Ken pensioen toe” PensioenToegekend

Een event heeft altijd:

  • een aggregaat-identiteit (op welk ding heeft dit betrekking — een deelnemer, een dienstverband);
  • een type (AdresGewijzigd, PremieOntvangen, …);
  • een payload (de gegevens die bij dit specifieke feit horen);
  • een tijdstip waarop het is vastgelegd;
  • een volgnummer binnen zijn aggregaat (paragraaf 6), zodat de volgorde van toepassing eenduidig is.

Een event wordt nooit gewijzigd of verwijderd. Een correctie is zelf weer een nieuw event (AdresGecorrigeerd), niet een aanpassing van het oorspronkelijke AdresGewijzigd-event. Dit is een streng, bewust ontwerpprincipe — en het is exact de reden dat een event store van nature append-only is, een eigenschap die je in deel 12 en 15 al hebt leren waarderen om heel andere redenen.

5. De event store: alleen toevoegen, nooit wijzigen

CREATE TABLE events (
    event_id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    aggregate_id  uuid NOT NULL,
    aggregate_type text NOT NULL,
    event_type    text NOT NULL,
    payload       jsonb NOT NULL,
    volgnummer    integer NOT NULL,
    occurred_at   timestamptz NOT NULL DEFAULT now(),
    UNIQUE (aggregate_id, volgnummer)
);

Herken je dit patroon? Uit deel 12, paragraaf 3: het onderzoek naar mutatie toonde al dat een tabel die alleen INSERT doet en nooit UPDATE, structureel minder bloat opbouwt. Uit deel 15, paragraaf 18: de oplossing voor het tellerrij-hotspot-probleem was “invoegen in plaats van bijwerken”. Uit deel 16, paragraaf 17: de aanbeveling om oude gebeurtenissen te partitioneren en met DROP TABLE te verwijderen in plaats van een DELETE.

Dit deel legt de naam op wat je in die eerdere delen al herkende als patroon: een append-only gebeurtenistabel is de kern van event sourcing. De cursus heeft je stap voor stap, zonder het te benoemen, klaargestoomd voor dit idee.

De UNIQUE (aggregate_id, volgnummer)-constraint is geen toeval — het is het mechanisme voor optimistische concurrency control (een idee dat je al kende uit deel 7, paragraaf over optimistisch vergrendelen): een schrijvende partij leest het huidige volgnummer, probeert het volgende event toe te voegen met volgnummer + 1, en als een andere partij intussen al een event met dat volgnummer heeft toegevoegd, faalt de constraint — een botsing wordt netjes afgevangen in plaats van stilzwijgend overschreven.

6. Aggregates en streams

Een aggregaat is de eenheid waarop events betrekking hebben en waarvoor consistentie gegarandeerd moet zijn — bij Meridiaan bijvoorbeeld één deelnemer, of één dienstverband.

Een stream is de volledige, geordende reeks events voor één aggregaat:

SELECT event_type, payload, occurred_at
FROM events
WHERE aggregate_id = '...' AND aggregate_type = 'dienstverband'
ORDER BY volgnummer;

1. DienstverbandGestart      {werkgever_id: 12, datum: '2020-03-01'}
2. SalarisGewijzigd          {nieuw_salaris: 42000}
3. DeeltijdPercentageGewijzigd {percentage: 80}
4. DienstverbandBeëindigd    {datum: '2024-06-30', reden: 'ontslag'}

Dit is de directe implementatie van het co-locatie-principe uit deel 24-25, nu toegepast op events in plaats van sharding: alle events van één aggregaat horen logisch (en, bij een gesharde opzet, idealiter ook fysiek) bij elkaar, want vrijwel elke bewerking — een nieuw event toevoegen, de huidige stand berekenen — werkt binnen precies één stream.

7. Projecties: van events naar een bruikbare stand

Niemand wil voor elke vraag “wat is het huidige salaris van deze deelnemer” door een hele stream van events lopen en ze handmatig optellen. Een projectie is een afgeleide, leesbare weergave, opgebouwd door de events toe te passen.

-- Een projectie: de huidige stand, herberekend uit de stream
CREATE MATERIALIZED VIEW dienstverband_huidige_stand AS
SELECT
    aggregate_id AS dienstverband_id,
    (SELECT payload->>'werkgever_id' FROM events e2
     WHERE e2.aggregate_id = e.aggregate_id AND event_type = 'DienstverbandGestart') AS werkgever_id,
    (SELECT payload->>'nieuw_salaris' FROM events e2
     WHERE e2.aggregate_id = e.aggregate_id AND event_type = 'SalarisGewijzigd'
     ORDER BY volgnummer DESC LIMIT 1) AS huidig_salaris
FROM events e
GROUP BY aggregate_id;

Dit is exact het materialized-view-patroon uit deel 8, en het federatieve equivalent uit deel 26 — nu toegepast op events. De projectie is een afgeleide, herbouwbare weergave; de events zijn de bron van waarheid. Verlies of corrumpeer de projectie, en je kunt hem volledig opnieuw opbouwen door de events opnieuw af te spelen (replay) — een eigenschap die een traditionele, state-based tabel niet heeft: als je daar de huidige waarde kwijtraakt zonder back-up, ben je hem écht kwijt.

Er kunnen meerdere projecties naast elkaar bestaan uit dezelfde events — een projectie voor het portaal (huidige stand), een andere voor een historisch overzicht (stand op elk gewenst moment), een derde voor een rapportage (aggregaties over alle deelnemers). Dit is een fundamenteel andere flexibiliteit dan een traditionele tabel, waar je vooraf moet beslissen welke vraag je makkelijk kunt beantwoorden.

8. Wat je “gratis” krijgt

Volledige, inherente audit trail. In deel 20 was pgaudit het antwoord op Sannes vraag uit deel 9: wie heeft wat ingezien of gewijzigd. Bij event sourcing is de vraag “wat is er ooit gewijzigd, en door wie” niet iets dat je met een aparte extensie moet toevoegen — het is inherent aan hoe de gegevens zijn opgeslagen. De events zijn het auditlog.

Tijdreizen. “Wat was het opgebouwde pensioen van deze deelnemer op 1 januari 2023?” is bij state-based opslag alleen te beantwoorden als je toevallig een back-up (deel 17) van precies dat moment hebt, of een aparte historietabel bijhield. Bij event sourcing: speel alle events tot die datum af, en je hebt het antwoord — een berekening, geen zoekactie in een archief.

-- Tijdreizen: de stand op een specifiek moment, berekend uit events tot dan
SELECT ... FROM events
WHERE aggregate_id = '...' AND occurred_at <= '2023-01-01'
ORDER BY volgnummer;

Nieuwe inzichten achteraf, zonder gegevensverlies. Een projectie die je vandaag nog niet had bedacht, kan morgen alsnog gebouwd worden — de ruwe events zijn er nog, ongeacht welke vragen je in het verleden wel of niet stelde. Bij state-based opslag is informatie die je destijds overschreef, onherroepelijk weg.

Natuurlijke correctheid bij correcties. Een foutieve mutatie wordt niet “rechtgezet” door de oorspronkelijke rij te overschrijven (waardoor het spoor van de fout zelf verdwijnt) maar door een corrigerend event toe te voegen — de fout én de correctie blijven allebei zichtbaar in de geschiedenis, wat voor een pensioenadministratie met wettelijke bewaar- en verantwoordingsplicht een reëel voordeel is.

9. Wat het kost: eventual consistency

De eerlijke tegenkant, zoals bij elk krachtig patroon in deze cursus.

Projecties lopen per definitie achter op de events. Tenzij je een projectie synchroon met elk event bijwerkt (mogelijk, maar dan verlies je een deel van de flexibiliteit en snelheid van het patroon), is er een venster waarin een net toegevoegd event nog niet in de projectie is verwerkt — eventual consistency: het systeem convergeert naar de juiste stand, maar niet noodzakelijk onmiddellijk.

Dit is dezelfde afweging als replicatievertraging uit deel 18, nu binnen één systeem in plaats van tussen primary en replica: hoe snel moet een lezer de laatste schrijfactie zien, en welke vertraging is acceptabel?

Complexiteit van het datamodel. Elke vraag die je wilt beantwoorden, vereist nadenken over welke projectie die vraag kan beantwoorden — in tegenstelling tot een traditionele tabel waar je in beginsel elke vraag met een SELECT en misschien een index kunt stellen. Dit is een reëel ontwerp- en onderhoudsoverhead.

Event-schema-evolutie. Wat gebeurt er als het formaat van een event-type moet veranderen (een nieuw verplicht veld, een hernoemde eigenschap)? Oude events in de store hebben het oude formaat en kunnen niet met terugwerkende kracht worden aangepast (events zijn onveranderlijk, paragraaf 4) — projecties en toepassingslogica moeten met meerdere versies van hetzelfde event-type kunnen omgaan. Dit is een vergelijkbaar vraagstuk als de kolomtype-migratie uit deel 22, maar dan voor de betekenis van een event in plaats van een kolom.

Geen gratis globale queries. “Alle deelnemers met een pensioen boven X” is bij state-based opslag een simpele WHERE-clausule op een projectie; zonder een goede projectie is dit bij pure events een dure operatie die door talloze streams moet lopen.

10. CQRS: het natuurlijke companion-patroon

Command Query Responsibility Segregation (CQRS) is het architectuurpatroon dat vaak samen met event sourcing wordt toegepast, al zijn de twee technisch onafhankelijk van elkaar.

Het idee: scheid het pad voor schrijven (commando’s — “wijzig het salaris”, die tot events leiden) volledig van het pad voor lezen (query’s — die een projectie raadplegen). De twee kanten kunnen zelfs volledig verschillende technologie of infrastructuur gebruiken.

Commando's                              Query's
    │                                       │
    ▼                                       ▼
Command handler                        Query handler
    │                                       │
    ▼                                       │
Event store (schrijven, append-only)        │
    │                                       │
    └──── events voeden projecties ─────────┘
                                             │
                                    Projecties (lezen)

Waarom dit natuurlijk samengaat met event sourcing: de schrijfkant (events toevoegen) en de leeskant (projecties raadplegen) hebben al fundamenteel verschillende eigenschappen — de een is append-only en transactioneel precies, de ander is afgeleid en mag eventual consistent zijn. CQRS maakt dat onderscheid expliciet in de architectuur in plaats van het te verbergen.

Dit hoeft niet extreem te zijn. CQRS kan zo eenvoudig zijn als “schrijf naar de event store, lees uit een materialized view” (paragraaf 7) — je hoeft er geen aparte technologie-stack voor te bouwen om het principe toe te passen.

11. Terugblik: waar deze cursus al naar event sourcing wees

Een overzicht, expliciet gemaakt, van signalen die door de hele cursus liepen zonder ooit “event sourcing” te heten:

Waar Wat er toen werd gezegd Hoe het hier terugkomt
Deel 7 Optimistisch vergrendelen met een versiekolom De UNIQUE (aggregate_id, volgnummer)-constraint
Deel 12 mutatie als insert-only tabel heeft minder bloat De event store is per ontwerp insert-only
Deel 15 Hotspot oplossen door invoegen i.p.v. bijwerken De kern van hoe events worden vastgelegd
Deel 16 Partitioneren en DROP TABLE in plaats van DELETE Oude event-partities kunnen net zo verdwijnen
Deel 8 Materialized views voor dure aggregaties Projecties zijn materialized views over events
Deel 20 pgaudit voor herleidbaarheid Event sourcing heeft herleidbaarheid ingebouwd
Deel 18 Replicatievertraging als afweging Eventual consistency van projecties

Dit is geen toeval. De ontwerpers van deze cursus (en van veel productiesystemen) komen bij event sourcing uit omdat de bouwstenen — append-only tabellen, optimistische concurrency, materialized views, partitionering — al bekend en vertrouwd zijn. Event sourcing is minder een compleet nieuw idee dan een naam voor een patroon dat je onderdelen ervan al kende.

12. Het raakvlak met het Locked Platform

Wie in de bredere Ductus-praktijk werkt, kan dit patroon herkennen uit het Locked Platform — een eigen, data-centrisch en event-driven platform dat FSM (finite state machines), CQRS en event sourcing combineert als alternatief voor traditionele BPMN/CMMN-procesengines.

Het raakvlak, kort en zonder in productdetails te treden: waar dit deel event sourcing behandelt als architectuurpatroon binnen een PostgreSQL-database, past het Locked Platform hetzelfde soort denken toe op procesbesturing zelf — een proces (of een dienstverband, of een aanvraag) heeft een expliciete toestand die verandert door events, in plaats van impliciet verscholen te zitten in de combinatie van kolomwaarden in een traditionele tabel.

Voor deze cursus is dit een zijlijn, geen kernstof — de connectie is de moeite waard om te noemen omdat het laat zien dat het patroon van vandaag niet geïsoleerd staat, maar aansluit bij bredere ontwikkelingen in procesgeoriënteerde architectuur.

13. Wanneer event sourcing wél, wanneer niet

Dezelfde discipline als bij elk krachtig patroon in deze cursus.

Event sourcing past goed bij: domeinen met een sterke audit- en verantwoordingsplicht (een pensioenadministratie is een schoolvoorbeeld — elke wijziging in een aanspraak moet herleidbaar zijn, soms decennia later); domeinen waar “wat was de stand op moment X” een legitieme, terugkerende vraag is; domeinen waar de business zelf al in termen van gebeurtenissen denkt (een aanvraag, een claim, een dienstverband dat een levenscyclus van duidelijke stappen doorloopt).

Event sourcing past minder goed bij: eenvoudige CRUD-domeinen zonder audit- of tijdreis-behoefte (een tabel met sectorcodes heeft hier niets aan); teams zonder ervaring met de bijkomende complexiteit (projectiebeheer, eventual consistency, schema-evolutie); systemen waar elke lezing absoluut, synchroon actueel moet zijn zonder enige tolerantie voor vertraging.

De vraag die je stelt: is de geschiedenis van hoe iets is ontstaan zelf waardevol, of volstaat de huidige stand? Bij Meridiaans deelnemersadres: de huidige stand volstaat meestal. Bij Meridiaans pensioenaanspraken, waar elke wijziging jarenlang verantwoord moet kunnen worden: de geschiedenis is het punt.

Voor de Pensioenfederatie, concreet: niet het hele systeem event-sourced maken — dat zou de eenvoudige delen (sectorcodes, contactgegevens) onnodig compliceren. Wel serieus overwegen voor de mutatie- en aanspraakverwerking specifiek, waar de cursus toch al insert-only werkte (deel 7, 12, 15) en waar de audit- en tijdreis-eisen het sterkst zijn.

14. Veelgemaakte fouten

Fout Gevolg Beter

Events achteraf wijzigen bij een fout Geschiedenis wordt onbetrouwbaar Een corrigerend event toevoegen
Elke vraag proberen te beantwoorden met de ruwe events, zonder projectie Trage, complexe query’s Een projectie ontwerpen per belangrijke leesvraag
Event sourcing toepassen op het hele systeem Onnodige complexiteit voor eenvoudige domeinen Selectief, waar audit/tijdreis er echt toe doen

15. Kernbegrippen

State-based opslag — de database bewaart de huidige toestand, overschrijft bij wijziging. Event-based opslag (event sourcing) — de database bewaart alle gebeurtenissen; de toestand wordt berekend. Event — een onveranderlijk feit over iets dat is gebeurd, in de verleden tijd. Event store — de append-only tabel/opslag voor events. Aggregaat — de eenheid waarop events betrekking hebben en waarvoor consistentie geldt. Stream — de geordende reeks events voor één aggregaat. Projectie — een afgeleide, leesbare weergave opgebouwd uit events. Replay — het opnieuw afspelen van events om een projectie (opnieuw) op te bouwen. Eventual consistency — de garantie dat een projectie uiteindelijk, maar niet per se onmiddellijk, de juiste stand toont. CQRS — het scheiden van schrijf- (commando) en leespaden (query) in de architectuur.

Volgende deel: event sourcing in de praktijk. Vandaag de concepten, met de erkenning dat je de bouwstenen al kende. Volgende keer bouw je een werkende event store voor Meridiaans mutatieverwerking, inclusief projecties, snapshotting, en het lastige vraagstuk van het recht op vergetelheid in een onveranderlijke geschiedenis.
