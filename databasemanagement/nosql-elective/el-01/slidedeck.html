Slide 2 — Waar we vandaan komen

Deel 21 gaf vier eerlijke gevallen voor NoSQL naast PostgreSQL:

  1. Cache-laag met sub-milliseconde eisen
  2. Relatieanalyse die inherent graafvormig is
  3. Grootschalig volledige-tekst-zoeken
  4. Logging op zeer grote schaal

Notities: vraag de zaal deze vier uit het hoofd te noemen vóór je verdergaat.

  • Vandaag: scenario 1 (Redis) en documentopslag (MongoDB)
  • Volgende sessie: scenario 2 en 4 (Neo4j, Cassandra)
  • Scenario 3 (Elasticsearch) blijft conceptueel, zoals in deel 21

NoSQL komt er naast PostgreSQL, niet in plaats ervan.

Slide 4 — Redis: wat het is

In-memory key-value store

  • Vrijwel alles in werkgeheugen → extreem snel
  • Zonder persistentie-configuratie: herstart = dataverlies
  • Nooit de enige opslag van iets belangrijks

Hash sessie met losse velden

Sorted set rate-limiter, “recent bekeken”-lijst

Slide 6 — TTL

Time to live

Een sleutel verdwijnt vanzelf na de ingestelde tijd.

De cache ruimt zichzelf op — geen aparte opruimlogica nodig.

Slide 7 — Drie invalidatiestrategieën

  1. TTL alleen — simpel, kan tijdelijk stale zijn
  2. Actief invalideren bij wijziging — vraagt discipline
  3. Write-through — nooit direct naar de bron zonder de cache mee te nemen

Notities: dit is het echte ontwerpprobleem, niet de opslag zelf.

Slide 8 — Sessieobject in Redis

HSET sessie:a1b2c3 deelnemer_id 4821 naam "Karin de Wolff" taal "nl"
EXPIRE sessie:a1b2c3 1800

Bij elke aanvraag: TTL verlengen, velden lezen — geen PostgreSQL-query.

Slide 9 — Wat wél, wat niet in de cache

Wél: naam, taal — weinig-veranderend, vaak gelezen

Niet: pensioensaldo — te belangrijk om stale te zijn, te weinig gelezen per sessie om de kost te rechtvaardigen

Leesfrequentie versus foutkosten bij staleness — de vuistregel.

Slide 11 — MongoDB: wat het is

Documentstore

  • Documenten (BSON) in collections
  • Geen vastgelegd schema
  • Twee documenten in dezelfde collection kunnen verschillen

Slide 12 — Embedding versus referencing

Embedding — genest in hetzelfde document, snel lezen, mogelijk dubbel Referencing — verwijzing naar een ID, geen databaseafdwinging

Vergelijk met deel 5 (normalisatie) en deel 6 (REFERENCES-constraint).

Slide 13 — Waarom klantcorrespondentie?

Sterk uiteenlopende metadata per kanaal:

  • E-mail: onderwerp, bijlagen
  • Telefoonnotitie: gespreksduur, medewerker-ID
  • Portaalbericht: sessie-referentie

Slide 14 — Een correspondentiedocument

{
  "deelnemer_id": 4821,
  "kanaal": "email",
  "onderwerp": "Vraag over indexatie 2026",
  "afgehandeld": false
}

Slide 15 — Zoeken en aggregeren

db.correspondentie.find({ deelnemer_id: 4821, afgehandeld: false })

db.correspondentie.aggregate([
  { $match: { afgehandeld: false } },
  { $group: { _id: "$kanaal", aantal: { $count: {} } } }
])
