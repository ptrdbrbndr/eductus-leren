1. Leerdoelen

Na dit deel kun je:

  • row level security-patronen ontwerpen voor multi-tenant-achtige scenario’s, verder dan de basisregels uit deel 9;
  • de prestatie-impact van RLS inschatten en verzachten;
  • kolomversleuteling toepassen met pgcrypto en de sleutelbeheervraag herkennen die daarbij hoort;
  • SSL/TLS voor databaseverbindingen configureren en verplicht stellen;
  • het onderscheid tussen versleuteling onderweg en in rust correct toepassen;
  • een rolhiërarchie ontwerpen die schaalt naar tientallen rollen;
  • de belangrijkste NoSQL-categorieën benoemen en tegen PostgreSQL’s eigen mogelijkheden afzetten;
  • gericht studeren voor de EDB PostgreSQL Professional-certificering.

2. Waar deel 9 ophield

In niveau 1 bouwde je de basis: rollen, GRANT/REVOKE, een eerste kennismaking met RLS, het PUBLIC-lek, SECURITY DEFINER als patroon. Dat volstond voor een enkele toepassing met een handvol rollen.

Wat er sindsdien is bijgekomen dat de zaak complexer maakt: partitionering (deel 16) die rechten per partitie kan compliceren, replicatie (deel 18) waarbij rechten en beleid op elke node moeten kloppen, en pgaudit (deel 20) dat pas zinvol is als de onderliggende rolstructuur al klopt. Dit deel voegt de patronen toe die je nodig hebt zodra een systeem groeit van “één applicatie, een paar rollen” naar “meerdere klantgroepen, tientallen rollen, een auditeis die niet vrijblijvend is”.

3. Row level security, verdiept: multi-tenant patronen

Uit deel 9: een simpel USING (eigenaar_id = current_user_id()). Bij Meridiaan wordt het patroon rijker zodra er onderscheid moet zijn tussen rollen die binnen een werkgever horen te blijven en rollen die alles mogen zien.

ALTER TABLE dienstverband ENABLE ROW LEVEL SECURITY;

CREATE POLICY werkgever_eigen_data ON dienstverband
    FOR SELECT
    USING (werkgever_id = current_setting('app.werkgever_id')::integer);

CREATE POLICY beheer_ziet_alles ON dienstverband
    FOR ALL
    TO beheer_rol
    USING (true);

Meerdere policies op dezelfde tabel worden met OR gecombineerd binnen dezelfde opdracht-categorie (SELECT, UPDATE, …) — een rij is zichtbaar als minstens één toepasselijke policy hem toelaat. Dat is een makkelijk te vergeten detail: twee restrictieve policies die je bedoelde als AND, werken in werkelijkheid als OR, tenzij je expliciet AS RESTRICTIVE gebruikt:

CREATE POLICY alleen_binnen_kantooruren ON dienstverband
    AS RESTRICTIVE
    FOR ALL
    USING (extract(hour FROM now()) BETWEEN 8 AND 18);

Een RESTRICTIVE-policy wordt met AND gecombineerd bovenop de gewone (permissieve) policies — hij kan alleen verder inperken, nooit verruimen. Voor een eis als “nooit buiten kantooruren, ongeacht wat de rest toestaat” is dat precies het gedrag dat je wilt.

Het patroon voor Meridiaan’s werkgeverportaal: elke sessie zet bij het inloggen app.werkgever_id op basis van de geauthenticeerde gebruiker, en alle RLS-policies verwijzen naar die sessie-instelling. Dit is dezelfde current_setting()-truc als in deel 9, nu opgeschaald naar meerdere policies die samen een compleet multi-tenant-model vormen.

4. RLS en prestaties

RLS is geen gratis beveiliging. De policy-voorwaarde wordt effectief toegevoegd aan elke query op die tabel, en de planner moet daar rekening mee houden.

EXPLAIN ANALYZE SELECT * FROM dienstverband WHERE deelnemer_id = 42;

Met RLS aan, verschijnt de policy-voorwaarde als extra filter in het plan. Zonder een index die bij de policy-kolom past, betekent dat een extra sequentiële doorloop bovenop wat de query zelf al vroeg.

CREATE INDEX ON dienstverband (werkgever_id);

De valkuil die het meest voorkomt: een policy die een functie aanroept (bijvoorbeeld een lookup naar een aparte tabel om te bepalen tot welke werkgever de gebruiker hoort) in plaats van een simpele sessie-instelling. Zo’n functie wordt per rij aangeroepen tenzij de planner hem kan optimaliseren — een prestatieval die niet in de eerste kennismaking met RLS zichtbaar wordt (een tabel met honderd rijen in deel 9), maar wel bij 466.000 dienstverbanden.

-- Traag: functie-aanroep per rij
CREATE POLICY … USING (werkgever_id = huidige_werkgever());

-- Sneller: directe sessie-instelling, geen functieaanroep
CREATE POLICY … USING (werkgever_id = current_setting('app.werkgever_id')::integer);

Markeer een functie die je toch nodig hebt als STABLE of IMMUTABLE waar dat klopt (deel 8) — dat geeft de planner meer ruimte om hem niet onnodig vaak opnieuw te evalueren.

5. pgcrypto: kolomversleuteling

RLS regelt wie een rij mag zien. Soms wil je dat zelfs een rol met leestoegang de waarde niet in leesbare vorm ziet zonder een aparte sleutel — bijvoorbeeld bij een veld dat nog gevoeliger is dan de rest.

CREATE EXTENSION pgcrypto;

-- Versleutelen bij het opslaan
UPDATE deelnemer
SET rekeningnummer_enc = pgp_sym_encrypt(rekeningnummer, 'sleutel-uit-kluis')
WHERE deelnemer_id = 42;

-- Ontsleutelen bij het lezen, alleen met de sleutel
SELECT pgp_sym_decrypt(rekeningnummer_enc, 'sleutel-uit-kluis') FROM deelnemer;

De sleutel hoort nooit in de query zelf, en zeker niet in de applicatiecode als tekst. Een sleutelbeheersysteem (HashiCorp Vault, of een cloud-eigen equivalent) dat de sleutel op aanvraag levert, is de praktische aanpak — dit is een integratiepunt dat buiten PostgreSQL zelf valt, maar je moet het als DBA kunnen aanwijzen als ontbrekend stuk in een ontwerp.

De afweging, expliciet:

Zonder kolomversleuteling Met kolomversleuteling
Doorzoekbaarheid Volledig (indexeerbaar) Beperkt — een versleutelde waarde is niet direct te indexeren op inhoud
Bescherming bij een gelekte back-up Geen Ja, als de sleutel apart blijft
Complexiteit Laag Sleutelbeheer, applicatie-aanpassingen
Prestatie Normaal Extra CPU-kosten per operatie

Wanneer dit de moeite waard is bij Meridiaan: een klein aantal bijzonder gevoelige velden (rekeningnummers, medische indicaties bij arbeidsongeschiktheid) waarbij zelfs RLS en toegangscontrole onvoldoende zekerheid geven — bijvoorbeeld als eis vanuit een specifieke wettelijke verplichting. Niet voor elke kolom met persoonsgegevens: dat zou de doorzoekbaarheid van vrijwel de hele database wegnemen voor weinig extra bescherming boven wat RLS en rolgebonden rechten al geven.

6. Versleuteling onderweg: SSL/TLS

Verkeer tussen applicatie en database, onversleuteld, is af te luisteren op elk punt onderweg — een ander risico dan wie er in de database zelf mag kijken.

# postgresql.conf
ssl = on
ssl_cert_file = 'server.crt'
ssl_key_file = 'server.key'

# pg_hba.conf — dwing SSL af, niet optioneel
hostssl  meridiaan  all  0.0.0.0/0  scram-sha-256

hostssl in plaats van host betekent dat een verbindingspoging zonder SSL wordt geweigerd — niet alleen aangeboden als mogelijkheid. Dit is het verschil tussen “SSL is beschikbaar” en “SSL is verplicht”, en voor productieverkeer met persoonsgegevens hoort het het laatste te zijn.

Vanaf de clientkant:

psql "host=... dbname=meridiaan sslmode=verify-full sslrootcert=ca.crt"

sslmode=verify-full controleert niet alleen dat er versleuteling is, maar ook dat het certificaat bij de verwachte server hoort — bescherming tegen een man-in-the-middle die zich voordoet als de databaseserver. Lagere niveaus (require, verify-ca) geven geleidelijk minder garantie; voor productieverkeer is verify-full de aanbeveling.

7. Versleuteling in rust: het onderscheid dat vaak wordt gemist

Versleuteling onderweg (paragraaf 6) beschermt tegen afluisteren tussen client en server. Versleuteling in rust beschermt de bestanden op de schijf zelf — relevant als iemand fysieke toegang tot de schijf krijgt, of een back-up (deel 17) op een onbeveiligde locatie belandt.

PostgreSQL zelf biedt geen ingebouwde volledige-schijfversleuteling (transparent data encryption zoals sommige andere systemen die kennen). De gangbare aanpak is versleuteling op besturingssysteemniveau — een versleuteld bestandssysteem (LUKS op Linux, of het cloud-eigen equivalent bij een beheerde dienst) waarbinnen het datadirectory staat.

Wat dit wel en niet oplost:

Dreiging Versleuteling in rust helpt?
Gestolen fysieke schijf Ja
Onbeveiligde back-up op een externe locatie Ja, als de back-up zelf ook versleuteld is (deel 17, pgBackRest-encryptie)
Een gecompromitteerde databaserol met leesrechten Nee — die rol leest via de draaiende server, die de gegevens ontsleuteld aanbiedt
SQL-injectie of een kwetsbare applicatie Nee — hetzelfde argument

De les: versleuteling in rust is een aanvulling op toegangscontrole (RLS, rollen), niet een vervanging. Een aanvaller met een geldige databaseverbinding en voldoende rechten ziet de gegevens gewoon, versleuteld-op-schijf of niet — de server ontsleutelt voor hem.

8. Rolhiërarchie op schaal

Uit deel 9: rollen, GRANT, REVOKE. Bij een groeiend aantal rollen (klantenservice, werkgeverportaal per sector, rapportage, beheer, migratie, backup — elk uit een eerder dagdeel) wordt losse toekenning onbeheersbaar.

-- Groepsrollen: geen LOGIN, alleen een verzameling rechten
CREATE ROLE lezer_deelnemer NOLOGIN;
GRANT SELECT ON deelnemer TO lezer_deelnemer;

CREATE ROLE schrijver_mutatie NOLOGIN;
GRANT SELECT, INSERT, UPDATE ON mutatie TO schrijver_mutatie;

-- Individuele of applicatierollen erven van groepsrollen
CREATE ROLE klantenservice LOGIN PASSWORD '...';
GRANT lezer_deelnemer TO klantenservice;
GRANT schrijver_mutatie TO klantenservice;

Het voordeel: een recht wijzigen op lezer_deelnemer werkt door naar elke rol die hem heeft geërfd, in plaats van dat je tientallen individuele GRANT-opdrachten moet naspeuren en herhalen.

-- Overzicht: wie heeft via welke groep welk recht?
SELECT r.rolname AS rol, g.rolname AS via_groep
FROM pg_auth_members m
JOIN pg_roles r ON r.oid = m.member
JOIN pg_roles g ON g.oid = m.roleid
ORDER BY r.rolname;

DEFAULT PRIVILEGES voor toekomstige objecten — een detail dat vaak wordt vergeten en dat tot rechtenlekken leidt:

ALTER DEFAULT PRIVILEGES IN SCHEMA meridiaan_prod
    GRANT SELECT ON TABLES TO lezer_deelnemer;

Zonder deze instelling krijgt een nieuwe tabel in het schema geen automatische rechten voor lezer_deelnemer — iemand moet er expliciet aan denken bij elke nieuwe tabel. Met DEFAULT PRIVILEGES gebeurt dat automatisch, wat het risico van een vergeten GRANT op een gevoelige nieuwe tabel wegneemt (of, omgekeerd, het risico dat een nieuwe tabel onbedoeld toegankelijk is — controleer dus zorgvuldig wélke standaardrechten je instelt).

9. SECURITY DEFINER, herzien met scherpere randen

Uit deel 9: een functie die met de rechten van de eigenaar draait in plaats van de aanroeper — nuttig om gecontroleerde toegang te geven zonder brede tabelrechten weg te geven.

De valkuil die in deel 9 nog niet werd uitgewerkt: search_path. Een SECURITY DEFINER-functie die geen expliciet schema opgeeft, kan door een kwaadwillende aanroeper worden misleid als die zijn eigen search_path zo zet dat een eigen, kwaadaardige functie of tabel met dezelfde naam eerder wordt gevonden dan de bedoelde.

-- Kwetsbaar: search_path niet vastgezet
CREATE FUNCTION genereer_rapportage() RETURNS void
    SECURITY DEFINER
    LANGUAGE plpgsql AS $$ ... $$;

-- Veilig: search_path expliciet en vast
CREATE FUNCTION genereer_rapportage() RETURNS void
    SECURITY DEFINER
    SET search_path = meridiaan_prod, pg_catalog
    LANGUAGE plpgsql AS $$ ... $$;

De regel, zonder uitzondering: elke SECURITY DEFINER-functie krijgt een expliciete SET search_path. Dit is een van de weinige plekken in PostgreSQL waar het weglaten van een instelling een concreet, exploiteerbaar beveiligingslek is in plaats van alleen een prestatie- of correctheidskwestie.

10. Wat we tot nu toe niet bespraken: NoSQL

Twintig dagdelen lang draaide alles om het relationele model. Terecht — het is nog steeds de juiste standaardkeuze voor de meeste administratieve systemen zoals Meridiaans kernregistratie. Maar de vraag “waarom niet NoSQL” verdient een eerlijk antwoord, niet een ontwijking.

Wat NoSQL als term dekt, is geen enkel ding. Het is een verzamelnaam voor datastores die niet het klassieke relationele model met SQL als hoofdinterface volgen — en de motivaties daarachter lopen sterk uiteen per categorie.

11. De categorieën op een rij

Categorie Voorbeeld Sterk in Zwak in
Document MongoDB Flexibel schema, geneste structuren Complexe joins, transactionele garanties over meerdere documenten
Key-value Redis Extreme snelheid bij eenvoudige opzoekingen Geen querytaal voor complexe vragen
Wide-column Cassandra Schrijfschaal over vele servers Ad-hoc query’s, consistentiegaranties
Graaf Neo4j Relatiepaden, netwerkanalyse Grote aggregaties, algemeen gebruik
Zoek-georiënteerd Elasticsearch Volledige-tekst-zoeken op schaal Als primaire bron van waarheid

De motivatie is zelden “sneller” in algemene zin. Het is bijna altijd: een specifiek toegangspatroon (extreem veel simpele opzoekingen, relatiepaden, tekstzoeken) waarvoor een gespecialiseerde structuur beter past dan een algemeen relationeel model — precies dezelfde logica als GIN versus BRIN versus B-tree in deel 14, nu op het niveau van hele datastores in plaats van indextypen.

12. Wat PostgreSQL al dekt van wat mensen bij NoSQL zoeken

Een groot deel van de historische motivatie voor NoSQL (flexibel schema, snel opzoeken, documentopslag) is inmiddels binnen PostgreSQL zelf beschikbaar, en je hebt het al gebruikt:

Wat mensen bij NoSQL zochten Wat PostgreSQL biedt Waar je het zag
Flexibel, schemaloos opslaan jsonb Deel 6, 14 (koppelvlakbericht)
Snel zoeken binnen documenten GIN op jsonb Deel 14
Key-value opzoeking Een tabel met twee kolommen plus een index, of hstore Deel 8, 14
Volledige-tekst-zoeken tsvector/to_tsquery, of pg_trgm Deel 14
Horizontale schrijfschaal Partitionering (deel 16) plus, op grotere schaal, Citus (niveau 3) Deel 16
Extreme leessnelheid bij eenvoudige queries Een goed geïndexeerde tabel, eventueel met een replica (deel 18) Deel 8, 18

De praktische conclusie voor de meeste organisaties: begin met PostgreSQL en zijn jsonb-mogelijkheden, en stap pas over naar een gespecialiseerde NoSQL-oplossing als er een concreet, gemeten knelpunt is dat PostgreSQL niet oplost — niet omdat NoSQL nieuwer klinkt. Dit is dezelfde discipline als bij BRIN (deel 14) en partitionering (deel 16): kies het gespecialiseerde gereedschap op basis van een gemeten behoefte, niet op basis van enthousiasme.

13. Wanneer NoSQL wél de juiste keuze is

Eerlijke gevallen waarin een aparte datastore de betere keuze is, ook naast een goed gebruikte PostgreSQL-installatie:

Een cache-laag met sub-milliseconde eisen op eenvoudige sleutel-opzoekingen waar zelfs een goed geïndexeerde PostgreSQL-tabel de latency-eis niet haalt: Redis ervoor.

Relatieanalyse die inherent graafvormig is — “welke deelnemers delen een werkgever binnen twee schakels van een gegeven deelnemer, via welke tussenliggende relaties” wordt in SQL met recursieve CTE’s (deel 4, 8) mogelijk maar onhandelbaar bij grote, diepe netwerken. Een graafdatabase is daar natuurlijker.

Volledige-tekst-zoeken op een schaal en met functies (facetten, relevantiescoring, fuzzy op grote schaal) die pg_trgm/tsvector niet meer comfortabel aankunnen: Elasticsearch naast PostgreSQL, met PostgreSQL als bron van waarheid en Elasticsearch als afgeleide zoekindex.

Logging/telemetrie op zeer grote, ongestructureerde schaal waar schrijfschaal over honderden servers de eis is: een wide-column store, met PostgreSQL voor de gestructureerde kant van het systeem.

Het patroon in alle vier: NoSQL komt er naast PostgreSQL, niet in plaats ervan. Meridiaans kernregistratie — deelnemers, dienstverbanden, aanspraken, mutaties — blijft relationeel, want de integriteitseisen (deel 6), de transactionele garanties (deel 7) en de query-flexibiliteit (deel 3, 4) die daar nodig zijn, zijn precies waar het relationele model sterk in is.

14. Een eerlijke vergelijking, geen wedstrijd

De vraag “SQL of NoSQL” is verkeerd gesteld. De juiste vraag, per toegangspatroon:

Heeft dit specifieke stuk van het systeem een toegangspatroon dat een gespecialiseerde structuur vraagt, en is de winst daarvan groot genoeg om de kosten van een tweede systeem (operationeel, consistentie tussen de twee, extra kennis in het team) te rechtvaardigen?

Voor de kern van Meridiaan is het antwoord nee — de administratieve, sterk samenhangende, integriteitsgevoelige aard van pensioengegevens past bij uitstek bij het relationele model. Voor randgevallen (zoeken, caching, toekomstige analysebehoeften) kan het antwoord ja zijn, en dan is de vervolgvraag niet “welk systeem is beter” maar “hoe houd ik de twee systemen consistent” — vaak weer via logische replicatie (deel 18) vanuit PostgreSQL als bron van waarheid.

15. Examenvoorbereiding: hoe de EDB-certificering is opgebouwd

Na twee niveaus is dit een goed moment om het certificeringstraject zelf te bespreken, los van de inhoud.

De structuur: EDB PostgreSQL Associate (niveau 1-stof) en EDB PostgreSQL Professional (niveau 2-stof) zijn afzonderlijke examens, elk met een eigen blauwdruk die periodiek wordt bijgewerkt. Controleer altijd de actuele blauwdruk vlak vóór je het examen plant — versies en nadrukpunten verschuiven.

Hoe te studeren vanaf hier:

  1. Loop de “aansluiting op de certificering”-paragrafen van elk deel (11 t/m 20) nog eens langs als checklist.
  2. Vertaal elke praktijkopdracht die je hebt gedaan naar een korte, mondelinge samenvatting — “wat zou ik hierover zeggen zonder de query voor me te hebben” is een betere test dan de query nog eens uittypen.
  3. Oefen met de officiële voorbeeldvragen van EDB, waar beschikbaar; die tonen het soort scenario-vraag (niet alleen definities) dat het examen gebruikt.
  4. Herhaal specifiek de onderwerpen waarbij dit niveau een cijfer of drempel gaf (deel 12’s wraparound-percentages, deel 19’s ttl, deel 20’s alarmdrempels) — examens toetsen vaak of je weet wanneer iets een probleem wordt, niet alleen dat het een concept is.

Wat dit deel je niet geeft: een garantie. Deze cursus is voorbereiding op de inhoud; het examen zelf toetst ook precisie onder tijdsdruk, wat alleen oefenen met een tijdslimiet traint.

16. Veelgemaakte fouten

Fout Gevolg Beter
Meerdere restrictieve policies bedoeld als AND, maar permissief gemaakt Rechten ruimer dan bedoeld AS RESTRICTIVE waar nodig
RLS-policy met een functie-aanroep per rij Trage query’s op schaal Sessie-instelling of STABLE-functie
Encryptiesleutel in applicatiecode of de query zelf Sleutel net zo blootgesteld als de data Extern sleutelbeheer
Versleuteling in rust zien als volledige bescherming Vals gevoel van veiligheid tegen gecompromitteerde rollen Combineren met RLS/rolrechten
hostssl vergeten, alleen host Onversleuteld verkeer blijft mogelijk Expliciet hostssl, geen host voor gevoelig verkeer
SECURITY DEFINER zonder vaste search_path Exploiteerbaar beveiligingslek Altijd SET search_path
DEFAULT PRIVILEGES vergeten Nieuwe tabellen onbedoeld ontoegankelijk óf onbedoeld toegankelijk Bewust instellen, niet negeren
NoSQL kiezen zonder gemeten knelpunt Twee systemen, extra complexiteit, geen aantoonbare winst Eerst PostgreSQL’s eigen mogelijkheden (jsonb, GIN) proberen
Denken dat NoSQL de kernregistratie moet vervangen Verlies van integriteitsgaranties die het domein nodig heeft NoSQL naast, niet in plaats van, waar het past

17. Kernbegrippen

Permissieve/restrictieve policy — hoe meerdere RLS-policies worden gecombineerd (OR respectievelijk AND). pgcrypto — extensie voor kolomversleuteling. Versleuteling onderweg / in rust — bescherming tijdens transport respectievelijk op de opslaglocatie. hostssl — pg_hba.conf-regel die SSL verplicht in plaats van optioneel maakt. sslmode=verify-full — strengste clientcontrole op de identiteit van de server. Groepsrol — een NOLOGIN-rol die rechten bundelt voor overerving. DEFAULT PRIVILEGES — vooraf ingestelde rechten voor nog te maken objecten. search_path-kaping — het beveiligingslek dat ontstaat als een SECURITY DEFINER-functie geen vast schema-pad heeft. Document/key-value/wide-column/graaf-datastore — de belangrijkste NoSQL-categorieën. jsonb/GIN — PostgreSQL’s eigen antwoord op veel document-georiënteerde behoeften.
