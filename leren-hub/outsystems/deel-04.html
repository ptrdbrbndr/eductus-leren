01

Server actions: waar bedrijfslogica woont

⏱ 5 min

Een server action is een visuele flow die op de server wordt uitgevoerd: je ziet stappen als knopen op een canvas, verbonden door pijlen die de uitvoeringsvolgorde tonen. Voor Verzuimmeldingen bouw je in dit deel AanmaakMelding — een server action die controleert of de ingevoerde startdatum geldig is, de melding met status Nieuw wegschrijft, en het resultaat teruggeeft.

Elke stap in een flow is een van een beperkt aantal bouwstenen: een dataquery (Aggregate), een schrijfactie (Create/Update/Delete Entity), een conditie (If), een lus (For Each), een aanroep naar een andere action, of een expressie. Dat is een bewuste beperking van het platform: door het aantal bouwstenen klein te houden, blijft een flow leesbaar voor iemand die hem niet zelf schreef — precies het voordeel dat in deel 1 werd genoemd.

Controlevraag

Uit Werkboek deel 4, Opdracht 4.1 — Server of client action?

1Bepaal voor elk van de volgende stukken logica van Verzuimmeldingen of dit een server action of een client action moet zijn, en waarom.

a. Controleren of het veld "startdatum" is ingevuld voordat het formulier wordt verzonden.

b. Een nieuwe melding wegschrijven naar de database met status Nieuw.

c. Controleren of de ingevoerde startdatum niet in de toekomst ligt, vergeleken met de systeemdatum van de server.Toon antwoord

a. Client action — geen serverdata nodig, directe feedback voordat er iets naar de server gaat.

b. Server action — schrijftoegang tot de database is per definitie server-side.

c. Server action, ondanks dat het op het eerste gezicht op client-validatie lijkt. De vergelijking moet tegen de betrouwbare servertijd, niet de (manipuleerbare) kloktijd van de client — anders kan een gebruiker de systeemklok van zijn eigen apparaat aanpassen om de validatie te omzeilen.

02

Client actions versus server actions

⏱ 5 min

Een client action draait in de browser (of app), niet op de server. Gebruik je voor logica die geen serverdata nodig heeft — bijvoorbeeld een velden-validatie die direct feedback geeft voordat een formulier wordt verzonden. Voor Verzuimmeldingen: een client action die controleert of het verplichte veld "startdatum" is ingevuld, zonder daarvoor naar de server te hoeven.

De vuistregel: alles wat de gebruiker moet zien vóórdat er data heen-en-weer naar de server gaat, hoort in een client action. Alles wat toegang tot de database of serverzijdige regels vereist, hoort in een server action.

03

Exceptions en foutafhandeling

⏱ 5 min

Een server action kan een exception opwerpen — bijvoorbeeld wanneer een schrijfactie faalt door een databaseconflict. OutSystems biedt de Exception Handler-bouwsteen om dit gestructureerd op te vangen: je vangt een specifiek excepties-type (of alle) op een tak van de flow, en bepaalt daar wat de gebruiker te zien krijgt.

Voor AanmaakMelding: als het wegschrijven faalt, wil je niet dat de HR-medewerker een technische foutmelding ziet, maar een begrijpelijke boodschap ("De melding kon niet worden opgeslagen, probeer het opnieuw"). Dat onderscheid — technische fout versus gebruikersvriendelijke boodschap — is een ontwerpkeuze die het platform faciliteert maar niet voor je maakt.

04

De debugger

⏱ 5 min

Beide platformen bieden een debugger waarmee je een flow stap voor stap kunt doorlopen, variabelen kunt inspecteren op elk punt, en breakpoints kunt zetten. Dit is essentieel bij het uitzoeken waarom AanmaakMelding bijvoorbeeld een onverwachte status oplevert: in plaats van te gissen, loop je de flow visueel door en zie je exact welke tak is genomen en welke waarde elke variabele had.

Verschil O11 ↔ ODC: de debug-ervaring is conceptueel gelijk — stap voor stap door een flow, variabelen inspecteren. In O11 start je een debug-sessie doorgaans tegen een specifieke Environment; in ODC is de sessie geïntegreerd in de cloud-workspace, met minder handmatige configuratie om een debug-sessie op te starten.

05

Kernpunten

⏱ 5 min
  • Server actions bevatten bedrijfslogica en draaien server-side; client actions draaien in de browser/app voor logica zonder serverdata
  • Een beperkt aantal visuele bouwstenen houdt flows leesbaar — dat is een bewuste ontwerpkeuze van het platform
  • Exception Handlers vangen fouten gestructureerd op; het onderscheid tussen technische fout en gebruikersboodschap blijft aan jou
  • De debugger werkt conceptueel gelijk in beide platformen; ODC vereist minder handmatige configuratie om te starten
Controlevraag

Uit Werkboek deel 4, Reflectieopdracht 4.2 — Reflectie

1Waarom moet de exception in AanmaakMelding resulteren in een gebruikersvriendelijke boodschap in plaats van de technische foutmelding die het platform standaard zou tonen?Toon antwoord

Een technische foutmelding (bijvoorbeeld een ruwe database-foutcode) is voor een HR-medewerker onbruikbaar en kan zelfs verwarrend of intimiderend overkomen — het lost het probleem van de gebruiker niet op en kan het vertrouwen in de applicatie schaden. Een gestructureerde Exception Handler geeft je de plek om technische details te loggen (voor de ontwikkelaar) terwijl de gebruiker een begrijpelijke, actiegerichte boodschap ziet. Dit is een klein voorbeeld van een patroon dat in deel 17 (beveiliging serieus) veel groter terugkomt: technische informatie nooit onnodig aan de eindgebruiker blootstellen.
