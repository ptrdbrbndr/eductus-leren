01

Wat is systemd?

⏱ 12 min

systemd is op vrijwel elke moderne Linux-distributie — waaronder Ubuntu — het eerste proces dat de kernel start (PID 1) en het systeem dat vervolgens alle andere processen, diensten en mountpoints beheert. Waar oudere systemen (SysV init) diensten sequentieel starten via genummerde shellscripts, start systemd diensten parallel waar mogelijk, op basis van expliciete afhankelijkheden tussen units.

Een unit is de generieke naam voor alles wat systemd beheert: een dienst (.service), een mountpoint (.mount), een timer (.timer, alternatief voor cron — zie deel 22), een socket (.socket), of een groepering van andere units (.target).

De boot-flow, vereenvoudigd

  1. De kernel laadt en start het init-proces, systemd, als PID 1.
  2. Systemd activeert het standaard-target — op een servermachine doorgaans multi-user.target (opstarten zonder grafische omgeving).
  3. Dat target heeft zelf afhankelijkheden naar andere targets en units (netwerk, lokale bestandssystemen, basisdiensten), die systemd in de juiste volgorde en waar mogelijk parallel start.
  4. Individuele .service-units starten zodra hun eigen afhankelijkheden (After=, Requires=) vervuld zijn.
Casus

Fenna legt Milan uit waarom een server soms "blijft hangen" bij het opstarten: een unit met een harde afhankelijkheid (Requires=netwerk-online.target) wacht op een dienst die zelf niet start. Met systemctl list-jobs tijdens het opstarten (of systemd-analyze blame na het opstarten) is precies te zien welke unit de vertraging veroorzaakt.

02

Diensten beheren met systemctl

⏱ 10 min

De status van een dienst opvragen:

systemctl status ssh

De uitvoer toont of de dienst actief (active (running)), inactief, of mislukt (failed) is, sinds wanneer, het proces-ID, en de laatste paar logregels.

Starten, stoppen, herstarten en herladen (waar ondersteund, zonder het proces volledig te stoppen):

sudo systemctl start rapportage-agent
sudo systemctl stop rapportage-agent
sudo systemctl restart rapportage-agent
sudo systemctl reload rapportage-agent

Een dienst automatisch laten starten bij het opstarten van het systeem, respectievelijk dat weer uitzetten:

sudo systemctl enable rapportage-agent
sudo systemctl disable rapportage-agent

Belangrijk: enable start de dienst niet meteen, en start maakt de dienst niet persistent na een herstart. Voor beide tegelijk:

sudo systemctl enable --now rapportage-agent

Alle actieve units bekijken:

systemctl list-units --type=service

Alle mislukte units:

systemctl --failed
Controlevraag

Uit Werkboek deel 19, Opdracht 19.1 + Uitwerking 19.1

03

Een eigen unit file schrijven

⏱ 14 min

Milan krijgt de opdracht een script dat aanleveringen bewaakt (bewaak_aanlevering.sh, uit deel 16) om te zetten in een beheerde systemd-dienst, in plaats van hem handmatig in tmux te starten.

Eigen unit files horen in /etc/systemd/system/. Bestandsnaam: rapportage-agent.service.

[Unit]
Description=Bewaakt aanlevering van mutatiebestanden voor het Rapportagecluster
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/opt/rapportage/bewaak_aanlevering.sh
Restart=on-failure
RestartSec=5
User=rapportage
WorkingDirectory=/opt/rapportage

[Install]
WantedBy=multi-user.target

Toelichting per sectie:

[Unit] bevat metadata en afhankelijkheden. Description is de tekst die bij systemctl status verschijnt. After=network-online.target zorgt dat deze dienst pas start nadat het netwerk actief is; Wants= drukt een zachte afhankelijkheid uit (de dienst start ook door als het netwerk faalt, maar wacht wel als mogelijk) tegenover Requires=, een harde afhankelijkheid (faalt de vereiste unit, dan start deze unit niet).

[Service] beschrijft hoe het proces zelf gestart en beheerd wordt. Type=simple betekent dat het hoofdproces van ExecStart de dienst zelf is. Restart=on-failure met RestartSec=5 laat systemd de dienst automatisch herstarten vijf seconden na een crash — precies het gedrag dat in deel 16 nog niet bestond toen Milan het script handmatig in tmux draaide. User= voorkomt dat de dienst als root draait.

[Install] bepaalt bij welk target de dienst hoort als hij ge-enabled wordt; WantedBy=multi-user.target is de gebruikelijke keuze voor een servergebonden achtergronddienst.

Na het aanmaken of wijzigen van een unit file moet systemd de configuratie herinlezen:

sudo systemctl daemon-reload
sudo systemctl enable --now rapportage-agent
sudo systemctl status rapportage-agent
Controlevraag

Uit Werkboek deel 19, Opdracht 19.5 (reflectie)

1rapportage-agent heeft een netwerkshare nodig die via /etc/fstab gemount wordt als een aparte systemd-mountunit. Welke directieve (After= en/of Requires=) voegt u toe in [Unit], en wat is het verschil in gedrag?Toon antwoord
After=netwerkshare.mount zorgt alleen voor de juiste volgorde: rapportage-agent wacht tot de mountunit is afgerond (succesvol of niet) voordat hij zelf start, maar start ook door als de mount mislukt. Requires=netwerkshare.mount (meestal gecombineerd met After= voor de volgorde) maakt de afhankelijkheid hard: mislukt de mount, dan start rapportage-agent niet. Voor een dienst die zonder die netwerkshare functioneel niets kan doen, is de combinatie After= + Requires= de juiste keuze; voor een dienst die ook zonder die share gedeeltelijk bruikbaar is, volstaat After= alleen.
04

Logs volgen met journald

⏱ 10 min

journald is de logging-component van systemd; alle output van units (stdout/stderr) en systeemberichten komen terecht in een binaire, doorzoekbare log die u opvraagt met journalctl.

Logs van één specifieke unit:

journalctl -u rapportage-agent

Live meelezen, vergelijkbaar met tail -f:

journalctl -u rapportage-agent -f

Filteren op tijd:

journalctl -u rapportage-agent --since "1 hour ago"
journalctl -u rapportage-agent --since "2026-08-28 09:00" --until "2026-08-28 10:00"

Filteren op ernst (priority), bijvoorbeeld alleen fouten en hoger:

journalctl -u rapportage-agent -p err

Systeembrede logs sinds de laatste opstart:

journalctl -b

Standaard is de journal soms alleen in het geheugen of beperkt persistent; op de meeste Ubuntu Server-installaties is persistente opslag (/var/log/journal/) al ingeschakeld. Ruimtegebruik beperken:

sudo journalctl --vacuum-size=500M
Casus

Nadat Milan rapportage-agent als dienst heeft opgezet, crasht die de eerste nacht drie keer. Met journalctl -u rapportage-agent --since today -p err vindt hij snel de foutmelding (een tijdelijk onbereikbare netwerkshare) en met systemctl status rapportage-agent ziet hij dat Restart=on-failure telkens netjes heeft opnieuw gestart — precies waarom hij dit destijds zo instelde.
