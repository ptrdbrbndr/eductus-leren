01

Van handmatig naar herhaalbaar

⏱ 8 min

Tot dusver heeft Milan elke Ubuntu Server-machine in het Rapportagecluster met de hand ingericht: inloggen via SSH, pakketten installeren, configuratiebestanden aanpassen, services herstarten. Dat werkt bij drie machines, met horten en stoten. Fenna wijst hem op het echte probleem: bij de eerstvolgende uitbreiding van het cluster — en die komt, want het Mutatieplatform-programma vraagt om meer rapportagecapaciteit — moet exact dezelfde inrichting herhaalbaar zijn, zonder dat iemand een checklist met veertig stappen met de hand afwerkt. Elke handmatige stap die wordt overgeslagen of in de verkeerde volgorde uitgevoerd, is een potentiële configuratiedrift tussen machines — precies het soort inconsistentie dat in deel 26 al zichtbaar werd tussen test en productie.

Ansible is een automatiseringstool die deze herhaalbaarheid biedt zonder dat er op de beheerde machines iets geïnstalleerd hoeft te worden. Dat laatste is het kenmerk dat Ansible onderscheidt van tools als Puppet of Chef: geen agent, geen achtergrondservice op elke server — alleen SSH en Python.

02

Push-architectuur

⏱ 8 min

Ansible werkt via een push-architectuur: één machine, de controlenode, verbindt via SSH met de managed nodes (de beheerde machines) en voert daar taken uit. Er is geen voortdurend draaiende agent op de beheerde machines die uit zichzelf configuratie ophaalt (dat zou een pull-model zijn, zoals bijvoorbeeld Puppet dat vaak gebruikt); de controlenode initieert elke actie op het moment dat u een playbook uitvoert.

Het voordeel voor het Rapportagecluster is direct: geen extra software op de productieservers, geen extra aanvalsoppervlak, en de controlenode kan tijdelijk zijn — Milans eigen laptop, of straks een aparte beheer-VM die alleen aan staat wanneer nodig.

03

Ansible installeren en de inventory

⏱ 12 min

Op de controlenode (niet op de managed nodes):

sudo apt update
sudo apt install -y ansible
ansible --version

Ansible heeft SSH-sleutelauthenticatie nodig naar elke beheerde machine (zie deel 15, niveau 2, voor de opzet van SSH-keys). De inventory beschrijft welke machines er zijn en hoe ze gegroepeerd worden. Milan legt het Rapportagecluster vast in inventory.ini:

[rapportage]
rapportage-01 ansible_host=10.20.1.11
rapportage-02 ansible_host=10.20.1.12
rapportage-03 ansible_host=10.20.1.13

[rapportage:vars]
ansible_user=ansible
ansible_ssh_private_key_file=~/.ssh/id_ed25519_ansible

De groep [rapportage] maakt het mogelijk om taken op alle drie de machines tegelijk uit te voeren onder één naam. Test de bereikbaarheid met de ping-module (die geen ICMP gebruikt, maar controleert of Ansible via SSH en Python bij de machine kan):

ansible rapportage -i inventory.ini -m ping
Controlevraag

Uit Werkboek deel 27, Uitwerking 27.1c

1U voert ansible homelab -i inventory.ini -m ping uit en krijgt UNREACHABLE te zien. Wat controleert u als eerste, en welke andere foutcategorie kan optreden op zeer minimale images?Toon antwoord
UNREACHABLE wijst op een mislukte SSH-verbinding: controleer de sleutel, de hostnaam en de poort. Op zeer minimale images ontbreekt soms python3, wat een Python-gerelateerde foutmelding geeft — installeer die dan eenmalig handmatig of via de raw-module, die geen Python op het doel vereist.
04

Ad-hoc commando's

⏱ 10 min

Voor eenmalige acties op meerdere machines tegelijk is een los commando vaak sneller dan een heel playbook:

ansible rapportage -i inventory.ini -m command -a "uptime"
ansible rapportage -i inventory.ini -m apt -a "update_cache=yes" --become
ansible rapportage -i inventory.ini -m shell -a "df -h /data"

--become laat Ansible het equivalent van sudo gebruiken op de beheerde machine. Het verschil tussen de modules command en shell is van belang: command voert het programma direct uit zonder shell-interpretatie (geen pipes, geen $VAR-expansie), terwijl shell het commando via /bin/sh laat lopen en dus wel shell-functionaliteit toestaat.

Vuistregel van Fenna

Gebruik command tenzij u aantoonbaar shell-functionaliteit nodig hebt.

Controlevraag

Uit Werkboek deel 27, Opdracht 27.2c / Uitwerking 27.2c

1Waarom heeft ansible homelab -i inventory.ini -m command -a "df -h" geen --become nodig, terwijl ansible homelab -i inventory.ini -m apt -a "update_cache=yes" --become dat wel heeft?Toon antwoord
Schijfruimte opvragen is een leesactie die als gewone gebruiker uitgevoerd kan worden. De pakketcache bijwerken vereist schrijfrechten op systeemniveau (/var/lib/apt), en dus verhoogde rechten via --become, vergelijkbaar met sudo apt update lokaal.
05

Playbooks: herhaalbare configuratie

⏱ 15 min

Een playbook is een YAML-bestand met een geordende reeks taken. Milans eerste playbook richt een basisconfiguratie in op alle rapportagemachines:

---
- name: Basisconfiguratie Rapportagecluster
  hosts: rapportage
  become: true

  vars:
    rapportage_gebruiker: rapportage-svc

  tasks:
    - name: Pakketlijst bijwerken
      apt:
        update_cache: true
        cache_valid_time: 3600

    - name: Benodigde pakketten installeren
      apt:
        name:
          - python3-pip
          - fail2ban
        state: present

    - name: Service-gebruiker aanmaken
      user:
        name: "{{ rapportage_gebruiker }}"
        system: true
        shell: /usr/sbin/nologin

    - name: Configuratiebestand plaatsen
      template:
        src: templates/rapportage.conf.j2
        dest: /etc/rapportage/rapportage.conf
        owner: "{{ rapportage_gebruiker }}"
        mode: "0640"
      notify: herstart rapportage-service

  handlers:
    - name: herstart rapportage-service
      service:
        name: rapportage-api
        state: restarted
ansible-playbook -i inventory.ini playbook.yml
ansible-playbook -i inventory.ini playbook.yml --check   # dry-run
ansible-playbook -i inventory.ini playbook.yml --diff    # toon wijzigingen

--check voert een dry-run uit: Ansible meldt wat er zou veranderen, zonder het daadwerkelijk te doen — onmisbaar om een playbook eerst tegen productie te toetsen voordat u hem echt uitvoert.

Kanttekening bij --check

Sommige modules ondersteunen --check niet volledig — met name command/shell-taken, die standaard altijd als "zouden veranderen" worden gerapporteerd omdat Ansible niet kan weten of ze idempotent zijn. Handlers worden in check-mode bovendien niet getriggerd.

06

Idempotentie: de kern van Ansible

⏱ 10 min

Een taak is idempotent als het uitvoeren ervan hetzelfde resultaat oplevert ongeacht hoe vaak u hem draait. De taak "installeer pakket X" laat het systeem na de eerste uitvoering in de gewenste staat; een tweede uitvoering verandert niets en meldt dat expliciet (ok in plaats van changed). Dat is fundamenteel anders dan een los shellscript met apt install, dat weliswaar ook niets stukmaakt bij een tweede run, maar niet vertelt óf en wát er veranderd is.

ansible-playbook -i inventory.ini playbook.yml
# eerste run: meerdere taken tonen "changed"
ansible-playbook -i inventory.ini playbook.yml
# tweede run, zonder wijzigingen op de machines: alle taken tonen "ok"

Dit rapport — welke taken "changed" waren en welke "ok" — is in de praktijk het eerste signaal dat er iets afwijkt. Als een tweede, ongewijzigde run onverwacht "changed" meldt bij een taak die dat niet zou moeten doen, wijst dat vrijwel altijd op configuratiedrift: iemand heeft de machine buiten Ansible om aangepast.

De module command/shell is hierin de uitzondering: die is van zichzelf niet idempotent (een commando als useradd milan faalt of doet iets bij een tweede keer draaien), tenzij u zelf een voorwaarde toevoegt met creates: of when:. Waar mogelijk kiest Ansible daarom voor gespecialiseerde modules (apt, user, service, copy, template) die idempotentie zelf al regelen.

"Als de tweede run 'changed' meldt op een taak die dat niet hoort te doen," zegt Fenna, "dan heeft iemand buiten Ansible om iets veranderd. Dat rapport is uw eerste drift-detector, nog voordat u een dashboard nodig hebt."

Controlevraag

Uit Werkboek deel 27, Opdracht 27.3 / Uitwerking 27.3

1U voert een playbook tweemaal uit zonder tussentijdse wijzigingen op de machines. Wat is het verschil in uitvoer tussen de eerste en de tweede run, en hoe verklaart u dat vanuit idempotentie?Toon antwoord
Bij de eerste uitvoering tonen de taken die daadwerkelijk iets aanpassen (bijvoorbeeld pakketinstallatie en het plaatsen van een configuratiebestand) changed, en een eventuele handler wordt getriggerd. Bij de tweede uitvoering, zonder wijzigingen aan het systeem tussendoor, tonen diezelfde taken ok en wordt de handler niet getriggerd — hetzelfde playbook, tweemaal uitgevoerd, levert dezelfde eindtoestand op en meldt de tweede keer expliciet dat er niets te doen was.
Controlevraag

Uit Werkboek deel 27, Opdracht 27.4c / Uitwerking 27.4c

2U past index.html op een managed node handmatig aan, buiten Ansible om, en draait daarna het playbook opnieuw (zonder --check). Wat gebeurt er?Toon antwoord
De copy-taak detecteert dat de inhoud van index.html afwijkt van wat gedefinieerd staat, meldt dat als changed, en herstelt het bestand naar de gedefinieerde staat — waarna de handler opnieuw triggert. Dit demonstreert het kernprincipe van declaratieve automatisering: Ansible dwingt de gedefinieerde staat af, ongeacht wat er buiten Ansible om is gewijzigd. Dat is precies waarom een onverwachte "changed" bij een tweede run een signaal is voor configuratiedrift.
07

Naar rollen: herbruikbare structuur

⏱ 10 min

Voor één playbook volstaat de structuur uit sectie 5. Zodra automatisering voor meerdere onderdelen van het cluster (webserver, database, monitoring) nodig is, wordt een platte lijst van taken al snel onoverzichtelijk. Ansible rollen groeperen tasks, templates, variabelen en handlers in een vaste mapstructuur:

roles/
└── rapportage_api/
    ├── tasks/main.yml
    ├── templates/rapportage.conf.j2
    ├── handlers/main.yml
    └── defaults/main.yml

Een playbook verwijst dan simpelweg naar de rol:

- name: Rapportagecluster inrichten
  hosts: rapportage
  become: true
  roles:
    - rapportage_api

Dit is precies de vorm waarin het Rapportagecluster in deel 30 wordt geautomatiseerd: één rol per verantwoordelijkheid, samen aangeroepen vanuit één overzichtelijk playbook.

Controlevraag

Uit Werkboek deel 27, Opdracht 27.5b / Uitwerking 27.5b

1Welk voordeel heeft een rolstructuur (webserver, hardening, monitoring) boven drie losse playbooks als het Rapportagecluster van drie naar acht machines groeit, waarvan niet alle acht dezelfde rollen nodig hebben?Toon antwoord
Het voordeel wordt zichtbaar zodra niet elke machine dezelfde rollen nodig heeft: bij acht machines waarvan er bijvoorbeeld drie een database draaien en vijf alleen de rapportage-API, kunt u per hostgroep in de inventory aangeven welke rollen gelden, zonder playbook-logica te dupliceren of met veel when-voorwaarden te werken. Elke rol is bovendien apart te testen, te versioneren en te hergebruiken in een ander playbook — bijvoorbeeld de hardening-rol ook toepassen op machines buiten het Rapportagecluster.
