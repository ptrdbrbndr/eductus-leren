01

Waarom Milan naar containers kijkt

⏱ 8 min

Het Rapportagecluster bij Meridiaan Pensioen draait op dit moment drie Ubuntu Server-machines die stuk voor stuk handmatig zijn ingericht: Python-versie, systeempakketten, een rapportage-API en een paar hulpscripts, allemaal rechtstreeks op het besturingssysteem. Fenna heeft Milan er al twee keer op gewezen dat "het werkt op mijn machine" bij dit landschap een reëel risico is geworden. De acceptatieomgeving en de productieomgeving lopen inmiddels uiteen in Python-patchversie, en een dependency-update die in test goed ging, brak vorige maand de productie-API omdat daar nog een oudere systeembibliotheek stond.

Containers lossen dat specifieke probleem op: de applicatie en alles wat hij nodig heeft om te draaien — runtime, bibliotheken, configuratie — worden samen verpakt in een image. Diezelfde image draait ongewijzigd op Milans laptop, in acceptatie en in productie.

"We containeriseren omdat het een concreet probleem oplost," zegt Fenna, "niet omdat het erbij hoort."

Dat onderscheid is deel 26 zelf.

02

Virtuele machine versus container

⏱ 10 min

Een virtuele machine virtualiseert hardware. Een hypervisor (bijvoorbeeld de VM-tools uit deel 3 en 4 van niveau 1) presenteert virtuele hardware waarop een volledig eigen besturingssysteem met eigen kernel draait. Een container virtualiseert niet de hardware maar het besturingssysteem: alle containers op een host delen dezelfde Linux-kernel, en worden van elkaar en van de host afgeschermd met kernelmechanismen — namespaces (elke container ziet zijn eigen procesboom, netwerkstack, bestandssysteem en hostnaam) en cgroups (elke container krijgt een begrensd aandeel CPU, geheugen en I/O).

Het gevolg is een groot verschil in gewicht en opstarttijd. Een VM start een volledige kernel op en kost al snel honderden megabytes tot gigabytes; een container start een proces in een geïsoleerde omgeving en is meestal in minder dan een seconde beschikbaar, met een image van enkele tientallen tot een paar honderd megabytes.

Dat gedeelde-kernel-gegeven heeft ook een consequentie voor security, die in deel 25 al even is aangestipt: een kernelkwetsbaarheid raakt in potentie alle containers op de host, terwijl een VM daar door de extra virtualisatielaag beter tegen is afgeschermd.

Afweging voor het Rapportagecluster

De rapportagediensten zijn intern en niet internet-facing, dus het team accepteert dat risico tegen de winst in consistentie en deploysnelheid.

03

Docker installeren op Ubuntu Server

⏱ 10 min

Docker Engine wordt niet vanuit de standaard Ubuntu-repository geïnstalleerd maar vanuit Docker's eigen apt-repository, zodat u actuele versies krijgt:

sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
  https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin

Na installatie draait Docker als systemd-service (het aanknopingspunt met deel 19 van niveau 2 is direct):

sudo systemctl status docker
sudo systemctl enable docker

Standaard heeft alleen root toegang tot de Docker-socket. Om sudo voor elk commando te vermijden, voegt Milan zijn eigen gebruiker toe aan de docker-groep:

sudo usermod -aG docker milan
Securitypunt van Fenna

Lidmaatschap van de docker-groep is functioneel gelijk aan root-rechten op de host, omdat een container zonder verdere beperkingen bij het bestandssysteem van de host kan komen. Op het Rapportagecluster krijgt alleen het beheerdersaccount die groep, niet de service-accounts van de applicaties.

Controlevraag

Uit Werkboek deel 26, Opdracht 26.1b

1U draait docker run hello-world voor het eerst op een verse installatie. Wat gebeurt er precies?Toon antwoord
Docker haalt (als hij nog niet lokaal aanwezig is) de image hello-world op van Docker Hub, start er een container van die één proces uitvoert (een korte tekst printen) en stopt daarna vanzelf, omdat het hoofdproces klaar is. De container blijft in gestopte toestand zichtbaar met docker ps -a.
04

Images en containers, en een eigen image bouwen

⏱ 16 min

Een image is een read-only sjabloon: een gelaagde stapel bestandssysteemwijzigingen, opgebouwd via een Dockerfile. Een container is een draaiende (of gestopte) instantie van een image, met een eigen schrijfbare laag erbovenop. Van één image kunt u tegelijk meerdere containers starten, elk met hun eigen staat.

docker run hello-world          # image ophalen en één keer draaien
docker images                   # lokaal aanwezige images tonen
docker ps                       # draaiende containers tonen
docker ps -a                    # ook gestopte containers tonen

Een praktisch voorbeeld: de rapportage-API testen in een tijdelijke container met poortdoorschakeling en achtergrondmodus:

docker run -d --name rapportage-test -p 8080:8080 nginx:latest
curl -I http://localhost:8080
docker logs rapportage-test
docker stop rapportage-test
docker rm rapportage-test

De -p 8080:8080-vlag koppelt poort 8080 op de host aan poort 8080 in de container; -d (detached) laat de container op de achtergrond draaien; --name geeft de container een leesbare naam in plaats van een gegenereerde id.

Een eigen image bouwen: de Dockerfile

Voor de rapportage-API van Meridiaan schrijft Milan een Dockerfile die de applicatie en zijn afhankelijkheden vastlegt:

FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8080
ENV RAPPORTAGE_ENV=productie

USER 1000:1000
CMD ["python", "-m", "rapportage_api"]

Elke instructie voegt een laag toe aan de image; Docker cachet lagen die niet zijn veranderd, waardoor COPY requirements.txt . bewust vóór COPY . . staat — een wijziging in de broncode hoeft dan niet de dependency-installatie te forceren. De regel USER 1000:1000 is een hardeningsmaatregel uit dezelfde familie als deel 25: de container draait niet als root binnenin.

docker build -t meridiaan/rapportage-api:1.0 .
docker run -d --name rapportage-api -p 8080:8080 meridiaan/rapportage-api:1.0
docker exec -it rapportage-api /bin/bash

docker exec -it opent een interactieve shell in een reeds draaiende container — nuttig om snel te controleren wat er binnenin gebeurt, niet bedoeld als vaste werkwijze.

Controlevraag

Uit Werkboek deel 26, Opdracht 26.2

1U bouwt een minimale Dockerfile op basis van nginx:alpine die een eigen index.html kopieert. Hoe ziet die Dockerfile eruit, en hoe controleert u dat de container uw eigen tekst toont?Toon antwoord
Een voorbeeld-Dockerfile: FROM nginx:alpine, COPY index.html /usr/share/nginx/html/index.html, EXPOSE 80 — met een index.html die de gevraagde tekst bevat. Bouwen met docker build -t oefening/rapportage-homepage:1.0 ., starten met docker run -d --name rapportage-homepage -p 8081:80 oefening/rapportage-homepage:1.0, en controleren met curl http://localhost:8081 — de uitvoer moet de eigen tekst tonen in plaats van de standaard-nginx-pagina. docker logs rapportage-homepage toont de toegangslogregel van de curl-aanroep; docker stop rapportage-homepage && docker rm rapportage-homepage ruimt de container op, de image blijft bestaan tot u hem expliciet verwijdert met docker rmi.
05

Volumes en persistente data

⏱ 8 min

Een container is van zichzelf vergankelijk: verwijdert u hem, dan verdwijnt zijn schrijfbare laag mee. Voor gegevens die dat moeten overleven — rapportagebestanden, een database — gebruikt Docker volumes:

docker volume create rapportage-data
docker run -d --name rapportage-api \
  -v rapportage-data:/data \
  -p 8080:8080 meridiaan/rapportage-api:1.0

Alles wat de container naar /data schrijft, komt terecht in het volume rapportage-data, dat blijft bestaan ook als de container wordt verwijderd en opnieuw wordt aangemaakt — precies het patroon dat in deel 29 (back-up) terugkomt: een volume is een van de dingen die u structureel moet meenemen in een back-upstrategie.

Controlevraag

Uit Werkboek deel 26, Opdracht 26.3c

1Waarom zijn volumes relevant voor het Rapportagecluster, en welke twee soorten data zou u willen scheiden van de container zelf?Toon antwoord
De twee relevante datasoorten zijn: de gegenereerde rapportagebestanden zelf (moeten een container-herstart of -update overleven) en eventuele lokale cache- of tussenbestanden (mogen vergankelijk zijn). Alleen de eerste categorie hoort in een volume; de tweede mag in de schrijfbare laag van de container blijven, juist omdat die na een herstart met een schone lei moet beginnen.
06

Meerdere containers samen: Docker Compose

⏱ 12 min

Het Rapportagecluster bestaat straks niet uit één container maar uit een klein setje: de API, een cachelaag en een reverse proxy. Dat met losse docker run-commando's beheren is foutgevoelig. Docker Compose beschrijft de samenhang in één bestand, compose.yaml:

services:
  rapportage-api:
    build: .
    image: meridiaan/rapportage-api:1.0
    ports:
      - "8080:8080"
    volumes:
      - rapportage-data:/data
    environment:
      RAPPORTAGE_ENV: productie
    restart: unless-stopped

  cache:
    image: redis:7-alpine
    restart: unless-stopped

volumes:
  rapportage-data:
docker compose up -d
docker compose ps
docker compose logs -f rapportage-api
docker compose down

Compose bouwt hiermee automatisch een intern netwerk waarin de services elkaar bij naam kunnen bereiken (rapportage-api kan bijvoorbeeld verbinden met host cache, poort 6379) — een klein voorproefje van hoe het Rapportagecluster er in deel 30 uit gaat zien.

Aandachtspunt bij nabespreking

depends_on regelt alleen de opstartvolgorde van de containers, niet of de dienst binnenin al gereed is om verbindingen te accepteren — dat onderscheid is de reden waarom productiedeployments vaak een expliciete gereedheidscontrole (health check) toevoegen.

Waar containers niet voor bedoeld zijn

Fenna's checklist voor Milan bevat één waarschuwende regel: een container is geen lichtgewicht virtuele machine om een heel besturingssysteem in te draaien, en is ook geen vervanging voor een goed geconfigureerde host. Systemd, cron en losse achtergrondprocessen horen niet standaard in een container; het gangbare patroon is één hoofdproces per container. Wie dat loslaat, krijgt een container die zich als een mini-VM gedraagt en daarmee de voordelen van reproduceerbaarheid en snel opstarten weer kwijtraakt.

Samenvatting

  • Een VM virtualiseert hardware met een eigen gastkernel; een container virtualiseert het besturingssysteem en deelt de hostkernel via namespaces en cgroups. Dat maakt containers lichter en sneller, maar minder streng geïsoleerd.
  • Docker Engine wordt op Ubuntu Server geïnstalleerd via Docker's eigen apt-repository, niet via de standaardrepository.
  • Een image is een read-only sjabloon opgebouwd uit een Dockerfile; een container is een draaiende instantie ervan met een eigen schrijfbare laag.
  • Volumes ontkoppelen persistente data van de levensduur van een container.
  • Docker Compose beschrijft meerdere samenhangende containers in één YAML-bestand en is het bruikbare startpunt voor een klein cluster van diensten zoals het Rapportagecluster.
  • Containers zijn geen vervanging voor een goed ingerichte host; het gangbare patroon is één hoofdproces per container.

Kernbegrippen

Container — een geïsoleerde, draaiende instantie van een image, die de kernel van de host deelt via namespaces en cgroups.

Image — een read-only, gelaagd sjabloon voor een container, opgebouwd via een Dockerfile.

Dockerfile — een tekstbestand met bouwinstructies (FROM, COPY, RUN, CMD e.d.) waarmee een image wordt gebouwd.

Volume — door Docker beheerde opslag die losstaat van de levenscyclus van een individuele container, gebruikt voor persistente data.

Docker Compose — hulpmiddel om meerdere samenhangende containers als één toepassing te definiëren en te beheren via een YAML-bestand.

Namespace / cgroup — kernelmechanismen die respectievelijk isolatie (wat een proces ziet) en resourcebegrenzing (hoeveel een proces mag gebruiken) aan een container geven.

Controlevraag

Uit Werkboek deel 26, Opdracht 26.5

1Meridiaan overweegt drie componenten: (1) de rapportage-API, (2) een nachtelijke batchjob met veel I/O, (3) een oud maatwerkpakket dat een specifieke, verouderde kernelmodule vereist. Container, VM, of blijft-op-eigen-host?Toon antwoord
Rapportage-API — container. Stateless, herstart-vriendelijk, dezelfde image moet in acceptatie en productie identiek draaien; precies het scenario waar containers voor gemaakt zijn. Nachtelijke batchjob met zware I/O — twijfelgeval, neigt naar host of container zonder resourcebeperking. Een container kán, maar de I/O-isolatie van cgroups voegt weinig toe zolang de job als enige zware proces op de machine draait; het argument vóór containeriseren is hier reproduceerbaarheid van de scriptomgeving, niet isolatie. Oud maatwerkpakket met verouderde kernelmodule — VM, niet container. Een container deelt de hostkernel en kan dus geen eigen, andere kernelmodule meenemen; alleen een VM (of een eigen fysieke machine) biedt dat.
