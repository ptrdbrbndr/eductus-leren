01

Waar dit deel over gaat

⏱ 6 min

Elke term uit deel 24 — shardsleutel, co-locatie, referentietabel, rebalancing — krijgt in dit deel een concrete CREATE-opdracht. Dit deel implementeert letterlijk de concepten van vorige keer, met Citus als het gereedschap.

Na dit deel kun je:

  • de architectuur van een Citus-cluster (coördinator, workers) beschrijven;
  • een distributed table en een reference table aanmaken en hun onderlinge samenhang uitleggen;
  • co-locatie expliciet configureren met colocate_with;
  • een EXPLAIN-plan op een distributed query lezen en onderscheid maken tussen lokale en cross-shard-uitvoering;
  • rebalancing met Citus' ingebouwde gereedschap uitvoeren en de risico's herkennen die ondanks automatisering blijven bestaan;
  • een bestaande, gepartitioneerde tabel migreren naar een Citus distributed table;
  • beoordelen of Citus voor een gegeven situatie het juiste gereedschap is.
02

Wat Citus is: coördinator en workers

⏱ 10 min

Citus is een PostgreSQL-extensie — geen apart databasesysteem, geen fork. Je installeert hem op een gewone PostgreSQL-installatie, op dezelfde manier waarop je pg_trgm of pgcrypto installeerde, en hij voegt sharding-functionaliteit toe aan wat verder gewoon PostgreSQL is.

Wat dat concreet betekent: alle SQL die je in niveau 1 en 2 leerde blijft geldig, alle systeemweergaven blijven bestaan met Citus-specifieke aanvullingen, en elke node in een cluster is een volwaardige PostgreSQL-server met alles wat daarbij hoort — WAL, vacuum, indexen, replicatie, zelfs Patroni voor HA per node indien gewenst.

                  ┌──────────────┐
   Applicatie ──→ │ Coördinator  │
                  │ (weet WAT    │
                  │  waar staat) │
                  └──────┬───────┘
           ┌─────────────┼─────────────┐
           ▼             ▼             ▼
     ┌──────────┐  ┌──────────┐  ┌──────────┐
     │ Worker 1 │  │ Worker 2 │  │ Worker 3 │
     │ (shards) │  │ (shards) │  │ (shards) │
     └──────────┘  └──────────┘  └──────────┘

De coördinator is het aanspreekpunt voor de applicatie. Hij bevat in de gangbare opzet geen shard-data zelf, maar wel de metadata: welke tabel is gesherd, op welke sleutel, en welke shard op welke worker staat. Elke query komt bij de coördinator binnen, die hem herschrijft naar één of meerdere queries op de betrokken workers en de resultaten samenvoegt.

De workers zijn gewone PostgreSQL-servers die de daadwerkelijke shards bevatten — elk een fysieke tabel die een deel van de logische, gesharde tabel vertegenwoordigt.

Let op

De coördinator kan een single point of failure zijn, tenzij hij zelf ook met Patroni hoogbeschikbaar wordt gemaakt. Recente Citus-versies ondersteunen ook een opzet zonder aparte coördinator-node, maar het klassieke model met een aparte coördinator blijft het meest voorkomend en het duidelijkst om te leren.

03

Een cluster opzetten: distributed en reference tables

⏱ 18 min

Het cluster

-- Op elke node (coördinator én workers)
CREATE EXTENSION citus;

-- Alleen op de coördinator: workers registreren
SELECT citus_add_node('worker1-host', 5432);
SELECT citus_add_node('worker2-host', 5432);
SELECT citus_add_node('worker3-host', 5432);

-- Controleren
SELECT * FROM citus_get_active_worker_nodes();

Vanaf dit punt gedraagt de coördinator zich naar de applicatie toe als één gewone PostgreSQL-database — het enige verschil is dat sommige tabellen, die je hierna expliciet distribueert, hun data over de workers hebben verspreid.

Distributed tables

CREATE TABLE deelnemer (
    deelnemer_id integer GENERATED ALWAYS AS IDENTITY,
    fonds_id     integer NOT NULL,
    achternaam   text NOT NULL,
    bsn_hash     text NOT NULL,
    PRIMARY KEY (deelnemer_id)
);

-- Distribueren op de shardsleutel uit deel 24
SELECT create_distributed_table('deelnemer', 'deelnemer_id');

Vanaf create_distributed_table bestaat deelnemer niet meer als één fysieke tabel — Citus heeft hem opgesplitst in standaard 32 shards, verdeeld over de geregistreerde workers, met hash-gebaseerde verdeling op deelnemer_id. Meer shards dan workers is gebruikelijk, zodat een worker meerdere shards draagt en toekomstige rebalancing kleinere eenheden kan verplaatsen.

Reference tables

Het concept uit deel 24 wordt hier één functieaanroep:

CREATE TABLE fonds (
    fonds_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    naam     text NOT NULL,
    sector   text NOT NULL
);

SELECT create_reference_table('fonds');

Wat er nu is: een volledige kopie van fonds op elke worker. Een join tegen fonds vanuit een gesharde tabel blijft op elke worker lokaal — geen cross-shard-verkeer nodig, precies de belofte uit deel 24. Wijzigingen op een reference table (een nieuw fonds toevoegen) worden door Citus automatisch naar elke worker gerepliceerd.

Controlevragen

Uit Werkboek deel 25, Opdracht 25.2 — distributed tables bouwen

1Opdracht 25.2 vraagt om fonds, deelnemer, dienstverband en mutatie aan te maken, deelnemer te distribueren op deelnemer_id, fonds een reference table te maken, en dat te controleren op pg_dist_partition. Waarom moet je create_reference_table gebruiken voor fonds en niet create_distributed_table?Toon antwoord
fonds is klein en zelden gewijzigd — precies het profiel voor een reference table. Zou je fonds distribueren, dan zou elke join tegen fonds vanuit een gesharde tabel cross-shard worden, met onnodige coördinatiekosten voor een tabel die klein genoeg is om overal een kopie van te hebben.
2Wat toont een query op citus_shards voor de tabel deelnemer direct na create_distributed_table, en hoeveel shards verwacht je standaard?Toon antwoord
De verdeling van de shards van deelnemer over de geregistreerde workers — standaard 32 shards, verdeeld op basis van de hash van deelnemer_id. Dit aantal (citus.shard_count) is vooraf in te stellen en bepaalt de fijnmazigheid van toekomstige rebalancing.
04

Co-locatie expliciet maken

⏱ 14 min

Standaard krijgt elke distributed table zijn eigen, onafhankelijke sharding-schema. Voor co-locatie moet je expliciet aangeven dat twee tabellen dezelfde verdeling moeten delen:

CREATE TABLE dienstverband (
    dienstverband_id bigint GENERATED ALWAYS AS IDENTITY,
    deelnemer_id      integer NOT NULL,
    werkgever_id      integer NOT NULL,
    PRIMARY KEY (dienstverband_id, deelnemer_id)
);

SELECT create_distributed_table('dienstverband', 'deelnemer_id',
    colocate_with => 'deelnemer');

Wat colocate_with garandeert: rijen in dienstverband met dezelfde deelnemer_id als een rij in deelnemer belanden gegarandeerd op dezelfde worker. Een join tussen de twee op deelnemer_id is daardoor altijd lokaal, ongeacht welke specifieke deelnemer het betreft.

-- Controleren of twee tabellen co-located zijn
SELECT logicalrelid, colocationid FROM pg_dist_partition
WHERE logicalrelid IN ('deelnemer'::regclass, 'dienstverband'::regclass);
-- gelijke colocationid = co-located
De valkuil

Twee tabellen op dezelfde shardsleutel zijn niet automatisch co-located. Citus koppelt tabellen alleen expliciet via colocate_with — een aanname die niet wordt geverifieerd, kan tot onnodig cross-shard-verkeer leiden zonder dat iemand het merkt totdat de prestaties tegenvallen.

Controlevragen

Uit Werkboek deel 25, Opdracht 25.4 — co-locatie testen

1Opdracht 25.4 laat je een tabel aanspraak aanmaken, gedistribueerd op deelnemer_id maar zonder colocate_with. Verwacht je dezelfde colocationid als deelnemer? En wat toont een join tussen beide in EXPLAIN?Toon antwoord
Niet automatisch dezelfde colocationid, ondanks de identieke shardsleutel — Citus koppelt alleen expliciet. Een join tussen deelnemer en aanspraak is daardoor cross-shard: dezelfde deelnemer_id-waarden kunnen op verschillende workers terechtkomen, door verschillende hash-toewijzing tussen de twee onafhankelijke sharding-schema's.
2Hoe corrigeer je dit, en wat verandert er in de Task Count van dezelfde join na de correctie?Toon antwoord
aanspraak opnieuw distribueren, nu wél met colocate_with => 'deelnemer'. Na deze correctie: Task Count: 1 voor dezelfde join, in plaats van cross-shard. De les: co-locatie is nooit impliciet, ook niet bij een identieke shardsleutel.
05

Query's en Task Count: wat blijft hetzelfde

⏱ 16 min

Bijna alles blijft hetzelfde. Dit is het punt dat Citus zo aantrekkelijk maakt ten opzichte van applicatieniveau-sharding: de applicatie schrijft gewone SQL, zonder te weten dat de data over meerdere servers verspreid is.

SELECT * FROM deelnemer WHERE deelnemer_id = 42;
UPDATE deelnemer SET achternaam = 'Jansen' WHERE deelnemer_id = 42;

Voor elk van deze query's herkent Citus, op basis van de WHERE-voorwaarde op de shardsleutel, direct welke ene shard — en dus welke ene worker — de query moet raken.

-- Geen voorwaarde op de shardsleutel: alle workers moeten mee
SELECT count(*) FROM deelnemer WHERE fonds_id = 2;

Deze query kan niet naar één worker worden gestuurd: fonds_id is niet de shardsleutel, dus Citus weet niet vooraf welke shard de relevante rijen bevat. De coördinator stuurt de query naar alle workers, elk telt zijn eigen deel, en de coördinator sommeert de deelresultaten — een tweetraps-aggregatie. Karins kwartaalrapportage, die over alle fondsen gaat, is precies dit soort query: werkend, maar duurder dan een lokale.

EXPLAIN en Task Count

EXPLAIN SELECT * FROM deelnemer WHERE deelnemer_id = 42;

Custom Scan (Citus Adaptive)
  Task Count: 1
  Tasks Shown: All
  ->  Task
        Node: host=worker2 port=5432
        ->  Index Scan using deelnemer_pkey on deelnemer_102008
              Index Cond: (deelnemer_id = 42)

Task Count: 1 bevestigt dat deze query precies één shard raakt, op precies één worker. Zonder voorwaarde op de shardsleutel toont EXPLAIN in plaats daarvan Task Count: 32 (of het aantal shards) — alle shards moeten worden doorzocht, met de extra kostenpost van netwerkverkeer tussen coördinator en elke worker.

De discipline

Controleer met EXPLAIN of je query het gunstige (Task Count: 1) of het dure (Task Count: <shard_count>) pad neemt, vóórdat je aanneemt dat een query snel is. De shardsleutel moet in de WHERE-clausule staan, net zoals een partitiesleutel moet voorkomen voor pruning.

Controlevragen

Uit Werkboek deel 25, Opdracht 25.3 — Task Count zien veranderen

1Opdracht 25.3d vraagt EXPLAIN op een join tussen deelnemer en de reference table fonds — zonder dat daar colocate_with tussen is ingesteld. Blijft dit lokaal? Verklaar met sectie 3 van dit deel.Toon antwoord
Ja, lokaal, ondanks het ontbreken van colocate_with. Verklaring: fonds is een reference table — die staat al volledig gekopieerd op élke worker, dus elke worker kan lokaal joinen tegen zijn eigen kopie, ongeacht welke shard van deelnemer wordt geraakt. colocate_with is alleen nodig tussen twee distributed tables.
2Opdracht 25.3e vraagt een GROUP BY soort op mutatie zonder filter. Wat gebeurt er met de Task Count, en wat doet de coördinator met de deelresultaten?Toon antwoord
Task Count: <shard_count> — elke worker voert zijn eigen gedeeltelijke GROUP BY soort, count(*) uit, en de coördinator sommeert de gedeeltelijke tellingen per soort tot het eindtotaal: een tweetraps-aggregatie, griffig voor count/sum, complexer voor bijvoorbeeld een exacte median.
06

Rebalancing, en wat Citus niet oplost

⏱ 14 min
-- Een nieuwe worker toevoegen
SELECT citus_add_node('worker4-host', 5432);

-- Shards herverdelen zodat de nieuwe worker ook data draagt
SELECT rebalance_table_shards('deelnemer');

rebalance_table_shards implementeert het expand-migrate-contract-patroon uit deel 24 grotendeels automatisch: shards worden gekopieerd naar de nieuwe worker, verkeer wordt omgeleid, en de oude locatie wordt opgeschoond, met minimale onderbreking van lopend verkeer.

Wat automatisering wél wegneemt: het handmatige kopieerwerk, de coördinatie tussen expand/migrate/contract, en veel risico op menselijke fouten. Wat het niet wegneemt: de noodzaak om te verifiëren dat de rebalancing correct is afgerond, en de planning — wanneer je rebalancet, en of de resulterende verdeling daadwerkelijk gelijkmatiger is.

Wat Citus niet automatisch oplost

Cross-shard-transacties vereisen nog steeds bewust ontwerp — Citus ondersteunt 2PC voor transacties die meerdere shards raken, maar maakt dat mogelijk, niet gratis. Globale uniciteit buiten de shardsleutel blijft een aandachtspunt: een UNIQUE-constraint op een kolom die niet de shardsleutel is, kan Citus niet over shards heen afdwingen. HA per node is niet automatisch — Citus lost horizontale capaciteit op, niet beschikbaarheid; die twee zijn orthogonale eisen. En back-up moet per node worden ingericht: een consistente back-up van coördinator plus alle workers, op hetzelfde moment, is complexer dan een back-up van één server.

Controlevraag

Uit Werkboek deel 25, Opdracht 25.6 — rebalancing

1Opdracht 25.6c vraagt een verificatiestap na een rebalancing: klopt het totaal aantal rijen in deelnemer nog met wat je vóór de rebalancing had? Waarom is deze stap niet optioneel, ook al draait rebalance_table_shards grotendeels automatisch?Toon antwoord
Automatisering vermindert het risico op fouten, het elimineert ze niet — dezelfde discipline als bij elke migratie in deze cursus. Een rijtelling vóór en ná die niet overeenkomt, wijst op een probleem tijdens de rebalancing dat zonder expliciete verificatie onopgemerkt zou blijven. De co-located tabellen (dienstverband, mutatie) moeten daarbij dezelfde verschuiving volgen als deelnemer, om co-locatie te behouden.
07

Migreren, en wanneer Citus wel of niet

⏱ 16 min

Migreren van een gepartitioneerde tabel naar Citus

De volledige toepassing van het architectuur-migratiepad uit deel 23 en het sharding-migratiepad uit deel 24, nu met Citus als concreet gereedschap: 1) Citus beschikbaar maken (extensie, workers registreren). 2) Een bestaande, op tijd gepartitioneerde tabel kan niet direct gedistribueerd worden op een andere sleutel — een nieuwe tabel opzetten met de juiste shardsleutel en colocate_with. 3) Data overzetten, via logische replicatie of een backfill-patroon. 4) Omschakelmoment, verificatie, en pas dan de oude tabel opruimen. Dit is geen nieuwe migratietechniek — het is expand-contract plus de shardsleutel-analyse plus de Citus-syntax, drie eerder geleerde stukken kennis samengevoegd.

Wanneer Citus, wanneer niet

Citus past goed bij een datamodel dat natuurlijk co-located kan worden rond één dominante sleutel, een aangetoonde capaciteitsgrens die verticaal schalen niet meer oplost, en een team dat de operationele last van meerdere PostgreSQL-nodes aankan. Citus past minder goed bij een datamodel met veel sterk verweven relaties zonder natuurlijke co-locatie-sleutel, een werklast die overwegend uit cross-shard-aggregaties bestaat, of een organisatie die de mogelijkheden van verticaal schalen nog niet heeft uitgeput.

Voor de Pensioenfederatie, concreet vandaag: met drie fondsen en een volume ruim onder de aangenomen capaciteitsgrens is Citus nu niet nodig — het architectuuradvies uit deel 23 volstaat. Wat vandaag is opgebouwd, is de kennis om, wanneer het wél nodig wordt, niet vanaf nul te hoeven beginnen.

Controlevragen

Uit Werkboek deel 25, Opdracht 25.8 en 25.9 — wel of niet Citus, het implementatievoorstel

1Opdracht 25.8d schetst een datamodel waarin bijna elke rapportagequery per definitie alle fondsen tegelijk aggregeert. Zou je Citus aanraden?Toon antwoord
Waarschijnlijk niet, of met terughoudendheid. Als vrijwel elke query inherent cross-shard is, wordt de winst van sharding grotendeels opgegeten door coördinatiekosten. Heroverweeg eerst of het datamodel een natuurlijke co-locatie-sleutel heeft, vóór Citus wordt ingevoerd.
2Het modelantwoord bij opdracht 25.9 (het implementatievoorstel) stelt voor Karins kwartaalrapportage met een hoge Task Count te accepteren en te verzachten met een materialized view. Waarom past dat specifiek bij een periodieke rapportage en niet bij elke query met hoge Task Count?Toon antwoord
Karins kwartaalrapportage (totalen per sector over alle fondsen) blijft inherent cross-shard — er is geen shardsleutel die dit lokaal zou maken zonder de primaire co-locatie rond deelnemer_id op te geven. Voor een periodieke, niet-realtime rapportage is een nachtelijk ververste materialized view een goede verzachting: de dure aggregatie gebeurt eenmalig, in plaats van bij elke interactieve raadpleging. Bij een query die continu, interactief en met hoge Task Count zou draaien, zou diezelfde verzachting niet volstaan.
