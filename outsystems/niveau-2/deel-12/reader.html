Deel 12 — Modules, libraries, afhankelijkheden

Reader · Ductus-cursus OutSystems · Niveau 2 — Professional · deel 12 van 30

12.1 Van app naar module: wat verandert er

In niveau 1 bouwde je Verzuimmeldingen als één zelfstandige app. In een landschap als WGP 2.0 spreek je liever van modules: elke module heeft een duidelijk afgebakende verantwoordelijkheid en communiceert met andere modules via expliciete, publieke interfaces — niet door in elkaars interne structuur te graven.

Voor WGP 2.0 betekent dit een concrete beslissing: de gedeelde mutatielogica uit deel 11 wordt een eigen Core-module genaamd MeridiaanMutatiesCore, met een publieke interface (server actions die andere modules mogen aanroepen) en een private interne structuur die andere modules niet direct kunnen benaderen.

12.2 Libraries versus applicaties

Een library is een module die zelf geen eindgebruikersschermen bevat — puur herbruikbare logica of entiteiten, bedoeld om door andere modules te worden gebruikt. MeridiaanMutatiesCore is een library. Een applicatie daarentegen bevat wel eindgebruikersschermen (WGP 2.0 zelf, Verzuimmeldingen).

Het onderscheid is niet alleen semantisch: een library publiceert een expliciete, stabiele interface waarop andere modules kunnen vertrouwen, terwijl de interne implementatie vrij te wijzigen blijft zolang die interface intact blijft — hetzelfde principe als een goed ontworpen API (zie de API-cursus), maar dan binnen het platform zelf.

12.3 Afhankelijkheden beheren

Elke keer dat een module een andere module gebruikt, ontstaat een afhankelijkheid. Het platform houdt deze automatisch bij, en TrueChange (deel 2) gebruikt deze informatie om te bepalen wat een wijziging in module X betekent voor module Y. Voor Meridiaan is dit direct praktisch relevant: als MeridiaanMutatiesCore wordt gewijzigd, moet het platform kunnen aangeven welke andere modules (WGP 2.0, Verzuimmeldingen, en potentieel nog meer satellieten) daardoor geraakt worden.

Cyclische afhankelijkheden — module A hangt af van module B, die weer afhangt van module A — zijn een architecturaal alarmsignaal, geen technisch detail. Ze duiden meestal op een verkeerde laagindeling (deel 11): iets dat eigenlijk in een lagere, gedeelde laag hoort, staat nu verdeeld over twee modules die elkaar nodig hebben.

12.4 Spoorsplitsing: modulebeheer in O11 versus ODC

O11: modules zijn eigen Service Studio-projecten met expliciete referenties naar andere modules; afhankelijkheden beheer je grotendeels handmatig, met LifeTime als overzicht van welke module welke versie van welke andere module gebruikt.

ODC: modules leven binnen een gedeelde workspace-structuur met een sterker geïntegreerd afhankelijkheidsbeheer — de Portal toont een actueler, directer overzicht van de afhankelijkheidsgraaf, en waarschuwt eerder bij een potentiële cyclische afhankelijkheid dan het equivalente O11-mechanisme.

Kernpunten

  • Modules hebben een afgebakende verantwoordelijkheid en communiceren via expliciete interfaces
  • Libraries bevatten geen eindgebruikersschermen; applicaties wel — libraries publiceren een stabiele interface met vrij wijzigbare interne implementatie
  • Cyclische afhankelijkheden zijn een architecturaal signaal, meestal wijzend op een verkeerde laagindeling
  • ODC biedt sterker geïntegreerd, actueler afhankelijkheidsbeheer dan O11's grotendeels handmatige aanpak
