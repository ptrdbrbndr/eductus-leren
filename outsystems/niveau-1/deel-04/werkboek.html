Deel 4 — Logica

Werkboek · Ductus-cursus OutSystems · Niveau 1 — Fundament · deel 4 van 30

Opdracht 4.1 — Server of client action? (beide banen gezamenlijk)

Bepaal voor elk van de volgende stukken logica van Verzuimmeldingen of dit een server action of een client action moet zijn, en waarom.

a. Controleren of het veld "startdatum" is ingevuld voordat het formulier wordt verzonden.

b. Een nieuwe melding wegschrijven naar de database met status Nieuw.

c. Controleren of de ingevoerde startdatum niet in de toekomst ligt, vergeleken met de systeemdatum van de server.

Uitwerking 4.1

a. Client action — geen serverdata nodig, directe feedback voordat er iets naar de server gaat.

b. Server action — schrijftoegang tot de database is per definitie server-side.

c. Server action, ondanks dat het op het eerste gezicht op client-validatie lijkt. De vergelijking moet tegen de betrouwbare servertijd, niet de (manipuleerbare) kloktijd van de client — anders kan een gebruiker de systeemklok van zijn eigen apparaat aanpassen om de validatie te omzeilen.

Baan A — OutSystems 11

Opdracht 4.A — AanmaakMelding bouwen in Service Studio

Bouw in VerzuimO11 een server action AanmaakMelding die: (1) controleert of de startdatum is ingevuld, (2) bij ontbrekende startdatum een exception opwerpt, (3) bij een geldige startdatum de melding wegschrijft met status Nieuw. Test de flow met de debugger: zet een breakpoint op de conditie-stap en loop de flow door met een lege startdatum.

Uitwerking 4.A

De flow bestaat uit: een If-conditie op de startdatum, een Raise Exception-tak bij ontbrekende waarde, en een Create Entity-stap in de andere tak. Bij het debuggen met een lege startdatum zie je de If-conditie naar de exception-tak springen — dit bevestigt visueel dat de conditie werkt vóórdat er iets naar de database wordt weggeschreven. Herkenningspunt: dit is de eerste keer dat deelnemers een fout bewust laten optreden om te zien hóe het platform daarmee omgaat, in plaats van alleen het happy path te testen.

Baan B — OutSystems Developer Cloud

Opdracht 4.B — AanmaakMelding bouwen in ODC Studio

Herhaal Opdracht 4.A in VerzuimODC. Noteer hoe het opstarten van een debug-sessie in ODC Studio verschilt van Service Studio.

Uitwerking 4.B

De flow-opbouw zelf is identiek. Het verschil zit in het opstarten van de debug-sessie: in ODC Studio is minder handmatige omgevingsconfiguratie nodig — de sessie start doorgaans direct tegen de cloud-workspace zonder dat je eerst een Environment moet selecteren zoals in Service Studio. Het debuggen zelf (breakpoints, variabelen inspecteren) voelt identiek.

Reflectieopdracht 4.2 (beide banen gezamenlijk)

Waarom moet de exception in AanmaakMelding resulteren in een gebruikersvriendelijke boodschap in plaats van de technische foutmelding die het platform standaard zou tonen?

Uitwerking 4.2

Een technische foutmelding (bijvoorbeeld een ruwe database-foutcode) is voor een HR-medewerker onbruikbaar en kan zelfs verwarrend of intimiderend overkomen — het lost het probleem van de gebruiker niet op en kan het vertrouwen in de applicatie schaden. Een gestructureerde Exception Handler geeft je de plek om technische details te loggen (voor de ontwikkelaar) terwijl de gebruiker een begrijpelijke, actiegerichte boodschap ziet. Dit is een klein voorbeeld van een patroon dat in deel 17 (beveiliging serieus) veel groter terugkomt: technische informatie nooit onnodig aan de eindgebruiker blootstellen.
